# am-orchestrator

큰 설계 문서를 작은 작업으로 나누고, 작업마다 [am](../README.md) 의 plan → do → check → commit 흐름을 별도의 `claude -p` 세션으로 돌리는 플러그인입니다. 서로 무관한 작업은 별도 작업 공간(git worktree)에서 동시에 돌립니다. 스킬 1개(`am-orchestrator:run`)와 Node 스크립트 1개로 되어 있고, 의존성은 없습니다(Node 18 이상).

- Claude Code 전용입니다. am 플러그인이 함께 설치돼 있어야 합니다.
- am 플러그인은 작게 유지한다는 규칙이 있어("배치 러너 없음"), 같은 마켓플레이스의 다른 플러그인으로 냅니다. am 의 스킬 본문과 게이트는 복사하지 않고 설치된 것을 그대로 부릅니다.

## 설치

```
/plugin marketplace add AlMandu/am
/plugin install am@am-workflow
/plugin install am-orchestrator@am-workflow
```

대상 저장소 루트에 `am-gate.json` 이 있어야 합니다(없으면 스킬이 어떤 명령을 넣을지 묻습니다).

## 스킬로 쓰기

```
/am-orchestrator:run docs/design.md     설계 문서 하나를 끝까지
/am-orchestrator:run                    멈춘 실행을 이어서
```

스킬을 실행한 세션이 준비(`doctor`) → 분할(`split`) → 실행(`run`)을 알아서 이어 가고, 아래 경우에만 멈추고 결정 카드로 묻습니다.

| 언제 | 무엇을 묻나 |
|---|---|
| 준비 | `am-gate.json` 이 없을 때 넣을 빌드·테스트 명령, 이 세션이 만들지 않은 미커밋 변경의 처리, 시작 전부터 실패하는 게이트 |
| 분할 직후 | 설계 문서가 사용자에게 남긴 결정(화면·범위·되돌리기 어려운 선택) |
| 실행 중 | 계획 단계가 스스로 정할 수 없다고 본 질문(기존 데이터·파일 삭제, 저장 형식 변경·데이터 이전, 저장소 밖 변경, 지침이 확인을 요구하는 일) |
| 막혔을 때 | 세션이 원인을 없앨 수 없는 막힘: 어느 단계부터 다시 할지, 손으로 고칠지, 여기서 멈출지 |

- 실행은 몇 시간이 걸릴 수 있습니다. 세션은 명령을 백그라운드로 띄우고 끝났다는 알림을 기다립니다. 그동안 저장소를 직접 고치거나 게이트가 쓰는 에디터를 열면 안 됩니다.
- 서로 무관한 작업(의존 관계가 없고 예상 파일이 겹치지 않음)은 최대 3개까지 동시에 돕니다. 진행 메시지와 `status` 에 돌고 있는 작업이 모두 보입니다. 아래 "동시 진행" 참고.
- 답을 기다리는 작업이 있어도 그 작업과 무관한 작업은 계속 진행합니다. 더 진행할 작업이 없을 때 모아서 묻습니다.
- 화면·범위 질문은 `am:auto` 와 같은 규칙으로 추천안을 적용하고 "(자동 결정)"으로 남깁니다. 끝나면 세션이 "대신 정한 것"으로 모아 알려 줍니다.
- push 와 merge 는 하지 않습니다. 실행은 `orch/<실행 ID>` 브랜치에 커밋만 쌓습니다.
- 세션을 닫았거나 사용량 한도로 멈췄으면 인자 없이 다시 실행합니다. 끊긴 단계부터 이어 갑니다.
- 늘 드는 토큰은 약 54, 스킬 호출 한 번은 약 2.3k 입니다(`claude --plugin-dir orchestrator plugin details am-orchestrator` 기준).

## 흐름

```
설계 문서 ──split──▶ tasks.json (작업 + 의존 관계 + 사용자가 정할 것)
                         │  사람이 tasks.md 를 읽고 결정에 답함
                         ▼
        run: 작업마다 새 세션으로. 서로 무관한 작업은 동시에(최대 parallel 개)
          1. 계획    /am:plan <작업 설명>     → .am/<slug>/plan.md (늘 이 저장소에서)
             함께 도는 작업이 있으면 여기서 별도 작업 공간(.orchestrator/wt/<실행>/<작업>)을 만들어 2~4 를 그 안에서
          2. 구현    /am:do <slug>            → 코드 변경 (커밋 안 함). am 0.1.3 이하는 /am:plan <slug>
          3. 점검    /am:check <slug>         → .am/<slug>/check.md, 판정 BLOCK 또는 NOTE
                     + 오케스트레이터가 gate.mjs 를 직접 실행
                     막히면 구현 세션을 이어서 수정 → 다시 점검 (기본 2번까지)
          4. 커밋    /am:commit               → 커밋 게이트 훅이 한 번 더 확인, push 안 함
                     커밋 훅이 거부하면 훅이 한 말을 구현 세션에 넘겨 고치고 3부터 다시
          5. 합치기  (별도 작업 공간일 때만) 실행 브랜치 끝이 그사이 움직였으면 그 위로 rebase,
                     게이트를 다시 돌린 뒤 실행 브랜치를 fast-forward. 한 번에 하나씩
                         ▼
        report.md: 완료·막힘·결정 대기, 작업별 사람 확인 체크리스트
```

단계마다 am 에서 쓰는 것과 이 스크립트가 덧붙이는 것은 이렇습니다.

| 단계 | am 에서 쓰는 것 | 오케스트레이터가 하는 일 |
|---|---|---|
| 분할 | (am 에 없음) | 설계 문서를 작업으로 나누게 하고 형식·의존 순서를 검사 |
| 계획 | `am:plan` | 작업 설명(`.am/<slug>/brief.md`)을 써 주고, slug 를 지정하고, `.am/` 밖 파일이 바뀌지 않았는지 확인 |
| 구현 | `am:do <slug>` (am 0.1.3 이하는 `am:plan <slug>`) | 커밋·push 를 막고, 끝난 뒤 변경이 있는지 확인 |
| 점검 | `am:check`, `hooks/gate.mjs --run --json` | 판정을 읽고, 게이트를 직접 한 번 더 돌려 둘 다 통과해야 다음으로 |
| 커밋 | `am:commit`, 커밋 게이트 훅 | 새 커밋이 생겼는지, 남은 변경이 없는지 확인 |

## 직접 실행 (스킬 없이)

스크립트는 `scripts/orchestrator.mjs` 입니다. 저장소를 클론해 두었다면 `node <am 저장소>/orchestrator/scripts/orchestrator.mjs <명령>` 으로 대상 저장소 루트에서 실행합니다(다른 폴더에서는 `--repo <대상 저장소>`).

```
node <경로>/orchestrator.mjs doctor    # claude, am 플러그인, 스킬, 게이트 확인. 설정 파일이 없으면 만듦
```

`doctor` 는 `claude -p` 를 한 번 짧게 불러 세션 시작 정보에서 am 플러그인과 `/am:plan`, `/am:do`, `/am:check`, `/am:commit` 이 실려 오는지, 답이 실제로 오는지(로그인) 봅니다. am 버전도 여기서 읽으므로, am 을 업데이트한 뒤에는 `doctor` 를 다시 실행하세요. 스킬이 실려 오면 슬래시 호출(slash)로, 아니면 SKILL.md 를 읽어 지시문으로 넘기는 방식(inline)으로 동작합니다.

am 플러그인은 설정의 `amPluginRoot`, 세션이 싣고 있는 것, 이 플러그인 곁(같은 저장소의 `plugin/`, 같은 마켓플레이스에서 설치된 `am`) 순서로 찾습니다. am 이 설치돼 있지 않고 곁에서만 찾았으면, 띄우는 세션마다 `--plugin-dir` 로 넘깁니다.

## 명령

```
node orchestrator.mjs split docs/design.md   # 작업 목록 생성 → .orchestrator/runs/<실행 ID>/tasks.md 검토
node orchestrator.mjs decide D1 "토스트로"    # 작업 목록에 딸린 결정에 답
node orchestrator.mjs run --dry-run          # 순서와 실제 claude 명령만 확인
node orchestrator.mjs run                    # 실행 (중단되면 같은 명령으로 이어 감)
node orchestrator.mjs status                 # 작업별 상태
node orchestrator.mjs status --json          # 다음에 할 일(next)과 답할 결정·막힌 작업을 구조로
```

`status --json` 의 `next` 는 `doctor`, `split`, `wait`, `fix-tasks`, `decide`, `answer`, `blocked`, `run`, `done`, `stuck` 중 하나입니다. 스킬은 이 값만 보고 다음 명령을 정합니다.

상태를 바꾸는 명령(`doctor`, `split`, `decide`, `answer`, `run`, `retry`, `done`)은 한 저장소에서 한 번에 하나만 돕니다. 실행 중에 다른 명령을 부르면 거절합니다. 작업 여러 개를 동시에 돌리는 것은 `run` 하나가 안에서 합니다.

`status --json` 의 `running.tasks` 는 돌고 있는 작업마다 단계와 작업 공간을, `parallel` 은 동시에 돌릴 수(`max`)와 하나씩 도는 이유(`reason`), 다시 확인이 필요한지(`stale`)를 알려 줍니다. `run --dry-run` 은 같이 돌 작업을 회차로 묶어 보여 줍니다.

다른 폴더에서 실행할 때는 `--repo <대상 저장소>` 를 붙입니다. 실행은 `orch/<실행 ID>` 브랜치에서 진행되고 push 와 병합은 하지 않습니다.

스킬 없이 직접 돌릴 때 사람이 개입하는 곳은 세 군데입니다(스킬을 쓰면 세션이 이 일을 대신하고, 답이 필요한 것만 묻습니다).

- 분할 직후: `tasks.md` 를 읽고 작업 범위가 맞는지 확인합니다. 고칠 것이 있으면 `tasks.json` 을 직접 고칩니다. 결정 카드에는 `decide` 로 답합니다. 답하지 않은 결정이 막고 있는 작업은 건너뜁니다.
- 계획 중 결정이 나왔을 때: 그 작업만 "결정 필요"로 남고 다른 작업은 계속됩니다. `answer <작업ID> "<답>"` 으로 계획 세션을 이어 마무리합니다.
- 막혔을 때: 기본값은 그 자리에서 멈추고 변경을 작업 트리에 그대로 둡니다. 직접 고친 뒤 `retry <작업ID> --from check`, 손으로 커밋까지 끝냈으면 `done <작업ID>`.

실행이 끝나면 `report.md` 에 작업별 `check.md`(사람이 확인할 "어디서·무엇을·무엇이 보이면 통과")가 한곳에 모입니다.

`run` 의 종료 코드: 0 은 모든 작업 완료, 1 은 남은 작업이 있음(결정 대기나 막힘, 오류 아님), 2 는 오류로 중단(같은 명령으로 이어 감).

실행 중에는 `report.md` 와 `status` 가 지금 돌고 있는 단계("진행 중(구현 중)" 등)를 보여 줍니다. 보고서는 단계가 바뀔 때마다 다시 씁니다. 여러 작업이 함께 돌면 진행 줄 앞에 `[T03]` 처럼 작업 ID 가 붙습니다.

Ctrl+C 로 멈추면 돌고 있던 세션을 모두 함께 끝냅니다. 상태는 단계마다 저장되므로 `run` 을 다시 실행하면 끊긴 단계부터 이어 갑니다. 일부만 돌리고 멈추려면 `run --max-tasks N` 을 씁니다.

막힌 작업을 이어 가는 방법은 보고서의 "사람이 할 일"에 단계별로 적힙니다. 별도 작업 공간에서 막힌 작업은 변경이 그 폴더(`.orchestrator/wt/<실행 ID>/<작업 ID>`)에 남아 있고 안내 첫머리에 그 경로가 나옵니다. 손으로 고치거나 커밋할 때는 그 폴더에서 합니다. 거기서 커밋까지 끝내고 `done <ID>` 하면 다음 `run` 이 실행 브랜치에 합칩니다. `retry <ID> --from plan` 은 작업 공간의 변경을 작업 폴더의 `worktree-N.patch` 로 남기고 지운 뒤 계획부터 다시 합니다.

| 막힌 단계 | 이어 가기 |
|---|---|
| 계획 | 원인을 고친 뒤 `retry <ID> --from plan`. 계획을 직접 `.am/<slug>/plan.md` 로 저장했다면 `retry <ID> --from implement` |
| 구현 | `retry <ID> --from implement` (남은 변경을 먼저 살펴보고 이어서 구현) |
| 점검 | 직접 고친 뒤 `retry <ID> --from check`. 커밋 훅이 계속 거부해 멈춘 경우도 여기에 해당(훅이 한 말은 `commit-rejected-N.md`) |
| 커밋 | 커밋이 안 됐으면 `retry <ID> --from commit`. 커밋은 됐는데 변경이 남았으면: 작업의 것이면 커밋하고 `done <ID>`, 빌드가 다시 쓴 파일이면 `volatilePaths` 에 적고 `done <ID>` |

## 설계 문서를 나누는 규칙

분할 세션에 주는 규칙의 요점입니다(전문은 `orchestrator.mjs` 의 `SYSTEM.split`).

- 작업 하나는 확인할 수 있는 결과 하나. "모델 전부" 같은 계층이나 파일 목록으로 나누지 않습니다.
- 크기는 S 또는 M 만. 파일 8개 안팎, 계획 문서 150줄 이내(am:plan 의 한도)에 들어가야 합니다.
- 어느 작업까지 끝나든 저장소는 빌드되고 게이트를 통과해야 합니다. 얇은 끝-끝 조각을 먼저 만들고 넓힙니다.
- 의존 관계는 앞선 작업으로만, 꼭 필요한 것만.
- 완료 조건은 게이트·테스트·프로브·사람 한 줄 확인 중 하나로 확인할 수 있어야 합니다.
- 요구사항을 지어내거나 빼지 않습니다. 뺀 부분은 사유와 함께 `uncovered` 에 남깁니다.
- 사용자만 정할 수 있는 것(보이는 것, 범위, 되돌리기 어려운 선택)은 am 의 결정 카드 형식으로 한꺼번에 뽑습니다.

분할 결과가 형식 검사(의존 순서, 크기, 완료 조건 유무 등)를 통과하지 못하면 같은 세션에 오류 목록을 주고 두 번까지 고치게 합니다.

계획 단계에서 "한 작업으로는 크다"고 판단하면 계획 대신 `split.json` 을 쓰게 하고, 그 작업을 `T02.1`, `T02.2` 같은 하위 작업으로 바꿔 계속 진행합니다(`maxSplitDepth`, 기본 1단계).

## 설정 (`.orchestrator/config.json`)

적은 값만 기본값을 덮어씁니다. `.orchestrator/` 는 git 에서 제외되므로 PC 마다 따로 둡니다.

| 키 | 기본값 | 뜻 |
|---|---|---|
| `claudeCommand` | `["claude"]` | 실행 파일과 앞에 붙일 인자 |
| `amPluginRoot` | 자동 | am 의 `plugin/` 폴더. gate.mjs 와 SKILL.md 를 여기서 찾음 |
| `pluginDir` | 없음 | 적으면 모든 호출에 `--plugin-dir` 로 넘김 |
| `skillMode` | `auto` | `slash`, `inline`, 또는 doctor 결과에 따름 |
| `branch` | `orch/{run}` | 실행용 브랜치. `""` 이면 현재 브랜치 |
| `parallel` | `3` | 동시에 돌릴 작업 수. `1` 이면 예전처럼 하나씩. 아래 "동시 진행" 참고 |
| `worktreeSetup` | 없음 | 새 작업 공간 안에서 먼저 돌릴 셸 명령. 예: `["npm ci"]`. 환경 변수 `ORCH_MAIN_REPO` 에 원래 저장소 경로 |
| `requireGate` | `true` | `am-gate.json` 이 없으면 시작하지 않음 |
| `orchestratorGate` | `true` | 점검 뒤 게이트를 직접 한 번 더 실행 |
| `maxFixRounds` | `2` | 작업당 수정 → 재점검 횟수 |
| `maxSplitDepth` | `1` | 계획 단계 재분할 깊이 |
| `onBlock` | `stop` | `stop` 은 새 작업을 시작하지 않고 돌던 작업만 끝까지. `stash` 면 막힌 작업의 변경을 stash 하고(별도 작업 공간이면 그대로 두고) 무관한 다음 작업으로 |
| `taskLimits` | 파일 8, 계획 150줄 | 분할·계획 세션에 주는 크기 기준 |
| `requiredGateCommands` | 없음 | `am-gate.json` 의 명령 이름. `"blocking": false` 라 커밋 훅에서는 돌지 않지만 오케스트레이터의 게이트에서는 통과해야 하는 것. 아래 "느린 검사" 참고 |
| `volatilePaths` | 없음 | 빌드 도구가 빌드할 때마다 다시 쓰는 추적 파일(경로나 glob). 아래 "빌드가 다시 쓰는 파일" 참고 |
| `model` | 없음 | 단계별 모델(`split`, `plan`, `implement`, `check`, `commit`, `default`). 예: `{ "default": "sonnet", "implement": "opus" }`. 수정(`fix`)은 `implement`, 결정 답변(`answer`)은 `plan` 의 값을 물려받음 |
| `timeoutMin` | 단계별 | 단계별 제한 시간(분) |
| `permissions` | 단계별 | 단계별 `--permission-mode`, 허용·거부 규칙 |
| `extraArgs` | 없음 | 단계별로 덧붙일 플래그. 예: `{ "commit": ["--effort", "low"] }`. `all` 은 모든 단계에 붙고, `fix`·`answer` 는 `model` 과 같은 방식으로 물려받음 |

단계별 기본 권한: 분할과 계획은 읽기와 `.orchestrator/`·`.am/` 쓰기만(규칙은 저장소 루트 기준이라 세션이 하위 폴더로 `cd` 해도 유효), 구현과 점검은 파일 수정과 셸 명령 허용(커밋·push·reset·checkout·브랜치 전환과 변경을 숨기는 stash 는 거부. `git stash list` 와 `git restore` 는 됨), 커밋은 `git add`·`git commit`·`git restore` 만 허용합니다. 질문 도구는 모든 단계에서 뺍니다.

## 동시 진행

- 함께 돌 수 있는 작업: 먼저 끝나야 하는 작업(`dependsOn`)이 모두 끝났고, 예상 파일(`files`)이 돌고 있는 모든 작업(계획 중 포함)과 겹치지 않는 것. 겹침은 첫 와일드카드 앞의 글자 그대로인 부분을 접두어로 비교합니다(`src/**` 는 `src/` 아래 전부와 겹침, 빈 목록은 모두와 겹침). 겹치는 작업은 앞 작업이 끝난 뒤에 돕니다.
- 계획은 늘 이 저장소에서 합니다(`.am/<slug>/` 에만 씀). 구현을 시작할 때 다른 작업이 돌고 있으면 별도 작업 공간(실행 브랜치의 지금 커밋에서 떨어져 나온 git worktree)을 만들어 구현·점검·커밋을 그 안에서 합니다. 혼자 도는 작업은 지금처럼 이 저장소에서 하고, 그동안은 새 작업을 시작하지 않습니다. 작업 목록이 한 줄로 이어진 구간은 예전과 똑같이 돕니다.
- 작업 공간에는 그 작업과 먼저 끝난 작업의 `.am/<slug>/` 를 베껴 넣고, 끝나면 되돌려 베낍니다(`.am/` 은 git 에서 제외돼 worktree 에 따라오지 않음).
- 합치기: 작업 공간에서 커밋이 끝나면 한 번에 하나씩 실행 브랜치에 합칩니다. 그사이 다른 작업이 먼저 합쳐졌으면 그 위로 rebase 하고 게이트를 다시 돌린 뒤 fast-forward 합니다. 병합 커밋은 생기지 않습니다. 충돌하거나 게이트가 실패하면 변경을 작업 폴더의 `integrate-N.patch` 로 남기고, 실행 브랜치의 새 커밋 위에서 구현부터 한 번 다시 합니다(그 patch 를 세션에 알려 줌). 두 번째도 안 되면 막힘으로 남깁니다.
- `doctor` 는 `parallel` 이 2 이상이면 임시 작업 공간을 만들어 `worktreeSetup` 을 돌리고 게이트를 한 번 돌려 봅니다. 이 저장소에서 통과하던 명령이 모두 통과해야 하고(비차단 명령 포함), 제한 시간은 max(2분, 이 저장소 게이트 시간 × 3) 입니다. 안 되면 경고를 내고 실행은 하나씩 합니다. git 에서 제외된 의존 폴더(`node_modules` 등)가 없어서라면 `worktreeSetup` 에 만드는 명령을 적고 `doctor` 를 다시 돌립니다. `am-gate.json` 이나 `worktreeSetup` 이 바뀌었거나 업데이트 뒤 아직 확인하지 않았으면 `doctor` 를 다시 돌릴 때까지 하나씩 진행하고, `status --json` 의 `parallel.stale` 로 알려 줍니다(스킬은 새 실행마다 `doctor` 부터 합니다). `doctor --skip-gate` 로 확인을 건너뛰어도 하나씩 진행합니다.
- 막히거나 세션 오류(사용량 한도 등)가 나면 새 작업은 시작하지 않고, 돌고 있던 작업은 끝까지 돌린 뒤 멈춥니다. 종료 코드는 지금과 같고(막힘 1, 오류 2), 둘 다면 2 입니다.
- 작업 공간은 일이 끝나는 대로 지웁니다. 막힌 작업과 중단된 작업의 작업 공간은 남겨 두고 다음 `run`·`retry` 가 같은 폴더에서 이어 갑니다(이어 가는 세션은 처음 연 폴더에서만 열림).

알아 둘 점

- rebase 로 옮긴 커밋은 커밋 훅(am 커밋 게이트, 저장소의 pre-commit·계약 검사)을 다시 거치지 않습니다. `am-gate.json` 에 든 것만 다시 확인됩니다.
- 게이트가 고정 포트·공용 DB·라이선스 하나 같은 공용 자원을 쓰면 동시에 도는 게이트끼리 부딪칠 수 있습니다. `doctor` 의 확인은 하나만 돌려 보므로 이것을 잡지 못합니다. 이럴 때는 `parallel: 1`.
- 작업 공간은 저장소 안(`.orchestrator/wt/`)에 있습니다. 루트에서 `.gitignore` 를 무시하고 하위 폴더를 훑는 도구는 남은 작업 공간을 볼 수 있고, 작업 공간의 세션은 상위 폴더인 이 저장소의 CLAUDE.md 도 함께 읽습니다.
- `.claude/settings.local.json` 처럼 git 에서 제외된 설정·플러그인 활성화는 작업 공간에 따라오지 않습니다. am 을 그렇게만 켰다면 `pluginDir` 를 적으세요.

## 느린 검사 (커밋 훅에 넣기에는 오래 걸리는 테스트)

am 의 게이트는 `"blocking": false` 명령을 커밋 훅에서는 돌리지 않고 `am:check` 와 `gate.mjs --run` 에서만 돌리며, 실패해도 게이트는 통과로 봅니다. 그래서 느린 테스트를 비차단으로 넣어 두면 점검 세션이 결과를 챙겨 볼 때만 걸러집니다.

무인 실행에서는 그 테스트도 매번 통과를 확인해야 하므로, `requiredGateCommands` 에 이름을 적으면 오케스트레이터가 직접 돌리는 게이트에서 그 명령의 실패를 게이트 실패로 봅니다(구현 세션이 고치고 다시 점검). 커밋 훅의 시간 예산에는 영향이 없습니다.

```json
// am-gate.json (저장소)
{ "commands": [
  { "name": "test", "run": "make test" },
  { "name": "unity-editmode", "run": "<Unity EditMode 테스트 명령>", "blocking": false }
] }

// .orchestrator/config.json
{ "requiredGateCommands": ["unity-editmode"] }
```

이렇게 하지 않으면 그 코드의 검증은 점검 세션이 테스트를 직접 돌리느냐에 달려 있습니다. 점검 세션에는 "기록을 읽지 말고 직접 돌려서 확인하라"고 지시하지만, 지시는 강제가 아닙니다.

## 빌드가 다시 쓰는 파일

빌드나 에디터 실행이 추적 중인 파일을 다시 쓰는 프로젝트가 있습니다(Unity 가 플레이어를 빌드하면서 URP 설정의 값을 고쳐 쓰는 경우 등). 작업마다 "커밋 뒤 작업 트리가 깨끗해야 한다"는 규칙에 걸리지 않도록 이렇게 다룹니다.

| 누가 다시 썼나 | 처리 | 설정 |
|---|---|---|
| 오케스트레이터가 직접 돌린 게이트 | 게이트 직전 상태로 되돌림. 이때는 다른 것이 돌지 않으므로 게이트가 한 일이 확실함 | 필요 없음 |
| 커밋 훅의 게이트 | 커밋 직전의 내용이 그대로 커밋됐는데도 바뀌어 있는 파일은 되돌림. 커밋 세션은 파일을 고칠 수 없으므로 게이트가 한 일임 | 필요 없음 |
| 세션 안의 빌드(구현 세션의 빌드, am:check 의 게이트) | 그 세션이 끝내기 전에 `git restore` 로 되돌리게 지시함. 되돌리지 않고 남기면 작업의 수정과 구분할 수 없어 작업의 커밋에 함께 들어감 | `volatilePaths` 에 적으면 아래 방식으로 가려냄 |

구현·점검 세션은 `git checkout` 과 `git stash` 가 막혀 있으므로, 빌드 부작용을 되돌릴 때 쓸 명령(`git restore -- <경로>`)을 지시문에 적어 줍니다.

`volatilePaths` 에 적은 파일이 바뀌어 있으면, 그 파일을 HEAD 로 되돌린 채 게이트를 돌려 봅니다. 게이트가 똑같은 내용을 다시 만들어 내면 빌드 산출 변화이므로 버리고, 다르면 작업이 실제로 고친 것으로 보고 원래 내용을 되살려 커밋합니다(보고서의 "참고"에 적힘). 원래 돌리던 게이트 한 번으로 하므로 세션이나 빌드가 늘지 않습니다. `orchestratorGate` 가 켜져 있어야 합니다. 게이트가 그 파일을 다시 쓰는 빌드를 돌리지 않으면(예: 게이트에 Unity 실행이 없음) 같은 내용이 만들어지지 않으므로 이 판별은 항상 "작업의 변경"으로 끝납니다. 이때는 세션의 `git restore` 에 기대게 됩니다.

- 커밋 세션은 check.md 나 계획의 Change log 가 "빌드 산출물이니 커밋에서 빼라"고 적은 파일을 커밋하지 않고 `git restore` 로 되돌립니다. 되돌린 파일은 보고서의 "참고"와 아래 목록에 남습니다. 두 문서 어디에도 그런 말이 없는 변경은 작업의 변경으로 보고 커밋합니다.
- 버린 변경은 작업 폴더의 `restored-N.patch` 에 남고, 보고서의 "빌드 도구가 다시 써서 되돌린 파일"에 횟수와 함께 모입니다.
- `doctor` 는 깨끗한 작업 트리에서 게이트를 돌린 뒤 바뀐 추적 파일을 알려 줍니다(되돌려 둠).
- "게이트 직전 상태"와 "커밋 직전 상태"는 임시 인덱스로 만든 스냅샷으로 비교합니다. 점검 세션이 `git add -N` 을 해 둔 상태에서도 동작합니다.
- 작업을 시작할 때와 `done` 에서는 `volatilePaths` 파일의 변경을 그대로 되돌립니다(지난 빌드의 흔적으로 봄).
- 게이트가 만든 추적되지 않는 파일(빌드 산출물)은 다루지 않습니다. `.gitignore` 에 넣어야 합니다.

## 저장소의 커밋 규칙 (pre-commit 훅, 계약 문서)

코드를 바꾸면 다른 파일도 함께 바꿔야 커밋이 되는 저장소가 있습니다(모듈 계약 문서의 이력 줄, 변경 기록, 밀린 줄 번호 인용 등). 커밋 세션은 `git add`·`git commit` 만 할 수 있어 이런 것을 직접 고치지 못하므로, 세 군데에서 챙깁니다.

- 분할과 계획: 저장소의 커밋 규칙(pre-commit 훅, CLAUDE.md, 계약 문서)을 찾아, 함께 바꿔야 하는 파일을 작업의 `files`·완료 조건과 계획의 단계에 넣게 합니다. `files` 는 힌트라서 목록에 없어도 계획 단계가 챙깁니다.
- 점검: 커밋 훅이 거부할 상태는 BLOCK 으로 판정하게 합니다.
- 커밋: 그래도 훅이 커밋을 거부하면, 훅이 출력한 내용을 `commit-rejected-N.md` 에 남기고 구현 세션을 이어 고치게 한 뒤 점검부터 다시 합니다. 횟수는 `maxFixRounds` 를 점검 수정과 함께 씁니다.

계약 검사를 커밋 없이 돌릴 수 있다면 `am-gate.json` 에 넣어 두는 편이 가장 확실합니다. 그러면 커밋 전에 게이트가 결정론적으로 잡습니다.

## 무인 실행에 맞춰 am 과 다르게 한 점

am 스킬 본문은 그대로 쓰고, 세션마다 덧붙이는 지시문으로 아래만 바꿉니다.

- 계획: 이 세션이 쓸 수 있는 곳은 `.am/<slug>/` 뿐이고 Write·Edit 도구만 된다는 것을 미리 알려 줍니다. 계획을 파일로 남기지 못하면 같은 세션에 저장을 한 번 다시 시키고, 그래도 없으면 "결정 필요"가 아니라 막힘으로 남깁니다(세션의 답변은 `plan-reply.md` 에 보관). 작은 변경이어도 "직접 할까요"에서 멈추지 않고 항상 plan.md 를 씁니다.
- 묻는 자리(계획과 구현 공통): am 0.1.7 의 `am:auto` 와 같은 규칙을 씁니다. 화면·범위 질문은 추천안으로 정해 계획 문서의 결정 절에 "(자동 결정)" 표시와 이유를 남기고 계속합니다. 기술 선택은 스킬이 정한 대로(2차 의견) 정합니다. 멈추는 것은 이번 실행 전부터 있던 데이터·파일 삭제, 저장 형식 변경·데이터 이전, 저장소 밖 변경, 사용자·프로젝트 지침이 확인을 요구하는 일뿐입니다. "(자동 결정)" 줄은 보고서의 "사용자 대신 정한 것"에 모입니다. 분할 단계에서 미리 뽑아 사용자가 답한 결정은 그대로 최우선입니다.
- 구현: `am:do` 의 단계를 따르되 마지막의 "am:check 로 넘어가기"만 하지 않습니다(점검과 커밋은 별도 세션). 완료 표시와 파일이 어긋나면 묻지 않고 `am:auto` 처럼 처리합니다(빠진 변경은 다시 하고, 이미 된 단계는 확인을 돌려 표시).
- 점검: 질문하지 않고, 사람만 확인할 수 있는 것은 check.md 의 체크리스트로 넘깁니다.
- 커밋: 작업 시작 때 작업 트리가 깨끗했으므로 남은 변경 전부를 이 작업의 것으로 봅니다(검증 중 빌드가 다시 쓴 설정 파일 포함). 일부러 남기는 파일이 있으면 이유를 답변에 적게 합니다. 허용된 명령이 `git add ...`, `git commit ...` 뿐이라, 저장소 루트에서 하나씩 단독으로 실행하게 합니다(`git -C`, 파이프, `&&` 묶음, heredoc 금지). 커밋 명령이 권한 규칙에 걸려 커밋이 안 되면 같은 세션에 한 번 다시 시키고, 게이트 실패일 때만 멈춥니다.
- 각 세션은 답변 끝에 `ORCH_STATUS: ...` 또는 `ORCH_VERDICT: ...` 한 줄을 붙입니다. 없으면 같은 세션에 한 번 되묻고, 점검은 그래도 없으면 check.md 의 판정 줄을 읽습니다.

## 확인한 것과 확인하지 못한 것

확인한 것

- am 0.1.7 의 스킬 5개(plan, do, check, commit, auto) 본문과 `agents/second-opinion.md`, `hooks/gate.mjs` 를 읽고 그 인터페이스(`/am:plan`, `/am:do <slug>`, `.am/<slug>/plan.md`·`check.md`, `gate.mjs --run --json --cwd`)에 맞췄습니다. `tests/orchestrator-skill.test.mjs` 가 이 접점을 지킵니다. `am:do` 가 없는 0.1.3 이하에서는 구현을 예전처럼 `/am:plan <slug>` 로 부릅니다.
- `am:auto` 는 한 세션에서 네 단계를 잇는 명령이라 오케스트레이터가 부르지 않습니다. 오케스트레이터는 단계마다 세션을 따로 띄워 권한을 달리 주고, 단계 사이에 게이트와 작업 트리를 직접 확인합니다.
- Claude Code 2.1.289 로 확인한 것: `claude plugin validate` 가 마켓플레이스와 두 플러그인을 통과시킵니다. 세션 시작 정보에 `am-orchestrator:run` 과 am 의 스킬이 실려 옵니다. 오케스트레이터가 단계별로 만드는 명령줄(권한 규칙, `--append-system-prompt-file`, `--plugin-dir`, `--resume`)을 CLI 가 받아들입니다. 로그인하지 않은 환경이라 모델 호출 직전까지만 봤습니다.
- 가짜 `claude` 로 흐름 전체를 테스트했습니다(`node --test tests/orchestrator.test.mjs`). 게이트와 스킬 파일은 이 저장소의 `plugin/` 것을 그대로 씁니다.
- 스킬 없이 스크립트만 쓴 이전 판으로 실제 저장소에서 두 번 실행했습니다(작업 28개, 48개). 그때 드러난 문제를 고친 것이 지금 판입니다.

확인하지 못한 것

- `am-orchestrator:run` 스킬을 실제 세션에서 돌려 보지 못했습니다. 세션이 지시대로 백그라운드 실행을 기다리고 `status --json` 을 따라가는지는 작은 설계 문서로 먼저 확인해야 합니다.
- 마지막 두 번의 실제 실행 뒤에 넣은 변경(구현을 `am:do` 로 호출, 커밋 훅 거부 시 자동 수정, 빌드 산출물 되돌리기, `(자동 결정)` 규칙, 잠금)은 실제 모델 호출로 돌려 보지 못했습니다.
- Windows 에서 실행해 보지 못했습니다. `claude` 가 `.exe` 면 직접, `.cmd` 면 cmd.exe 를 거쳐 실행하도록 했고 따옴표 처리만 단위 테스트했습니다.
- 권한 규칙에 걸린 명령은 실행 로그에 "권한 거부 N건"으로 찍히고, 어떤 명령이었는지는 보고서의 "참고"와 `NN-<단계>.out.json` 의 `permission_denials` 에 남습니다. 규칙이 부족하면 여기서 드러납니다.

알아 둘 점

- 동시 진행은 가짜 `claude` 로만 확인했습니다(두 작업이 실제로 겹쳐 도는지, 합칠 때 옮기기·충돌·막힘·중단). 실제 모델 호출로는 돌려 보지 못했습니다.
- Unity 는 worktree 마다 `Library` 와 `.csproj` 가 없어 예시 게이트가 "파일 없음"으로 실패합니다. `doctor` 의 확인에서 걸려 하나씩 진행하게 됩니다. Unreal 처럼 작업 공간마다 처음부터 빌드하느라 오래 걸리는 프로젝트도 확인의 제한 시간에 걸리면 하나씩 진행합니다.
- `--bare` 는 앞으로 `-p` 의 기본값이 될 예정이라고 문서에 적혀 있습니다. 그렇게 되면 설치된 플러그인이 자동으로 실리지 않으므로 `pluginDir` 를 적어야 합니다. `doctor` 가 플러그인이 안 보이면 알려 줍니다.
- Unity: 빌드가 URP 설정 파일 등을 다시 쓰면 위 "빌드가 다시 쓰는 파일"대로 처리됩니다. 실제 Unity 프로젝트에서는 확인하지 못했습니다.
- Unity: 예시 게이트(`gate-build.cmd`)는 Windows 전용이고, `.csproj` 에 아직 없는 새 `.cs` 파일은 컴파일하지 않습니다. 무인 실행에서 새 파일을 추가한 작업은 게이트를 통과해도 컴파일이 확인된 것이 아니므로, 보고서의 사람 확인 체크리스트(에디터 재컴파일)를 꼭 봐야 합니다.
