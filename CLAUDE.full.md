# am plugin repository

Lightweight plan/do/check/commit workflow plugin for Claude Code and Codex CLI. The repository root is the marketplace (`.claude-plugin/marketplace.json`) and lists five plugins, each installed into users' caches on its own: `plugin/` is `am` (the skills plan, do, check and commit, the commit gate, the second opinion), `auto/` is `am-auto` (Claude Code only, `dependencies: ["am"]`: the unattended skills multi, one and agent, the sessions report, the stage agents, the stage runner and its hooks), `util/` is `am-util` (the land and update-branch skills), `art/` is `am-art` (Claude Code and Codex, no dependencies: Claude Code sees the art skills ad-review, pipe-apply, log-compare, log-resume and git-sync, Codex only ad-execute), and `orchestrator/` is `am-orchestrator` (Claude Code only), which runs the am skills task by task over a whole design document.

## Rules
- One source for both tools. Codex reads `.claude-plugin/` manifests and plugin hooks natively; do not add Codex-only copies. One exception (user decision): `art/.codex-plugin/plugin.json` (same `name`, `version` and `description` as `art/.claude-plugin/plugin.json`, plus `"skills": "./codex-skills/"`) shows Codex only `art/codex-skills/`, and `art/.claude-plugin/plugin.json` names `"skills": "./claude-skills/"`; `art/` has no default `skills/` folder because both tools add a manifest's `skills` path to it rather than replace it; no other folder has a `.codex-plugin/` (`tests/skills.test.mjs`).
- `hooks/hooks.json` handler keys: `type`, `command`, `timeout` only. No `args`, `if` or `commandWindows` (one of the two tools ignores or rejects them). The command must not rely on shell path expansion: Codex runs it with `cmd /C` on Windows.
- `plugin.json` must not list `hooks` or `skills`; the default folders are loaded and listing them registers twice in Claude Code (exception: am-art's two manifests name their non-default skill folders, see above). Do not list `agents` either; the default `agents/` folder is scanned.
- Hook output contract (measured on Claude Code 2.1 and Codex 0.160): always exit 0; stdout is empty or exactly one JSON object; block with `hookSpecificOutput.permissionDecision: "deny"` plus a non-empty reason. Codex ignored exit 2.
- Changing `hooks.json` makes every Codex user re-trust the hook. Avoid it: am's `plugin/hooks/hooks.json` is frozen byte for byte (its SHA-256 is pinned in `tests/gate.test.mjs`, the old skill name in its description included), and `plugin/hooks/hook.mjs` ends with no output and loads nothing for input whose `agent_type` starts with `am-auto:stage-`.
- Stage guard: am-auto's own `auto/hooks/hooks.json` (three groups: Bash|PowerShell with a 900-second timeout, Write|Edit|MultiEdit|NotebookEdit, SubagentStop; its command string differs from am's) calls `auto/hooks/stage-hook.mjs`, which sends only input whose `agent_type` starts with `am-auto:stage-` to `auto/hooks/stage-guard.mjs` and then sends an allowed shell command through the gate copy `auto/hooks/gate.mjs` (its deny wins); the guard allows what the stage's allow list holds and denies the rest, binds and touches the task's `.am/<slug>/stage.json` (which also records the `core` am folder) as a heartbeat on every tool call, and on SubagentStop prints `{"decision":"block"}` once when the final answer is not the one status line. Changing `otherRuns`, `leaseOf` or the `stage.json` format means changing `agent-stage.mjs`, `stage-guard.mjs` and `tests/agent-stage.test.mjs` in the same commit.
- Shared copies: each plugin is installed on its own, so `auto/` and `util/` ship copies of am files (`COPIES` of `scripts/sync-shared.mjs`: the gate, `user-models.mjs`, `user-settings.mjs`, `codex-opinion.mjs`, `second-opinion.md`). Edit only the `plugin/` source and run `node scripts/sync-shared.mjs` (`--check` only lists drift; `node scripts/models.mjs` runs it at its end).
- Core lookup: am-auto finds the am folder with `findCore` of `auto/hooks/handover.mjs` (the development sibling `plugin/`, else the one enabled am of `claude plugin list --json`, else, when the list fails, the newest am in the cache folder beside am-auto); `node auto/scripts/stage.mjs core` prints it, and stage sessions get `--plugin-dir` only for a core outside the plugin cache (`pluginDirFor`, a development copy). am-auto relies on the core folder for the four skill files (path, frontmatter, body), am:do's done mark, the plan skeleton's `## Change log`, `scripts/codex-opinion.mjs` and plugin.json's `name` and `version`: an am change to any of them changes am-auto in the same commit and raises `AM_MIN_VERSION` of `handover.mjs` to that am version (never above it; `tests/handover.test.mjs`).
- Skills: English bodies; frontmatter `description` and `argument-hint` in Korean (users see them in the command palette); README/CHANGELOG in Korean. The common rules block is edited only in its source `shared/common.md` and written into every SKILL.md by `node scripts/skills.mjs` (`--check` only lists drift; `tests/skills.test.mjs` runs that check); block names, markers and targets are `BLOCKS` of `scripts/skills.mjs`. Size limits plan/check 120 lines, commit/do/multi/one/agent/land/update-branch/sessions 80 (tests enforce both); each skill lives in its plugin's `skills/` folder (`plugin/`, `auto/`, `util/` or `art/`, `SKILL_HOME` of `tests/skills.test.mjs`; am-art's in `art/claude-skills/` and ad-execute in `art/codex-skills/`, `SKILL_SUB`), and `tests/skills.test.mjs` fails on the skill names before 0.1.67 and the old `plugin/` paths in the plugin folders, `scripts/`, `shared/`, the orchestrator's skill and script, both READMEs and this file. Refer to other skills as "the am:check skill", not `/am:check`. `auto/flow/` holds the shared flow the three run skills read while they run; it is not a skill (outside `skills/`, no SKILL.md or frontmatter, each file at most 80 lines, `tests/skills.test.mjs`): `run.md` ("Running without stops" and Steps 1-7, all three), `stage-sessions.md` (am-auto:multi and am-auto:one) and `parts.md` (am-auto:one and am-auto:agent). am-auto:multi's `## Hand-over (am-orchestrator)` section adds to run.md's step 2, 4 and 7 (and `HANDED`), the `- Loop step N:` lines of the `## Parts` sections of am-auto:one and am-auto:agent add to the parts.md loop, and am-auto:agent uses its own `## Stage agents (Claude Code)` instead of stage-sessions.md; changing a flow file's headings, step numbers or step 4's first sentence means changing the skills and tests that point at them in the same commit. The Parts lines (the `## Parts` section, `PART_LINE` of `auto/scripts/stage.mjs`) and the `- Part <k> done: <slug>-p<k>` Change log line change only together: am-auto:one, am-auto:agent (its own fixed `- Part <k> done:` command), `auto/flow/parts.md` (the Parts rules and loop both read), `agent-stage.mjs --part` (`partOwner`), `stage.mjs` (its plan-stage Parts rule, `COUNTED` and the compaction keep list), `tests/skills.test.mjs` and `tests/stage.test.mjs` in the same commit.
- Second opinion: `plugin/agents/second-opinion.md` is the one reviewer subagent, and Claude Code only (Codex has no such subagent, so the common rules fall back to the session's own pick). Its frontmatter pins `model` and `effort` (values from `models.json`, see below); the only override is the user models file's `second-opinion` key, which `codex-opinion.mjs` reports as its first output line `Claude reviewer: …` and the common rules pass as the Agent call's `model`/`effort` (aliases in `OPINION_MODELS` only). Both opinion keys skip the file's `default`. The frontmatter keeps the tools read-only. Write the model as an alias (`opus`): it follows the main session's Opus version, so a new Opus is used without an edit. Claude Code ignores a misspelled frontmatter key without an error, so the tests check the exact keys and values. English body, Korean `description`; am-auto and am-util ship it as the copy `scripts/second-opinion.md` read by their `codex-opinion.mjs` copies. The only other agents are the five am-auto:agent stage agents `auto/agents/stage-*.md` (called `am-auto:stage-*`) (tools Read, Grep, Glob, Write, Edit, Bash, plus Agent for stage-check; model and effort from models.json's plan/do/check/commit through `STAGE_AGENTS` of `scripts/models.mjs`; exact frontmatter and the shared body pinned in `tests/skills.test.mjs`).
- Codex second opinion: when Codex is installed, the common rules also run `plugin/scripts/codex-opinion.mjs <brief>` (Claude Code only) and debate a split with the subagent (at most 2 more rounds, then the user decides). When Codex is not installed (exit code 2), the common rules send the brief to two subagents at once, labelled Claude 1 and Claude 2, and debate a split between them the same way; their agreement mark is `(second opinion, Claude reviewers agreed)`. The am-auto:agent plan stage has no Agent tool, so its rules (`agentRules`, plan stage only) run `auto/scripts/claude-opinion.mjs <brief> [--as 1|2]` instead of the subagent: a read-only `claude -p` session with fixed flags (Read, Grep and Glob, no MCP servers, no skills) on the user models file's `second-opinion` key, else the subagent's frontmatter, that prints the answer under `Claude's answer:`; `--as 2` also asks Claude 2 to argue against its first leaning before it picks (user decision). Orchestrator plan sessions may run that script and nothing else, so its `codex exec` flags stay constants except the model and effort of the user models file's `codex-opinion` key, unquoted tokens checked against `CODEX_MODEL` and `CODEX_EFFORTS` (Codex runs through `cmd /C` and reads `-c` values as TOML), it sends only a `.md` brief under `.am/`, and it takes no other argument; tests set the timeout and PATH through function parameters, never environment variables, and point `CLAUDE_CONFIG_DIR` at a temporary folder. `second-opinion.md` is the instruction text for both reviewers.
- Model and effort: every SKILL.md sets `model` and `effort` in its frontmatter (Claude Code only; Codex ignores both keys), and the tests check the exact keys and values. They hold only for the turn that invokes the skill. Write the model as an alias (`opus`), not a full ID, as for the second opinion: a skill whose model cannot be resolved has no fallback, unlike the subagent.
- One source for model and effort: `models.json` at the repository root holds the values of every skill (am, am-auto, am-util and am-orchestrator), the second-opinion subagent, the am-auto:agent stage agents, the Codex second opinion (an empty model leaves the user's codex config in charge), the stage runner's compaction session and the orchestrator's split stage. Change values only there, then run `node scripts/models.mjs`: it rewrites the frontmatter, `STAGE_DEFAULTS`, `CODEX_ARGS`, `COMPACT_MODEL`, `BUILTIN_MODELS` and the tables between `<!-- am:models:start -->` and `<!-- am:models:end -->` in both READMEs (`--check` only lists drift). No plugin reads `models.json` at runtime, and the docs point at those tables instead of repeating values. Each target must match exactly once, so a changed file format stops the script; fix its target in `scripts/models.mjs`.
- User files: `plugin/scripts/user-files.mjs` creates the two user files (models, settings) only when one is missing, with the defaults as `_` note keys (and `minFreeMemoryMB: null`), atomically (a temp file in the same folder plus a hard link; a direct `wx` write only on a file system without hard links); it never touches an existing file and does nothing when the config folder is missing. Its `BUILTIN_MODELS` is a `scripts/models.mjs` target. When the format or keys of the user models or settings file change, change the templates in the same commit. `plugin/hooks/hook.mjs` calls it before every gate decision (a dynamic import inside its own try/catch, so a load or creation failure is swallowed and never changes the gate or the hook output), so the files appear on the first shell command after install or update without changing `hooks.json`.
- Hand-over hook: am-auto:multi's frontmatter declares a one-line PreToolUse hook (`auto/hooks/handover.mjs`, Claude Code only, active for the rest of a session that invoked am-auto:multi). It denies file edits outside `.am/`, `.orchestrator/` and `am-gate.json` while the session's plan is above 1 implementation run (the commit count plays no part), am-orchestrator is installed, and no step is done or hand-over logged. It reads am-auto:multi's Scale line, am:do's done mark and the fixed `Hand-over:` line in the plan's Change log (older wording still read), so changing any of them means changing `handover.mjs` and `tests/handover.test.mjs` in the same commit. Shell commands are not checked (user decision).
- Stage sessions: in Claude Code, am-auto:multi runs each phase in a fresh `claude -p` session through `auto/scripts/stage.mjs` (one stage per call, not a batch runner); Codex, and a PC where no session can start (`unavailable`), keep the single-session flow. The script fixes each stage's permissions (the commit stage may only unstage with `git restore --staged -- <paths>`, so no `--worktree` can slip in, and that one rule is Bash only, with no PowerShell copy; a hand-over may `git switch` only to its start branch, never `git checkout`, from the `Hand-over:` line by `handedStartBranch` of `handover.mjs`, else the branch checked out at its start, and may `git stash push`, `show` and `apply` but never drop: it logs `- Stash: <oid>, base <commit>` and after the merge applies that stash only when it shares no file with the run's changes, the same rule as am-auto:multi step 4), calls the stage's am skill by slash command and passes no `--model`/`--effort` (the skill's frontmatter applies), unless the user models file gives the stage a value different from that frontmatter: then the skill body without frontmatter is written to `.am/<slug>/skill-<kind>.md` and called inline with both flags, also on the second ask; the hand-over does the same with the run skill (key `run`, defaults from `<orchRoot>/skills/run/SKILL.md`); it reads an `AM_STAGE:` end line. The plan, do, check and commit sessions and the compaction session get `FORCE_PROMPT_CACHING_5M=1` in their environment (`CACHE_5M_KINDS`); only the hand-over keeps the 1-hour cache because it waits on orchestrator workers. Every orchestrator session (`runClaude`) gets it too. The plan session may run the Codex second-opinion script of the runner's am and of every enabled installed am found by `findAm` of `handover.mjs` (not looked up for a `--plugin-dir` copy); a different folder is a `note`. The stage sessions' unattended rules are an English copy of "Running without stops" in `auto/flow/run.md` written for one stage (user decision); change them together, `tests/stage.test.mjs` pins the auto-decided mark and the stop list in both. The do stage becomes a hand-over to the run skill by `readPlan` and `findOrchestrator` of `handover.mjs`, and follows am-auto:multi step 4's additions (run ID line, merge, push). Every status the script prints must be handled in am-auto:multi (`tests/skills.test.mjs`); what the hand-over relies on in `orchestrator/` is pinned in `tests/orchestrator-skill.test.mjs`. Tests pass the claude command, time limits and the orchestrator lookup as function parameters. Before writing its `start` line, a stage takes the start lock `.am/.admission.lock` and waits (a `note` with `stage: 'wait'`, then status `WAIT` that am-auto:multi answers by running the stage again) while another unattended run of this working tree goes on (`otherRuns`: another task's live stage or its gap between stages, a live orchestrator lock, or the gap after its split or answer, read from `lock.json`'s `pid` and `leaseMs` and those end statuses, pinned in `tests/orchestrator-skill.test.mjs`); a task whose `stage-worker.json` went untouched for `WORKER_STALE_MS`, or a lock with `leaseMs` untouched that long, no longer blocks once the stage has waited `RECORD_SETTLE_MS` (counted again after a wake from sleep), so a dead run whose pid was reused cannot block for good, while a lock without `leaseMs` (an older orchestrator) keeps the pid rule; every wait value is a function parameter of `main`. A live stage goes stale only by the record whose `pid` is its `start` pid (`leaseOf`: `stage-worker.json`, or am-auto:agent's `.am/<slug>/stage.json`, written by `auto/scripts/agent-stage.mjs` and stale after `AGENT_STALE_MS`, 20 minutes), else by the pid alone; `agentRules` is the subagent copy of the same unattended rules (exact swaps that throw unless each matches once: no session wording, the report in `.am/<slug>/reply-<stage>.md`, the runId in the status line), pinned together with them in `tests/stage.test.mjs`. A stage reads the per-PC settings file with `user-settings.mjs` (broken: `failed` with no session), and a stage that is not a hand-over, inside the start lock, first writes a `.gate` record in the orchestrator's record folder with `memory-guard.mjs`, then checks the free memory (short: it waits, up to `WAIT`) and holds the record until `finish`; it relies on the orchestrator's record name pattern and folder, pinned in `tests/orchestrator-skill.test.mjs`, so changing them means changing `memory-guard.mjs` and `stage.mjs` in the same commit, and `freeMem`, `platform` and `heartbeatMs` are function parameters of `main` too. Before a stage, task files above about 13,000 estimated tokens are shortened in a separate compaction session (it always gets `--model`/`--effort`: the user models file's `compact`, else `default` value (`plugin/scripts/user-models.mjs`), else `COMPACT_MODEL`), checked mechanically and put back on any failure; a record `.am/<slug>/compact-pending.json` (`COMPACT_PENDING`, the texts to put back) is written before that session and removed once its outcome is settled, a stop puts the files back after killing the session (POSIX; on Windows the kill runs on its own), and the next stage of the task puts back whatever a leftover record names before anything else (`recoverCompaction`); its markers are `COMPACT_MARKS`, not `MARKS`, because they never reach am-auto:multi as a status (am-auto:multi only reports the result's `compacted` field). `request.md` is never counted or shortened (user decision): the compaction session gets a deny rule for that file, and the script puts it back and undoes the compaction when it was changed. Nothing is shortened before the plan stage or a hand-over (user decision): a `plan.md` shortened before a plan stage that runs again would reach the orchestrator short, with no notice of its original. Worker and follower: `stage.mjs` without the hidden `--worker` starts the stage as a detached worker and follows it; the follower writes no event (the `start` pid and `end` are the worker's), refreshes `.am/<slug>/stage-heartbeat` every poll, passes stop signals on, and prints the worker's result line, claimed by a `stage-delivered-<pid>` mark (`wx`). The worker holds `stage-worker.json` (pid, stage, push, fix, start time `t`; one per task, touched every `WORKER_TICK_MS`, only suspect after `WORKER_STALE_MS`), logs to `stage-worker.log`, writes `stage-result.json` once (the line plus plan.md/check.md size and change time) and stops `failed` (delivered) when the heartbeat stays unchanged for `WORKER_IDLE_MS` (30 minutes). Before the start lock, a live worker of the same stage and flags is followed; one of another stage is waited for up to `WAIT_MS`, then `WAIT` naming it. After `FOLLOW_LIMIT_MS` (equal to progress's `maxLifeMs`, pinned in `tests/stage.test.mjs`) the call ends `WAIT` with `stillRunning` (`the <stage> stage is still running (started HH:MM)`, the record's `t`, the same for the whole run) and the worker keeps running. A result nobody took goes once to the next call of the same stage and flags while plan.md and check.md are unchanged; otherwise, or for another stage, it is dropped. The hand-over session gets `AM_HANDOVER_OWNER` (the stage worker's pid), which the orchestrator worker writes as `worker.json`'s `owner`; however the hand-over worker ends, it sends SIGTERM only to an orchestrator worker whose `owner` is its pid, whose pid is alive and equals `lock.json`'s `pid` (pinned in `tests/orchestrator-skill.test.mjs`; see "Worker and follower" under Orchestrator). The worker files are never task files to read or shorten; every wait of `worker` and `follow` is a function parameter. After every session's `close` (also after its timeout), `exec` stops what it left behind with a `proc-tree.mjs` tracker within `CLEANUP_MS` (a hand-over first stops its orchestrator worker with `stopHandedRun` and leaves that pid and its descendants out); only when something was stopped it writes a `note` (`cleanedNote`) and a worker log line, and a failed cleanup never changes the result. Every session gets `DISABLE_AUTOUPDATER=1` (`sessionEnv`); the tracker (`track`) and the log are function parameters of `main`. Unless the user settings file's `stageMcpServers` is true, every session gets `--strict-mcp-config --mcp-config .am/<slug>/stage-mcp.json` (an empty server list, rewritten right before each session because sessions may write under `.am/`; a path because cmd.exe cannot pass `"`). Solo mode (am-auto:one): `--solo` marks a task that owns one shared session and `--solo=<owner>` a part of the task `<owner>`; the owner goes into the worker record and the result file and is compared like `--push`/`--fix`; a solo session gets the unattended rules with am-auto:one named and the stage continuing in the same session, its owner plan stage the Parts rule and a part plan the one-part rule; `do --solo` (`doKind` with `solo`) never looks up the orchestrator, and a plan not yet started that was handed over, has no Scale line or is above 1 implementation run ends `failed` with what to do. A solo stage `--resume`s the session named in `.am/<owner>/solo-session.json` (`SOLO_SESSION`: `sessionId`, `slug`, `stage`, `model`, `status`, `t`, rewritten after each stage; `model` is the model the stage ran on, the user models file's value else the skill's frontmatter alias), unless the record is a `NEEDS_DECISION` end of the same stage of the same slug (resumed at once, no model comparison or measurement); a `BLOCKED` or `failed` end of the same stage of the same slug starts the stage in a new session instead, with no call before it, a note and `solo.fresh` `the last <stage> stage ended <status>`; otherwise, when the record's `model` differs from this stage's model (string comparison) or either is unknown (an older record without the field), the stage starts in a new session with no call before it (`solo.fresh` `model change (<a> -> <b>)`, user decision); on the same model a separate `/context` call (`SOLO_CONTEXT_PROMPT` on the stage's model, no tool, `limits.compact`) reads the share of the context window in use (`contextShare`: used ÷ total tokens, the rounded percent ignored), and below `SOLO_CONTEXT_LIMIT` (20 percent, a code constant; user decision) the stage resumes the session ID it returned; unreadable, the stage starts in a new session (`solo.fresh` `context use could not be read (…)`, that call's reported cost added); at or above it a `/compact` call (`SOLO_COMPACT_PROMPT`, same model, no tool, `limits.compact`; user decision) compacts that session, its ID is recorded at once and `/context` measures again: below the limit the stage resumes it, otherwise a new session (`solo.fresh` `compaction failed (…)`, `context use after compaction could not be read (…)` or `context P of the window after compaction`, the dropped conversation's last reported cost added); the result's `solo` keys stay as they are (compaction shows only in progress notes); no clear file between stages; with no record, an unreadable one or a resumed call that ends with an error other than a time-out it runs once in a new session (user decision; after a failed resumed call, the dropped conversation's last reported cost added), writes a note and reports why in the result's `solo.fresh` (`solo`: `owner`, `sessionId`, `fresh`, `context`); every solo stage is told to rewrite `.am/<owner>/solo-context.md` (`SOLO_CONTEXT`, the shared session's memory) before its final reply, and a stage that starts in a new session while that file exists gets its rules file rewritten with a line to read it first, a note, and `solo.context` true; in `otherRuns` (its `owner` option) a part skips its owner's gap between stages, waits for the owner only while an owner stage runs, and waits for other tasks with the owner's place in line when that is earlier.
- Progress news: stage sessions append events to `.am/<slug>/progress.jsonl` (append-only, one JSON object per line: required `t`, `ev`, `text`; optional `pid` (on `start` only), `stage`, `task`, `status`, `min`, `src`; `ev` is `start`, `step`, `note`, `alert` or `end`). `stage.mjs` writes them and, during a hand-over, copies the run's lines with `src: "run"`; an error while writing is swallowed. `auto/scripts/agent-stage.mjs` writes the same line format for am-auto:agent stages (`start`, `note`, `end`). The progress command `auto/scripts/progress.mjs <slug> [--consumer <name>]` prints the lines its consumer has not seen plus one state line (`state: running (…)` or `state: ended`) and always ends by itself (exit code 0, or 1 for bad arguments; under the 10-minute limit of a background command). Each consumer has its own cursor file: am-auto:multi calls it with `--consumer main`, a person with no option (`terminal`). am-auto:multi reads that command string (in `auto/flow/stage-sessions.md`) and `state: ended`, so changing either means changing the skill and `tests/skills.test.mjs` in the same commit. The line format and the output must equal the orchestrator's `progress` command (`tests/orchestrator-skill.test.mjs` compares them on the same input). The state line counts done steps with `countDone` of `handover.mjs`, one more reader of am:do's done mark: changing the mark also means changing it and `tests/progress.test.mjs`. In plan and do stages `stage.mjs` writes a `step` (`second opinion: <line>`) for each new `(second opinion` line of plan.md (lines there after compaction are the in-memory baseline, read every `opinionMs`, a function parameter, and a last time in `finish` before the end event), and the compaction's `COUNTED` and keep list protect that mark. Every wait value (batch time, quiet time, start wait, poll interval, lifetime, clock, pid check) is a function parameter, never an environment variable.
- Sessions report: `auto/scripts/sessions.mjs` is a read-only one-shot report of the am-auto:multi and am-auto:one stage sessions and live am-orchestrator runs on this PC, per working tree (it writes, removes and stops nothing). The am-auto:sessions skill runs it once with no argument by the command string `tests/skills.test.mjs` pins, so changing the script's path or arguments means changing the skill and that test in the same commit. It relies on `stage-worker.json` (`pid`, `t`, `stage`, `fix`, `solo`, its mtime and `WORKER_STALE_MS`), `progress.jsonl` (`start`, the `stage: "handover"` note), `compact-pending.json`, plan.md's done mark (`countDone`) and the `.gate` records' file name and `phase`, `repo`, `where`, `startedAt` (read through `liveRecords` of `memory-guard.mjs`), so changing any of those formats means changing `sessions.mjs` and `tests/sessions.test.mjs` in the same commit. A task line names am-auto:one when the worker record's `solo` is set (a `.gate`-only line reads the task's `stage-worker.json` as it is, live or not), else am-auto:multi. On the orchestrator side it relies on `.orchestrator/lock.json` (`pid`, `leaseMs`, `run`, `command`, its mtime), `worker/worker.json` (`pid`, `owner`: a run whose owner is an am-auto:multi stage worker's pid goes under that task as a hand-over), `runs/<run>/state.json` (`tasks.*.running`, `worktree`), `runs/<run>/tasks.json` (`tasks[].id`, `title`), the `task` of `runs/<run>/progress.jsonl` events, and the session and `.gate` records' `phase` (split, answer, gate, worktreeSetup), `where` (`.orchestrator/runs/<run>/<id>` for a session), `repo` and `startedAt`; changing one of those in `orchestrator/` means changing `sessions.mjs`, `tests/sessions.test.mjs` and `tests/orchestrator-skill.test.mjs` (which runs a real orchestrator and reads it through `collect`) in the same commit. Time values, the pid check, the host, the record folder and the git call are function parameters; only the command-line entry passes the environment.
- Commit record: am:commit appends `<full hash> <subject>` to `.am/<slug>/commits.md` after each commit, except in a session am-orchestrator started (it looks for "running inside am-orchestrator"); the commit stage of `stage.mjs` may write only that file, and in a solo task also its owner's `solo-context.md`.
- Current task mark: am:plan and am:do write the slug to `.am/.active`, which am:do and am:commit only list first as current, never follow on their own. `.am/.active` is not written in a session am-orchestrator started (the commits.md wording), and the plan stage's rules of `stage.mjs` name it. `tests/skills.test.mjs` and `tests/stage.test.mjs` pin the rules.
- Do result: am:do rewrites `.am/<slug>/do-result.md` whole when every step is done and whenever it stops (its step 5), first line exactly `Status: done` or `Status: stopped - <reason>` in English, the rest in the plan's language; it reads the previous one when it resumes. am:check reads it at the start only to aim its runtime check and review, never as evidence; am:commit uses its file list to tell the task's files (the actual diff wins). It is not a compaction target of `stage.mjs`. `tests/skills.test.mjs` pins the wording, so change the three skills and that test together.
- Art plugin (`art/`): the repository is public, so company values (work folders, the Python path, deploy tool paths, page IDs) never go into it; each PC keeps them in `<CLAUDE_CONFIG_DIR or ~/.claude>/am/art.json`, read and written only by `art/scripts/art-settings.mjs` (checked keys, a lock and an atomic rename; `autoChanged` (repository folder -> path patterns) is written only by its `auto add` and `auto remove` commands; `auto match` does the pattern matching), and `tests/art.test.mjs` scans `art/`, `shared/art.md`, README, CHANGELOG and itself for drive-letter paths, Notion URLs and hex IDs. Each skill is for one tool: the five Claude Code skills live in `art/claude-skills/`, which only the Claude manifest names (the exception above), and ad-execute (the Codex worker) in `art/codex-skills/`, which Claude Code does not scan (`SKILL_SUBDIR` of `scripts/models.mjs`); as a last guard ad-review still stops with one line when it is not Claude Code, ad-execute has `disable-model-invocation: true` and stops with one line in Claude Code, and the five Claude Code skills keep `agents/openai.yaml` with implicit invocation off, ad-execute none (`tests/skills.test.mjs`); a personal mail address never goes into the repository (`tests/art.test.mjs`). The five Claude Code skills carry the art owner rules block (`shared/art.md`, `BLOCKS.art`) instead of the common block, ad-execute neither block (it runs in Codex, without `${CLAUDE_PLUGIN_ROOT}` or AskUserQuestion, and finds its package by folder name instead of art.json); they refer to each other as "the am-art:pipe-apply skill"; ad-review's `/loop 5m /am-art:ad-review 자동` line is the one slash name `tests/skills.test.mjs` allows. `art/scripts/make_compare.py` (Python; Pillow only for share mode) writes only files carrying its generator mark and never an input path. `art/scripts/make_dropin.py` (Python and Pillow) writes only a new file, never an existing one or its input. Size limits ad-review 150, pipe-apply 120, log-compare 100, log-resume 120, git-sync 100, ad-execute 120.
- Keep `plugin/`, `auto/` and `util/` small: no telemetry, panels, release gates or batch runners. The batch runner is the separate `orchestrator/` plugin, and the others must work without it: only am-auto:multi hands a large task to its run skill, and only when it is installed.

## Orchestrator plugin (`orchestrator/`)
- One skill (`skills/run`, user-invoked only) and one script (`scripts/orchestrator.mjs`: no dependencies, Node 18+). When `claude` goes through cmd.exe (an npm `.cmd` shim), allow rules with `"` are dropped and plan sessions are told to run node scripts unquoted, as `cmdExeArgs` of `stage.mjs` does. The skill drives the script through `status --json`; every `next` value the script can return must be handled in the skill, and every command the skill names must exist in the script (tests enforce both).
- It calls the installed am skills and `hooks/gate.mjs`, and allows plan sessions to run am's `scripts/codex-opinion.mjs` by its exact path; it never copies them. Unless the config names `amPluginRoot` or `pluginDir`, `run`, `split` and `answer` check the installed am at start with `claude plugin list --json` (entries' `id` starting with `am@`, `enabled`, `installPath`) and use it over the am path `doctor` recorded in `env.json`, which they never rewrite. What it relies on is pinned in `tests/orchestrator-skill.test.mjs`: the skill names, the script path and the debate rounds of the common rules, `$ARGUMENTS`, `.am/<slug>/plan.md` and `check.md`, the hand-over to am:check at the end of am:do, the `(auto-decided)` mark of am-auto:multi (in `auto/flow/run.md`), the second-opinion marks of the common rules (`(second opinion)`, `(second opinion, Codex agreed)`, `(no second opinion)`, read by `SECOND_MARK` for progress news, which also accepts the Korean `(2차 의견` but not `(2차 의견 없음)`; the common rules tell the model to keep the marks in English, and both `SECOND_MARK` copies must stay equal), and the gate's command line and report fields. Changing any of these in `plugin/` or `auto/` means changing the script in the same commit.
- The limit on `claude` sessions for the whole PC (`sessions` command) and the records of running sessions live under `<CLAUDE_CONFIG_DIR or ~/.claude>/am-orchestrator/`, outside the plugin folder so they survive updates. Every test that starts the script must point `CLAUDE_CONFIG_DIR` at a temporary folder (the `makeRepo` helper in `tests/orchestrator-helpers.mjs` does), or it reads and writes the user's real limit and records.
- Its rules for running without a user (what is decided on the user's behalf, when to stop) follow `auto/flow/run.md` (am-auto:multi's flow). Change them together. One exception: stage sessions have a time limit, so they cap the Claude-Codex debate at 1 more round instead of 2.
- Stage sessions get `--model` and `--effort` from `STAGE_DEFAULTS` in the script unless `.orchestrator/config.json` names other values. Its plan, implement, check and commit rows must equal the frontmatter of the am skill that stage runs (pinned in the same test file); `scripts/models.mjs` writes them from those skills' entries in `models.json`. A stage whose values the config changes is called inline (only when `skillMode` is `auto`), because a slash call also carries the skill's own frontmatter and which of the two Claude Code uses is not documented. The user models file `<CLAUDE_CONFIG_DIR or ~/.claude>/am/models.json` is the next layer, read by the script's own copy of `plugin/scripts/user-models.mjs` (same path, checks and error wording); model and effort each go config chain → user file chain (`implement` reads `do`, fix and answer inherit) → `STAGE_DEFAULTS`, `extraArgs` flags first; a broken file stops before any session; a stage the user file changes is also called inline.
- The user models file's format or keys change only together: `plugin/scripts/user-models.mjs`, its copy in `orchestrator/scripts/orchestrator.mjs` and the test in `tests/orchestrator-skill.test.mjs` that runs both copies on the same inputs change in the same commit.
- The user settings file (`<CLAUDE_CONFIG_DIR or ~/.claude>/am/settings.json`) likewise: `plugin/scripts/user-settings.mjs`, its copy in `orchestrator/scripts/orchestrator.mjs` (`userSettingsFile`, `readUserSettings`) and the test in `tests/orchestrator-skill.test.mjs` that runs both copies on the same inputs change only in the same commit; the orchestrator uses a usable `.orchestrator/config.json` value first, then this file, then the default; the orchestrator copy only accepts `stageMcpServers`, which am-auto alone uses.
- `auto/scripts/memory-guard.mjs` copies the orchestrator's free-memory rule (`memoryShortMB`, `DEFAULT_MIN_FREE_MEMORY_MB`), `recordHeld`, the record folder, name pattern (`RECORD_NAME`), host name and the 30-second/5-minute times, and writes `.gate` records that the orchestrator counts only in its memory check; `tests/orchestrator-skill.test.mjs` compares both copies on the same inputs, so changing one means changing the other in the same commit.
- `orchestrator/scripts/orchestrator.mjs` copies `auto/scripts/proc-tree.mjs` (same exported names and bodies) and, in `exec()`, stops what each `runClaude` session left behind after it closes (within `CLEANUP_MS`; a Korean run-log line and progress note only when something was stopped; a failed cleanup never changes the result); `tests/orchestrator-skill.test.mjs` runs both copies on the same fake lists, so changing one means changing the other and that test in the same commit.
- The other direction: am-auto:multi finds the run skill with `claude plugin list --json`, reads it and drives it. What it relies on is pinned in the same test file: the plugin id, `skills/run/SKILL.md`, the run skill's request form, Prepare step, step 4 loop and no-merge rule, the `status --json` fields it reads (`run.id`, `run.branch`, `run.report`, `autoDecided`, `secondOpinions`) and the default task size. Changing any of these in `orchestrator/` means changing am-auto:multi in the same commit. `auto/scripts/stage.mjs` also relies on the run skill's frontmatter `model`/`effort`, `Request: $ARGUMENTS` and the `node "${CLAUDE_PLUGIN_ROOT}/scripts/orchestrator.mjs"` command form for an inline hand-over (pinned in the same file).
- Progress news: `split`, `run` and `answer` append events to `.orchestrator/runs/<run>/progress.jsonl` in the same line format as am's `progress.jsonl`, and `lock.json` holds the run's name from the moment the lock is taken. The `progress [--run <run>] [--consumer <name>]` command takes no lock, picks the run to follow again at every check (`--run`, the run of a live lock, the run it was following, `current`), keeps one cursor per run and consumer, and always ends by itself. The run skill starts `progress --consumer main` next to `split`, `answer` and `run` and stops on `state: ended`: changing that command string or that line means changing the skill and `tests/orchestrator-skill.test.mjs` in the same commit. am-auto relies on `.orchestrator/current`, `runs/<run>/progress.jsonl`, the line format and the command name `progress` (`stage.mjs` copies those lines during a handed-over implementation and tells the hand-over session not to run that command); the same test file pins them, and changing one means changing `auto/scripts/stage.mjs` and `auto/scripts/progress.mjs` in the same commit. The progress section imports nothing from am and reads no environment variable: every wait value is a function parameter.
- Worker and follower: `doctor`, `split`, `answer` and `run` without the hidden `--worker` start a detached worker and follow it; the worker holds the lock (`lock.json`'s `pid` is the worker; every lock holder touches it every `lockTouchMs` and stops like Ctrl+C when it names another pid or is gone twice; a lock with `leaseMs` (`LOCK_LEASE_MS`, 5 minutes) untouched that long is not live, and is removed only when a look `lockConfirmMs` later finds it unchanged; a lock without `leaseMs` keeps the pid rule) and keeps `.orchestrator/worker/`: `worker.json` (pid, command, args, start, `owner` from `AM_HANDOVER_OWNER`; written only after the lock is taken), `log`, `read-<pid>` (shared read position), `result-<pid>.json`, `delivered-<pid>` (`wx` claim), `heartbeat`. The follower prints the log from the read position, forwards signals and ends with the worker's code, or after `followLimitMs` (equal to progress's `maxLifeMs`, pinned) with the still-running line and exit code 4; the same command with no argument follows a live worker again; a call with arguments follows only a worker, and takes only a result, with the same `argsKey` (a live worker of other arguments is busy), and `result-*.json` carries `args`. A result no follower took goes once to the next call of the same command, counts as delivered after another state-changing command succeeds, and is ignored after `heartbeatMs`. The worker stops like Ctrl+C (130, result delivered) when `heartbeat`, refreshed by each follower poll, stays unchanged for `heartbeatMs` (30 minutes, counted by its own polls). `WORKER_DEFAULTS` and `FOLLOW_DEFAULTS` are function parameters; am-auto's `stage.mjs` reads `worker.json`'s `pid`/`owner` and the lock pid (pinned in `tests/orchestrator-skill.test.mjs`), so changing them means changing `auto/scripts/stage.mjs` in the same commit.
- The run skill carries the same common rules block as the am skills and stays within 120 lines. Text sent to a model is English; what a person reads (script output, report, README) is Korean.
- Each plugin has its own `version`; a user-visible change to `orchestrator/`, `auto/`, `util/` or `art/` bumps that folder's `.claude-plugin/plugin.json` and gets its own CHANGELOG entry headed `am-orchestrator <version>`, `am-auto <version>`, `am-util <version>` or `am-art <version>`.
