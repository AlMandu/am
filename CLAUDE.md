# am plugin repository

Lightweight plan/do/check/commit workflow plugin for Claude Code and Codex CLI. The repository root is the marketplace (`.claude-plugin/marketplace.json`) and lists two plugins, each installed into users' caches on its own: `plugin/` is `am`, and `orchestrator/` is `am-orchestrator` (Claude Code only), which runs the am skills task by task over a whole design document.

## Rules
- One source for both tools. Codex reads `.claude-plugin/` manifests and plugin hooks natively; do not add Codex-only copies.
- `hooks/hooks.json` handler keys: `type`, `command`, `timeout` only. No `args`, `if` or `commandWindows` (one of the two tools ignores or rejects them). The command must not rely on shell path expansion: Codex runs it with `cmd /C` on Windows.
- `plugin.json` must not list `hooks` or `skills`; the default folders are loaded and listing them registers twice in Claude Code. Do not list `agents` either; the default `agents/` folder is scanned.
- Hook output contract (measured on Claude Code 2.1 and Codex 0.160): always exit 0; stdout is empty or exactly one JSON object; block with `hookSpecificOutput.permissionDecision: "deny"` plus a non-empty reason. Codex ignored exit 2.
- Changing `hooks.json` makes every Codex user re-trust the hook. Avoid it.
- Skills: English bodies; frontmatter `description` and `argument-hint` in Korean (users see them in the command palette); README/CHANGELOG in Korean. The common rules block must stay identical in every SKILL.md; size limits plan/check 120 lines, commit/do/auto/compactmem 80 (tests enforce both). Refer to other skills as "the am:check skill", not `/am:check`.
- Second opinion: `plugin/agents/second-opinion.md` is the one subagent, and Claude Code only (Codex has no such subagent, so the common rules fall back to the session's own pick). Its frontmatter pins `model` and `effort` (values from `models.json`, see below) and keeps the tools read-only. Write the model as an alias (`opus`): it follows the main session's Opus version, so a new Opus is used without an edit. Claude Code ignores a misspelled frontmatter key without an error, so the tests check the exact keys and values. English body, Korean `description`.
- Codex second opinion: when Codex is installed, the common rules also run `plugin/scripts/codex-opinion.mjs <brief>` (Claude Code only) and debate a split with the subagent (at most 2 more rounds, then the user decides). Orchestrator plan sessions may run that script and nothing else, so its `codex exec` flags stay constants, it sends only a `.md` brief under `.am/`, and it takes no other argument; tests set the timeout and PATH through function parameters, never environment variables. `second-opinion.md` is the instruction text for both reviewers.
- Model and effort: every SKILL.md sets `model` and `effort` in its frontmatter (Claude Code only; Codex ignores both keys), and the tests check the exact keys and values. They hold only for the turn that invokes the skill. Write the model as an alias (`opus`), not a full ID, as for the second opinion: a skill whose model cannot be resolved has no fallback, unlike the subagent.
- One source for model and effort: `models.json` at the repository root holds the values of every skill (both plugins), the second-opinion subagent, the Codex second opinion (an empty model leaves the user's codex config in charge), the stage runner's compaction session and the orchestrator's split stage. Change values only there, then run `node scripts/models.mjs`: it rewrites the frontmatter, `STAGE_DEFAULTS`, `CODEX_ARGS`, `COMPACT_MODEL` and the tables between `<!-- am:models:start -->` and `<!-- am:models:end -->` in both READMEs (`--check` only lists drift). Neither plugin reads `models.json` at runtime, and the docs point at those tables instead of repeating values. Each target must match exactly once, so a changed file format stops the script; fix its target in `scripts/models.mjs`.
- Hand-over hook: am:auto's frontmatter declares a one-line PreToolUse hook (`plugin/hooks/handover.mjs`, Claude Code only, active for the rest of a session that invoked am:auto). It denies file edits outside `.am/`, `.orchestrator/` and `am-gate.json` while the session's plan is above 1 implementation run or 1 commit, am-orchestrator is installed, and no step is done or hand-over logged. It reads am:auto's Scale line, am:do's done mark and the hand-over line with the run ID, so changing any of them means changing `handover.mjs` and `tests/handover.test.mjs` in the same commit. Shell commands are not checked (user decision).
- Stage sessions: in Claude Code, am:auto runs each phase in a fresh `claude -p` session through `plugin/scripts/stage.mjs` (one stage per call, not a batch runner); Codex, and a PC where no session can start (`unavailable`), keep the single-session flow. The script fixes each stage's permissions, calls the stage's am skill by slash command and passes no `--model`/`--effort` (the skill's frontmatter applies), and reads an `AM_STAGE:` end line. Its unattended rules are an English copy of am:auto's "Running without stops" written for one stage (user decision); change them together, `tests/stage.test.mjs` pins the auto-decided mark and the stop list in both. The do stage becomes a hand-over to the run skill by `readPlan` and `findOrchestrator` of `handover.mjs`, and follows am:auto step 4's additions (run ID line, merge, push). Every status the script prints must be handled in am:auto (`tests/skills.test.mjs`); what the hand-over relies on in `orchestrator/` is pinned in `tests/orchestrator-skill.test.mjs`. Tests pass the claude command, time limits and the orchestrator lookup as function parameters. Before a stage, task files above about 13,000 estimated tokens are shortened in a separate compaction session (the only one that gets `--model`/`--effort`, from `COMPACT_MODEL`), checked mechanically and put back on any failure; its markers are `COMPACT_MARKS`, not `MARKS`, because they never reach am:auto as a status (am:auto only reports the result's `compacted` field). `request.md` is never counted or shortened (user decision): the compaction session gets a deny rule for that file, and the script puts it back and undoes the compaction when it was changed. Nothing is shortened before the plan stage or a hand-over (user decision): a `plan.md` shortened before a plan stage that runs again would reach the orchestrator short, with no notice of its original.
- Progress news: stage sessions append events to `.am/<slug>/progress.jsonl` (append-only, one JSON object per line: required `t`, `ev`, `text`; optional `pid` (on `start` only), `stage`, `task`, `status`, `min`, `src`; `ev` is `start`, `step`, `note`, `alert` or `end`). `stage.mjs` writes them and, during a hand-over, copies the run's lines with `src: "run"`; an error while writing is swallowed. The progress command `plugin/scripts/progress.mjs <slug> [--consumer <name>]` prints the lines its consumer has not seen plus one state line (`state: running (…)` or `state: ended`) and always ends by itself (exit code 0, or 1 for bad arguments; under the 10-minute limit of a background command). Each consumer has its own cursor file: am:auto calls it with `--consumer main`, a person with no option (`terminal`). am:auto reads that command string and `state: ended`, so changing either means changing the skill and `tests/skills.test.mjs` in the same commit. The line format and the output must equal the orchestrator's `progress` command (`tests/orchestrator-skill.test.mjs` compares them on the same input). The state line counts done steps with `countDone` of `handover.mjs`, one more reader of am:do's done mark: changing the mark also means changing it and `tests/progress.test.mjs`. Every wait value (batch time, quiet time, start wait, poll interval, lifetime, clock, pid check) is a function parameter, never an environment variable.
- Keep `plugin/` small: no telemetry, panels, release gates or batch runners. The batch runner is the separate `orchestrator/` plugin, and `plugin/` must work without it: only am:auto hands a large task to its run skill, and only when it is installed.

## Orchestrator plugin (`orchestrator/`)
- One skill (`skills/run`, user-invoked only) and one script (`scripts/orchestrator.mjs`: no dependencies, Node 18+). The skill drives the script through `status --json`; every `next` value the script can return must be handled in the skill, and every command the skill names must exist in the script (tests enforce both).
- It calls the installed am skills and `hooks/gate.mjs`, and allows plan sessions to run am's `scripts/codex-opinion.mjs` by its exact path; it never copies them. What it relies on is pinned in `tests/orchestrator-skill.test.mjs`: the skill names, the script path and the debate rounds of the common rules, `$ARGUMENTS`, `.am/<slug>/plan.md` and `check.md`, the hand-over to am:check at the end of am:do, the `(auto-decided)` mark of am:auto, and the gate's command line and report fields. Changing any of these in `plugin/` means changing the script in the same commit.
- The limit on `claude` sessions for the whole PC (`sessions` command) and the records of running sessions live under `<CLAUDE_CONFIG_DIR or ~/.claude>/am-orchestrator/`, outside the plugin folder so they survive updates. Every test that starts the script must point `CLAUDE_CONFIG_DIR` at a temporary folder (the `makeRepo` helper in `tests/orchestrator-helpers.mjs` does), or it reads and writes the user's real limit and records.
- Its rules for running without a user (what is decided on the user's behalf, when to stop) follow the am:auto skill. Change them together. One exception: stage sessions have a time limit, so they cap the Claude-Codex debate at 1 more round instead of 2.
- Stage sessions get `--model` and `--effort` from `STAGE_DEFAULTS` in the script unless `.orchestrator/config.json` names other values. Its plan, implement, check and commit rows must equal the frontmatter of the am skill that stage runs (pinned in the same test file); `scripts/models.mjs` writes them from those skills' entries in `models.json`. A stage whose values the config changes is called inline (only when `skillMode` is `auto`), because a slash call also carries the skill's own frontmatter and which of the two Claude Code uses is not documented.
- The other direction: am:auto finds the run skill with `claude plugin list --json`, reads it and drives it. What it relies on is pinned in the same test file: the plugin id, `skills/run/SKILL.md`, the run skill's request form, Prepare step, step 4 loop and no-merge rule, the `status --json` fields it reads (`run.id`, `run.branch`, `run.report`, `costUsd`, `autoDecided`) and the default task size. Changing any of these in `orchestrator/` means changing am:auto in the same commit.
- Progress news: `split`, `run` and `answer` append events to `.orchestrator/runs/<run>/progress.jsonl` in the same line format as am's `progress.jsonl`, and `lock.json` holds the run's name from the moment the lock is taken. The `progress [--run <run>] [--consumer <name>]` command takes no lock, picks the run to follow again at every check (`--run`, the run of a live lock, the run it was following, `current`), keeps one cursor per run and consumer, and always ends by itself. The run skill starts `progress --consumer main` next to `split`, `answer` and `run` and stops on `state: ended`: changing that command string or that line means changing the skill and `tests/orchestrator-skill.test.mjs` in the same commit. am relies on `.orchestrator/current`, `runs/<run>/progress.jsonl`, the line format and the command name `progress` (`stage.mjs` copies those lines during a handed-over implementation and tells the hand-over session not to run that command); the same test file pins them, and changing one means changing `plugin/scripts/stage.mjs` and `plugin/scripts/progress.mjs` in the same commit. The progress section imports nothing from am and reads no environment variable: every wait value is a function parameter.
- The run skill carries the same common rules block as the am skills and stays within 120 lines. Text sent to a model is English; what a person reads (script output, report, README) is Korean.
- Each plugin has its own `version`; a user-visible change to `orchestrator/` bumps `orchestrator/.claude-plugin/plugin.json` and gets its own CHANGELOG entry headed `am-orchestrator <version>`.

## Before committing
- `node --test tests/gate.test.mjs tests/skills.test.mjs tests/codex-opinion.test.mjs tests/models.test.mjs tests/handover.test.mjs tests/stage.test.mjs tests/progress.test.mjs`
- `claude plugin validate .` and `claude plugin validate plugin`
- After touching `orchestrator/`, anything in `plugin/` that it relies on, or am:auto's hand-over: `node --test tests/orchestrator-skill.test.mjs tests/orchestrator.test.mjs tests/orchestrator-plan.test.mjs tests/orchestrator-commit.test.mjs tests/orchestrator-drive.test.mjs tests/orchestrator-doctor.test.mjs tests/orchestrator-parallel.test.mjs tests/orchestrator-volatile.test.mjs tests/orchestrator-rewrite.test.mjs tests/orchestrator-sessions.test.mjs tests/orchestrator-progress.test.mjs` (the files after the first take about 35 seconds together on a 24-core PC and need no `claude`) and `claude plugin validate orchestrator`
- User-visible change: bump `version` in `plugin/.claude-plugin/plugin.json` and add one CHANGELOG entry.
- Refresh a local Codex install with `codex plugin remove am@am-workflow` then `codex plugin add am@am-workflow`.
