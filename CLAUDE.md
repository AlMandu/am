# am plugin repository

Lightweight plan/do/check/commit workflow plugin for Claude Code and Codex CLI. The repository root is the marketplace (`.claude-plugin/marketplace.json`) and lists two plugins, each installed into users' caches on its own: `plugin/` is `am`, and `orchestrator/` is `am-orchestrator` (Claude Code only), which runs the am skills task by task over a whole design document.

## Rules
- One source for both tools. Codex reads `.claude-plugin/` manifests and plugin hooks natively; do not add Codex-only copies.
- `hooks/hooks.json` handler keys: `type`, `command`, `timeout` only. No `args`, `if` or `commandWindows` (one of the two tools ignores or rejects them). The command must not rely on shell path expansion: Codex runs it with `cmd /C` on Windows.
- `plugin.json` must not list `hooks` or `skills`; the default folders are loaded and listing them registers twice in Claude Code. Do not list `agents` either; the default `agents/` folder is scanned.
- Hook output contract (measured on Claude Code 2.1 and Codex 0.160): always exit 0; stdout is empty or exactly one JSON object; block with `hookSpecificOutput.permissionDecision: "deny"` plus a non-empty reason. Codex ignored exit 2.
- Changing `hooks.json` makes every Codex user re-trust the hook. Avoid it.
- Skills: English bodies; frontmatter `description` and `argument-hint` in Korean (users see them in the command palette); README/CHANGELOG in Korean. The common rules block must stay identical in every SKILL.md; size limits plan/check 120 lines, commit/do/auto/compactmem/merge 80 (tests enforce both). Refer to other skills as "the am:check skill", not `/am:check`.
- Second opinion: `plugin/agents/second-opinion.md` is the one subagent, and Claude Code only (Codex has no such subagent, so the common rules fall back to the session's own pick). Its frontmatter pins `model` and `effort` (values from `models.json`, see below); the only override is the user models file's `second-opinion` key, which `codex-opinion.mjs` reports as its first output line `Claude reviewer: …` and the common rules pass as the Agent call's `model`/`effort` (aliases in `OPINION_MODELS` only). Both opinion keys skip the file's `default`. The frontmatter keeps the tools read-only. Write the model as an alias (`opus`): it follows the main session's Opus version, so a new Opus is used without an edit. Claude Code ignores a misspelled frontmatter key without an error, so the tests check the exact keys and values. English body, Korean `description`.
- Codex second opinion: when Codex is installed, the common rules also run `plugin/scripts/codex-opinion.mjs <brief>` (Claude Code only) and debate a split with the subagent (at most 2 more rounds, then the user decides). Orchestrator plan sessions may run that script and nothing else, so its `codex exec` flags stay constants except the model and effort of the user models file's `codex-opinion` key, unquoted tokens checked against `CODEX_MODEL` and `CODEX_EFFORTS` (Codex runs through `cmd /C` and reads `-c` values as TOML), it sends only a `.md` brief under `.am/`, and it takes no other argument; tests set the timeout and PATH through function parameters, never environment variables, and point `CLAUDE_CONFIG_DIR` at a temporary folder. `second-opinion.md` is the instruction text for both reviewers.
- Model and effort: every SKILL.md sets `model` and `effort` in its frontmatter (Claude Code only; Codex ignores both keys), and the tests check the exact keys and values. They hold only for the turn that invokes the skill. Write the model as an alias (`opus`), not a full ID, as for the second opinion: a skill whose model cannot be resolved has no fallback, unlike the subagent.
- One source for model and effort: `models.json` at the repository root holds the values of every skill (both plugins), the second-opinion subagent, the Codex second opinion (an empty model leaves the user's codex config in charge), the stage runner's compaction session and the orchestrator's split stage. Change values only there, then run `node scripts/models.mjs`: it rewrites the frontmatter, `STAGE_DEFAULTS`, `CODEX_ARGS`, `COMPACT_MODEL` and the tables between `<!-- am:models:start -->` and `<!-- am:models:end -->` in both READMEs (`--check` only lists drift). Neither plugin reads `models.json` at runtime, and the docs point at those tables instead of repeating values. Each target must match exactly once, so a changed file format stops the script; fix its target in `scripts/models.mjs`.
- Hand-over hook: am:auto's frontmatter declares a one-line PreToolUse hook (`plugin/hooks/handover.mjs`, Claude Code only, active for the rest of a session that invoked am:auto). It denies file edits outside `.am/`, `.orchestrator/` and `am-gate.json` while the session's plan is above 1 implementation run or 1 commit, am-orchestrator is installed, and no step is done or hand-over logged. It reads am:auto's Scale line, am:do's done mark and the fixed `Hand-over:` line in the plan's Change log (older wording still read), so changing any of them means changing `handover.mjs` and `tests/handover.test.mjs` in the same commit. Shell commands are not checked (user decision).
- Stage sessions: in Claude Code, am:auto runs each phase in a fresh `claude -p` session through `plugin/scripts/stage.mjs` (one stage per call, not a batch runner); Codex, and a PC where no session can start (`unavailable`), keep the single-session flow. The script fixes each stage's permissions, calls the stage's am skill by slash command and passes no `--model`/`--effort` (the skill's frontmatter applies), unless the user models file gives the stage a value different from that frontmatter: then the skill body without frontmatter is written to `.am/<slug>/skill-<kind>.md` and called inline with both flags, also on the second ask; the hand-over does the same with the run skill (key `run`, defaults from `<orchRoot>/skills/run/SKILL.md`); it reads an `AM_STAGE:` end line. The do, compactmem and commit sessions and the compaction session get `FORCE_PROMPT_CACHING_5M=1` in their environment (`CACHE_5M_KINDS`); plan, check and the hand-over keep the 1-hour cache because they wait longer. The plan and compactmem sessions may run the Codex second-opinion script of the runner's am and of every enabled installed am found by `findAm` of `handover.mjs` (not looked up for a `--plugin-dir` copy); a different folder is a `note`. The memory stage starts no session and reports NOTHING when the memory folder (in a git worktree also the main checkout's, which Claude Code shares across worktrees) holds no `.md` file and no settings file (user, project, local, of both checkouts) names `autoMemoryDirectory`. Its unattended rules are an English copy of am:auto's "Running without stops" written for one stage (user decision); change them together, `tests/stage.test.mjs` pins the auto-decided mark and the stop list in both. The do stage becomes a hand-over to the run skill by `readPlan` and `findOrchestrator` of `handover.mjs`, and follows am:auto step 4's additions (run ID line, merge, push). Every status the script prints must be handled in am:auto (`tests/skills.test.mjs`); what the hand-over relies on in `orchestrator/` is pinned in `tests/orchestrator-skill.test.mjs`. Tests pass the claude command, time limits and the orchestrator lookup as function parameters. Before writing its `start` line, a stage takes the start lock `.am/.admission.lock` and waits (a `note` with `stage: 'wait'`, then status `WAIT` that am:auto answers by running the stage again) while another unattended run of this working tree goes on (`otherRuns`: another task's live stage or its gap between stages, a live orchestrator lock, or the gap after its split or answer, read from `lock.json`'s `pid` and those end statuses, pinned in `tests/orchestrator-skill.test.mjs`); every wait value is a function parameter of `main`. A stage reads the per-PC settings file with `user-settings.mjs` (broken: `failed` with no session), and a stage that is not a hand-over, inside the start lock, first writes a `.gate` record in the orchestrator's record folder with `memory-guard.mjs`, then checks the free memory (short: it waits, up to `WAIT`) and holds the record until `finish`; it relies on the orchestrator's record name pattern and folder, pinned in `tests/orchestrator-skill.test.mjs`, so changing them means changing `memory-guard.mjs` and `stage.mjs` in the same commit, and `freeMem`, `platform` and `heartbeatMs` are function parameters of `main` too. Before a stage, task files above about 13,000 estimated tokens are shortened in a separate compaction session (it always gets `--model`/`--effort`: the user models file's `compact`, else `default` value (`plugin/scripts/user-models.mjs`), else `COMPACT_MODEL`), checked mechanically and put back on any failure; its markers are `COMPACT_MARKS`, not `MARKS`, because they never reach am:auto as a status (am:auto only reports the result's `compacted` field). `request.md` is never counted or shortened (user decision): the compaction session gets a deny rule for that file, and the script puts it back and undoes the compaction when it was changed. Nothing is shortened before the plan stage or a hand-over (user decision): a `plan.md` shortened before a plan stage that runs again would reach the orchestrator short, with no notice of its original.
- Progress news: stage sessions append events to `.am/<slug>/progress.jsonl` (append-only, one JSON object per line: required `t`, `ev`, `text`; optional `pid` (on `start` only), `stage`, `task`, `status`, `min`, `src`; `ev` is `start`, `step`, `note`, `alert` or `end`). `stage.mjs` writes them and, during a hand-over, copies the run's lines with `src: "run"`; an error while writing is swallowed. The progress command `plugin/scripts/progress.mjs <slug> [--consumer <name>]` prints the lines its consumer has not seen plus one state line (`state: running (…)` or `state: ended`) and always ends by itself (exit code 0, or 1 for bad arguments; under the 10-minute limit of a background command). Each consumer has its own cursor file: am:auto calls it with `--consumer main`, a person with no option (`terminal`). am:auto reads that command string and `state: ended`, so changing either means changing the skill and `tests/skills.test.mjs` in the same commit. The line format and the output must equal the orchestrator's `progress` command (`tests/orchestrator-skill.test.mjs` compares them on the same input). The state line counts done steps with `countDone` of `handover.mjs`, one more reader of am:do's done mark: changing the mark also means changing it and `tests/progress.test.mjs`. In plan and do stages `stage.mjs` writes a `step` (`second opinion: <line>`) for each new `(second opinion` line of plan.md (lines there after compaction are the in-memory baseline, read every `opinionMs`, a function parameter, and a last time in `finish` before the end event), and the compaction's `COUNTED` and keep list protect that mark. Every wait value (batch time, quiet time, start wait, poll interval, lifetime, clock, pid check) is a function parameter, never an environment variable.
- Commit record: am:commit appends `<full hash> <subject>` to `.am/<slug>/commits.md` after each commit, except in a session am-orchestrator started (it looks for "running inside am-orchestrator"); the commit stage of `stage.mjs` may write only that file. am:merge (user-invoked only, never pushes) reads it, so changing the file or its line format means changing am:merge and `tests/skills.test.mjs` in the same commit.
- am:merge also reads `.orchestrator/runs/<run>/state.json` (`tasks.*.commits`, each entry starting with a hash), `.orchestrator/lock.json` and am:auto's hand-over Change log line with the run ID; `tests/orchestrator-skill.test.mjs` pins them, and changing one in `orchestrator/` or am:auto means changing am:merge in the same commit.
- Keep `plugin/` small: no telemetry, panels, release gates or batch runners. The batch runner is the separate `orchestrator/` plugin, and `plugin/` must work without it: only am:auto hands a large task to its run skill, and only when it is installed.

## Orchestrator plugin (`orchestrator/`)
- One skill (`skills/run`, user-invoked only) and one script (`scripts/orchestrator.mjs`: no dependencies, Node 18+). The skill drives the script through `status --json`; every `next` value the script can return must be handled in the skill, and every command the skill names must exist in the script (tests enforce both).
- It calls the installed am skills and `hooks/gate.mjs`, and allows plan sessions to run am's `scripts/codex-opinion.mjs` by its exact path; it never copies them. What it relies on is pinned in `tests/orchestrator-skill.test.mjs`: the skill names, the script path and the debate rounds of the common rules, `$ARGUMENTS`, `.am/<slug>/plan.md` and `check.md`, the hand-over to am:check at the end of am:do, the `(auto-decided)` mark of am:auto, the second-opinion marks of the common rules (`(second opinion)`, `(second opinion, Codex agreed)`, `(no second opinion)`, read by `SECOND_MARK` for progress news), and the gate's command line and report fields. Changing any of these in `plugin/` means changing the script in the same commit.
- The limit on `claude` sessions for the whole PC (`sessions` command) and the records of running sessions live under `<CLAUDE_CONFIG_DIR or ~/.claude>/am-orchestrator/`, outside the plugin folder so they survive updates. Every test that starts the script must point `CLAUDE_CONFIG_DIR` at a temporary folder (the `makeRepo` helper in `tests/orchestrator-helpers.mjs` does), or it reads and writes the user's real limit and records.
- Its rules for running without a user (what is decided on the user's behalf, when to stop) follow the am:auto skill. Change them together. One exception: stage sessions have a time limit, so they cap the Claude-Codex debate at 1 more round instead of 2.
- Stage sessions get `--model` and `--effort` from `STAGE_DEFAULTS` in the script unless `.orchestrator/config.json` names other values. Its plan, implement, check and commit rows must equal the frontmatter of the am skill that stage runs (pinned in the same test file); `scripts/models.mjs` writes them from those skills' entries in `models.json`. A stage whose values the config changes is called inline (only when `skillMode` is `auto`), because a slash call also carries the skill's own frontmatter and which of the two Claude Code uses is not documented. The user models file `<CLAUDE_CONFIG_DIR or ~/.claude>/am/models.json` is the next layer, read by the script's own copy of `plugin/scripts/user-models.mjs` (same path, checks and error wording); model and effort each go config chain → user file chain (`implement` reads `do`, fix and answer inherit) → `STAGE_DEFAULTS`, `extraArgs` flags first; a broken file stops before any session; a stage the user file changes is also called inline.
- The user models file's format or keys change only together: `plugin/scripts/user-models.mjs`, its copy in `orchestrator/scripts/orchestrator.mjs` and the test in `tests/orchestrator-skill.test.mjs` that runs both copies on the same inputs change in the same commit.
- The user settings file (`<CLAUDE_CONFIG_DIR or ~/.claude>/am/settings.json`) likewise: `plugin/scripts/user-settings.mjs`, its copy in `orchestrator/scripts/orchestrator.mjs` (`userSettingsFile`, `readUserSettings`) and the test in `tests/orchestrator-skill.test.mjs` that runs both copies on the same inputs change only in the same commit; the orchestrator uses a usable `.orchestrator/config.json` value first, then this file, then the default.
- `plugin/scripts/memory-guard.mjs` copies the orchestrator's free-memory rule (`memoryShortMB`, `DEFAULT_MIN_FREE_MEMORY_MB`), `recordHeld`, the record folder, name pattern (`RECORD_NAME`), host name and the 30-second/5-minute times, and writes `.gate` records that the orchestrator counts only in its memory check; `tests/orchestrator-skill.test.mjs` compares both copies on the same inputs, so changing one means changing the other in the same commit.
- The other direction: am:auto finds the run skill with `claude plugin list --json`, reads it and drives it. What it relies on is pinned in the same test file: the plugin id, `skills/run/SKILL.md`, the run skill's request form, Prepare step, step 4 loop and no-merge rule, the `status --json` fields it reads (`run.id`, `run.branch`, `run.report`, `autoDecided`, `secondOpinions`) and the default task size. Changing any of these in `orchestrator/` means changing am:auto in the same commit. `plugin/scripts/stage.mjs` also relies on the run skill's frontmatter `model`/`effort`, `Request: $ARGUMENTS` and the `node "${CLAUDE_PLUGIN_ROOT}/scripts/orchestrator.mjs"` command form for an inline hand-over (pinned in the same file).
- Progress news: `split`, `run` and `answer` append events to `.orchestrator/runs/<run>/progress.jsonl` in the same line format as am's `progress.jsonl`, and `lock.json` holds the run's name from the moment the lock is taken. The `progress [--run <run>] [--consumer <name>]` command takes no lock, picks the run to follow again at every check (`--run`, the run of a live lock, the run it was following, `current`), keeps one cursor per run and consumer, and always ends by itself. The run skill starts `progress --consumer main` next to `split`, `answer` and `run` and stops on `state: ended`: changing that command string or that line means changing the skill and `tests/orchestrator-skill.test.mjs` in the same commit. am relies on `.orchestrator/current`, `runs/<run>/progress.jsonl`, the line format and the command name `progress` (`stage.mjs` copies those lines during a handed-over implementation and tells the hand-over session not to run that command); the same test file pins them, and changing one means changing `plugin/scripts/stage.mjs` and `plugin/scripts/progress.mjs` in the same commit. The progress section imports nothing from am and reads no environment variable: every wait value is a function parameter.
- The run skill carries the same common rules block as the am skills and stays within 120 lines. Text sent to a model is English; what a person reads (script output, report, README) is Korean.
- Each plugin has its own `version`; a user-visible change to `orchestrator/` bumps `orchestrator/.claude-plugin/plugin.json` and gets its own CHANGELOG entry headed `am-orchestrator <version>`.

## Before committing
- `node --test tests/gate.test.mjs tests/skills.test.mjs tests/codex-opinion.test.mjs tests/models.test.mjs tests/handover.test.mjs tests/stage.test.mjs tests/progress.test.mjs`
- `claude plugin validate .` and `claude plugin validate plugin`
- After touching `orchestrator/`, anything in `plugin/` that it relies on, or am:auto's hand-over: `node --test tests/orchestrator-skill.test.mjs tests/orchestrator.test.mjs tests/orchestrator-plan.test.mjs tests/orchestrator-commit.test.mjs tests/orchestrator-drive.test.mjs tests/orchestrator-doctor.test.mjs tests/orchestrator-parallel.test.mjs tests/orchestrator-volatile.test.mjs tests/orchestrator-rewrite.test.mjs tests/orchestrator-sessions.test.mjs tests/orchestrator-progress.test.mjs` (the files after the first take about 35 seconds together on a 24-core PC and need no `claude`) and `claude plugin validate orchestrator`
- User-visible change: bump `version` in `plugin/.claude-plugin/plugin.json` and add one CHANGELOG entry.
- Refresh a local Codex install with `codex plugin remove am@am-workflow` then `codex plugin add am@am-workflow`.
