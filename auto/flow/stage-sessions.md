## Stage sessions (Claude Code)
In Claude Code, when `${CLAUDE_PLUGIN_ROOT}/scripts/stage.mjs` exists, steps 3 to 6 each run in a fresh session that gets that step's am skill and the runner's English copy of the rules above; this session only drives and changes no file outside `.am/`, and step 2 is skipped. A new request: pick a short kebab-case slug not under `.am/`, write the request word for word to `.am/<slug>/request.md`, start with the plan stage. To resume: ask an OPEN card left in plan.md first (as for `NEEDS_DECISION`), run the plan stage again if the plan has no Steps yet (write its Summary to `.am/<slug>/request.md` first if that file is missing), add a missing Scale line (step 3), then start with the do stage, or with commit when every step is done and committed. Progress news: right after starting each stage command below, also start `node "${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs" <slug> --consumer main` from the repository root in the background unless one is still running (the progress command). Each time it ends, tell the user what it printed in one or two plain lines (a bare `state: ended` needs no line), except that each `second opinion:` line gets its own plain line: what had to be decided and which option was chosen, and which reviewers agreed, if both did; then stop if its last line is `state: ended` or the stage command it followed has already ended and no stage command of this task is running now; otherwise start it again. When you act on a stage command's result before the progress command reported its end, say that end in one line yourself (stage and status), unless a reply to the user comes next (step 7, a stop or a question) or it is a `WAIT` (its own rule below); never report late news of a stage command whose result you already handled (a `WAIT` is not a result of the stage), other than its `second opinion:` lines. Never choose the next stage from this output: the stage's JSON line decides. For each stage run `node "${CLAUDE_PLUGIN_ROOT}/scripts/stage.mjs" <stage> <slug>` (`plan`, `do`, `check` or `commit`; add `--push` in push mode) from the repository root in the background, wait for its notice, and act on `status` in the JSON line it prints:
- `READY` (plan): the do stage. `DONE` (do): check. `NOTE` (check): commit. `COMMITTED` or `NOTHING` (commit): step 7.
- `BLOCK` (check): run the do stage with `--fix`, then check once more; still `BLOCK` stops (step 5).
- `NEEDS_DECISION`: the stage left an OPEN card in plan.md, a stop above: ask it, replace the card with the answer marked as the user's decision, and run the same stage again with the same flags.
- `BLOCKED` or `failed` (any stage): stop with its `reason` and `reply` file. `unavailable`: no session can start here; read the files of step 2 and do the remaining steps in this session, and say so in the final reply. `WAIT` (any stage): another run of this repository is still going, this PC is short of free memory while other sessions run, or the stage is still running; tell the user once, and again when the `reason` changes, what it waits for, then run the same stage again with the same flags.
For step 7 read plan.md, check.md and the `reply` files; with the deviations from the plan, it also gives each result's `compacted` that is not null (the task files shortened before that stage and their originals, or why the shortening failed and the originals were used).
