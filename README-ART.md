## 먼저 알아 둘 것

### 어느 도구에서 어떻게 부르나

| 스킬 | 도구 | 부르는 법 |
|---|---|---|
| `am-art:ad-review`, `am-art:pipe-apply`, `am-art:log-compare`, `am-art:log-resume` | Claude Code | 아래 예시 문장처럼 말하면 알아서 불립니다. `/am-art:<이름> <인자>` 로 직접 불러도 됩니다. |
| `am-art:ad-auto` | Claude Code | 자리를 비울 때 `/loop 5m /am-art:ad-auto` 로 반복해 돌립니다(아래 ad-review 의 "자동 반복"). |
| `am-art:ad-execute` | Codex | 예시 문장처럼 말하거나 지시서 경로를 붙여 넣으면 불립니다. `$am-art:ad-execute <인자>` 로도 부릅니다. Claude Code 목록에는 나타나지 않습니다. |
| `am-util:git-sync`(Claude Code 만), `am-util:update-branch`, `am-util:land` | Claude Code·Codex | **말로는 불리지 않습니다.** `/am-util:git-sync`, `/am-util:update-branch`, `/am-util:land`(Codex 는 update-branch·land 만, `$` 로 시작)를 직접 입력해야 합니다. |

- 역할: AD(검수·지시)는 Claude Code, 실무자(이미지 생성)는 Codex 입니다. 두 실무자 세션은 `실무자1`, `실무자2` 로 나눕니다.
- 오너(사람)에게 묻는 질문은 한 번에 하나씩, 고르는 방식으로 나옵니다. 추천안이 맨 위에 "(추천)" 표시와 함께 옵니다.
- 결과 파일과 근거 파일은 Claude Code 에서는 누르면 열리는 경로로, Codex 실무자는 한 줄에 하나씩 절대 경로 글자로 알려 줍니다.
- 이미지 생성은 실무자(Codex)만 합니다. AD 쪽 스킬은 이미지를 만들지 않습니다(게임 투입용 축소 사본만 예외).
- 커밋은 어느 스킬이든 오너 승인 뒤에만 합니다. push 는 git-sync 의 "올리기" 와 am-util:land 만 합니다.

### PC별 설정 파일 (`art.json`)
저장소가 공개라 회사 경로는 스킬에 들어 있지 않습니다. 각 PC 의 `<CLAUDE_CONFIG_DIR 또는 ~/.claude>/am/art.json` 에 두고, **값이 없으면 스킬이 처음 필요할 때 하나씩 물어서 저장**합니다. 미리 만들 필요는 없습니다.

| 키 | 뜻 | 처음 묻는 스킬 |
|---|---|---|
| `adCodexRoot` | AD 패키지(`AD_Codex_*`)들이 든 폴더 | ad-review, pipe-apply |
| `spineRoot` | Spine 저장소 | pipe-apply |
| `python` | 패키지 도구·비교 생성기·투입본 생성기를 돌릴 파이썬 | pipe-apply, log-compare, ad-review 게임투입 |
| `deployTools.<이름>` | 반영 도구 스크립트 경로(`무기`, `캐릭터`, `spine-unity`, `펫`) | pipe-apply (도구 없는 종류는 묻지 않음) |
| `gameRoot` | 게임 프로젝트 폴더 | ad-review 게임투입 |
| `browserSmoke` | (선택) 비교 페이지를 브라우저로 확인할 스크립트 | 묻지 않음 |

저장소별 "저절로 바뀌는 파일" 패턴 목록은 이 파일이 아니라 같은 폴더의 `git-sync.json` 에 있고, git-sync 가 아티스트 확인 뒤 더합니다. 예전 art.json 에 있던 목록(`autoChanged`)은 그대로 남아 git-sync 가 저장소마다 처음 한 번 가져갑니다.

손으로 고쳐도 되지만 모르는 키나 깨진 JSON 이 있으면 스킬이 값을 쓰지 않고 멈춥니다. 반영 도구를 새로 등록하려면 오너가 스크립트 경로를 알려 주면 됩니다(예: "배경 반영 도구는 이 스크립트야").

## am-art:ad-review: AD 한 바퀴 (Claude Code)

**하는 일**: AD 패키지에서 AD 역할로 한 바퀴를 돕니다.
피드백 채널 확인 → 실무자의 완료보고·질문 검수 → 판정과 FB 작성 → 다음 지시서 발행 → 상태 대장(`_상태.md`) 기록 → 오너에게 표 하나로 보고.

**하지 않는 일**: 이미지 생성, 파치·Spine·Unity 반영(pipe-apply 가 맡음), 오너 승인 없는 커밋, 새 패키지 만들기, 패키지 규칙 문서(`00`~`04`, `README.md`, `CLAUDE.md`, `AGENTS.md`) 수정.

**시작 조건**: `AD_Codex_*` 패키지 폴더 안에서 시작합니다. 밖이면 어느 패키지인지 묻습니다. 패키지의 설정 사본(`프로젝트/<프로젝트>_<타입>_설정.md`)이 없거나 빈 칸이 있으면 검수하지 않고 무엇이 비었는지 알려 줍니다.

### 인자

| 인자 | 동작 |
|---|---|
| (없음) | 패키지의 처리 안 된 완료보고·질문 전부 |
| `실무자1` / `실무자2` | 그 실무자 문서만 |
| `<문서 경로>` | 그 문서 하나 |
| `자동` | 오너 확인 없이 AD 권한 안의 일은 추천대로 진행. 오너가 정할 일은 그 대상만 `보류` 로 두고 "오너 대기 목록" 에 모음. 반복은 am-art:ad-auto 로 돌림 |
| `시험 <폴더>` | 과거 문서로 예행연습. 쓸 파일을 모두 그 폴더에만 쓰고 피드백 채널은 그대로 둠 |
| `새요청` | 스케치·외부 이미지로 첫 지시서 준비 |
| `게임투입` | 정본을 게임 파일 이름에 맞춘 축소 사본으로 준비 |

`새요청` 과 `게임투입` 은 오너 확인이 필요해서 `자동` 모드에서는 돌지 않습니다.

### 검수 한 바퀴에서 일어나는 일
1. 각 피드백 폴더에서 마지막 AD 기록 뒤의 완료보고·질문을 찾습니다. "최신" 은 파일 이름의 순번과 머리글의 `작성:` 시각으로만 정합니다(파일 수정 시각은 보지 않음). 없으면 `검수할 문서 없음` 한 줄로 끝나서, 반복 실행해도 같은 문서를 두 번 검수하지 않습니다.
2. 완료보고의 해시가 실제 파일과 맞을 때만 검수합니다. 다르면 재전송 요청 문서를 씁니다.
3. 결과 이미지를 직접 열고, 지시서 §8-A 와 같은 명령·스크립트로 다시 잽니다. 정본 옆에 실제 크기(1:1)로 놓고 눈으로 봅니다. 보고서 문구만 보고 판정하지 않습니다.
4. 판정은 `통과 / 수정 / 재생성 / 보류 / 서브보관` 중 하나입니다. FB 는 새 순번 파일로 쓰고, 기존 FB·지시서는 고치지 않고 v+1 로 다시 냅니다.
5. 실무자 질문은 AD 권한 안이면 답변 지시서로 답하고, 오너 결정이 필요하면 오너에게 넘깁니다.
6. 다음 지시서의 수치는 스크립트로 다시 계산하고, 누가 정한 값인지(★오너 / AD실측 / AD추정) 적습니다.
7. 통과하면 정본 위치에 복사합니다. 같은 이름 파일이 있으면 "정본 교체" 라서 오너 승인 → 기존 파일 백업 → 복사 → 상태 대장에 "교체" 기록 순으로 합니다.
8. 오너 보고: 대상 / 버전 / 실무자 / 판정 / 한 줄 이유(측정값 포함) 표, 검수한 이미지와 쓴 문서 경로, "다음 작업 추천" 질문 하나.

### 오너에게 묻는 것과 묻지 않는 것
- **묻지 않고 하고 나중에 보고**: 통과 결과 채택, 정본으로 옮기기, ★ 없는 수치의 v+1 재발행.
- **항상 묻기**: ★ 값 바꾸기, 정하지 않은 디자인 항목, 스타일 기준 변경, 정본 교체, 커밋.

### 상황별 예시

| 상황 | 이렇게 말하기 |
|---|---|
| 새로 들어온 게 있는지 보고 검수 | `검수 ㄱㄱ`, `검수할게 있나?`, `검수나 완료가 있어?` |
| 한 실무자 것만 | `실무자2 검수`, `/am-art:ad-review 실무자1` |
| 특정 완료보고 하나 | `피드백/<대상>/023_<이름>_v02_완료보고.md` (경로만 붙여 넣기) |
| 실무자 질문 처리 | `질문파일 보고 질문해봐`, `검수하고 질문해` |
| 다음 지시서 | `지시서 ㄱㄱ`, `다음 작업 추천` |
| 자리를 비울 때 계속 돌리기 | `/loop 5m /am-art:ad-auto` |
| 돌아와서 밀린 결정 처리 | `오너 대기 목록 하나씩 물어봐` |
| 규칙을 바꾸기 전 과거 문서로 시험 | `/am-art:ad-review 시험 _시험/1차 피드백/<대상>/012_<이름>_완료보고.md` |

### 자동 반복
- `/loop 5m /am-art:ad-auto` 는 바퀴마다 별도 하위 작업에서 `자동` 한 바퀴를 돌리고, 지금 대화에는 보고 표(새 문서가 없으면 `검수할 문서 없음` 한 줄)만 남깁니다. 검수 과정의 문서·이미지는 대화에 쌓이지 않아 오래 돌려도 대화가 거의 커지지 않습니다. 예전 줄 `/loop 5m /am-art:ad-review 자동` 도 돌지만 바퀴마다 문서·이미지가 대화에 쌓입니다.
- 하위 작업은 이 대화를 보지 못합니다. 대화로만 말한 목표(예: "각 20종")는 패키지 문서나 상태 대장에 적혀 있어야 완료 판정에 쓰입니다.
- `자동` 바퀴는 설정 사본과 상태 대장 끝부분만 먼저 보고, 확실히 새 문서가 없으면 패키지 문서를 다 읽지 않고 끝납니다. 새 문서가 있거나 애매하면 전부 읽습니다.
- `자동` 반복은 오너 목표(예: "원시·중세·근대 각 20종")의 대상이 모두 통과하고 옮겨지면 "완료 판정" 과 함께 `/loop` 을 멈춰도 된다고 알려 줍니다.
- `시험` 모드는 끝에 이번 실행이 쓴 것과 실제 과거 문서를 비교한 표(판정어, 재측정 여부, 양식 유지)를 보여 줍니다.

### 새 요청 (`새요청`)
오너가 스케치나 외부 이미지를 주며 실무자가 작업할 수 있게 준비해 달라고 할 때입니다.
1. 준 이미지를 모두 직접 열고, 대상·용도·모양·색·크기와 아직 모르는 점을 쉬운 말로 설명합니다. 지시서 용어는 괄호 안에 풀어 씁니다. 이해가 맞는지 한 번 확인받습니다.
2. 확인되면 03 양식 A 로 첫 지시서를 씁니다. 판단 기준과 허용 범위를 수치로 적어서 실무자가 묻거나 멈출 일을 줄입니다. 대상이 여럿이면 실무자 1·2 에게 나누거나 이미지 시트 한 장으로 요청합니다.
3. 새 대상의 피드백 폴더와 `_상태.md` 는 설정 사본 §2 대로 만들고, 둘 곳이 없으면 묻습니다.

| 상황 | 이렇게 말하기 |
|---|---|
| 스케치로 시작 | (이미지 첨부) `내가 그린 스케치야. 이거 코덱스가 작업할 수 있게 준비해줘` |
| 외부 참고 이미지로 시작 | (이미지 첨부) `이런 느낌의 방패 3종, 코덱스가 작업할 수 있게 준비해줘` |
| 이해했는지만 확인(파일을 쓰지 않음) | `이해했는지 대답부터 해줘`, `대답만 해줘` |

### 게임 투입본 (`게임투입`)
정본을 게임 파일에 바로 덮어쓸 수 있도록, 게임 파일 이름으로 된 축소 사본을 패키지 안에 만듭니다. **게임 폴더에는 아무것도 쓰지 않습니다.** 복사는 오너가 직접 합니다.
1. 이미 정본인 대상만 다룹니다. 통과했지만 아직 안 옮긴 대상은 먼저 옮기고, 통과 전인 대상은 빼고 그렇다고 알려 줍니다.
2. `gameRoot` 에서 같은 용도의 게임 파일을 찾습니다(이전 `게임투입/*/대응표.md` 와 설정 사본을 먼저 봄). 하나로 정해지지 않으면 후보를 보여 주고 묻습니다.
3. 규격은 설정 사본 값, 없으면 128px·투명 배경 유지입니다. Pillow 가 없으면 어느 환경에 설치할지 묻고, 답을 받은 뒤 설치합니다.
4. 결과물:
   - `<패키지>/게임투입/<YYYYMMDD-HHMM>/`: 게임 이름의 사본과 `대응표.md`(제작 이름 | 게임 이름 | 용도 | 게임 안 위치 | 백업 파일)
   - `<패키지>/백업/게임_<YYYYMMDD-HHMM>/`: 지금 게임 파일의 복사본(옮기거나 지우지 않음)
5. 보고 끝에 "이 폴더 파일을 게임 안 위치로 복사하면 덮어씌워집니다" 라고 알려 줍니다.

| 상황 | 이렇게 말하기 |
|---|---|
| 통과한 아이콘을 게임용으로 | `통과한 아이콘들 게임에 바로 덮어씌울수 있도록 이름 맞추고 128 사본 만들어줘` |
| 특정 대상만 | `/am-art:ad-review 게임투입` 뒤 대상을 고름 |

## am-art:ad-execute: 실무자 한 바퀴 (Codex)

**하는 일**: Codex 가 실무자로 한 바퀴를 돕니다.
공통 계약 읽기 → 환경·계정 확인 → 내 지시서 찾기 → 상태 대장에 `생성중` 표시 → 생성·후처리(imagegen 스킬에 맡김) → 자가검수 → 완료보고와 상태 대장 기록 → 승인 뒤 커밋 → 짧은 알림.

**하지 않는 일**: 디자인 결정, 검수 판정, 정본으로 옮기기(모두 AD 의 일), 승인 없는 커밋, push.

### 인자

| 인자 | 동작 |
|---|---|
| (없음) | 나에게 온 최신 지시서 |
| `실무자1` / `실무자2` | 내가 몇 번 실무자인지 정함 |
| `<지시서 경로>` | 그 지시서. FB 절과 함께 줄 수 있음(`FB §5 → 011 지시 실행`) |
| `대기 <N>분 [<M>시간]` | 대기 모드. M 을 안 주면 8시간 |
| `정지` | 지금 시도까지 저장하고 멈춤 |

### 알아 둘 점
- 시작할 때마다 패키지의 공통 계약 문서(`AGENTS.md`, 실무자 수칙, 역할 정의, 문서 템플릿, 설정 사본)를 다시 읽고 `공통 계약 읽음: …` 한 줄을 보여 줍니다. 대기 모드의 두 번째 바퀴부터는 내 지시서가 있는지 먼저 보고, 확실히 없으면 다시 읽지 않고 `지시서 대기` 로 끝냅니다(있거나 애매하면 전부 다시 읽음).
- 세션의 첫 생성 전에 로그인된 계정을 보여 주고 회사 계정이 맞는지 한 번 묻습니다. 아니면 생성하지 않습니다.
- 건너뛰는 지시서: 제목 아래 `⛔ 보류` 가 있는 것, 다른 실무자 배정, 이미 완료보고가 있는 대상, 다른 실무자가 먼저 `생성중` 을 쓴 대상, AD 가 아직 답하지 않은 내 질문이 걸린 대상. 남은 게 없으면 `지시서 대기` 한 줄로 끝납니다.
- 두 실무자가 같은 대상을 잡으면 상태 대장에 먼저 쓴 쪽이 가져가고, 늦은 쪽은 양보했다는 줄을 남기고 다른 지시서를 찾습니다.
- 다른 실무자나 AD 와는 피드백 채널의 파일로만 이야기합니다. 운영자에게 말을 전해 달라고 하지 않습니다.
- 시도 한도(설정 사본 §5)에 닿으면 멈추고 질문 문서(양식 D)를 씁니다. "거의 맞음" 은 완료가 아닙니다.

### 상황별 예시 (Codex 창에서)

| 상황 | 이렇게 말하기 |
|---|---|
| 처음 시작, 번호 정하기 | `너는 실무자 2번이야. 피드백 채널 최신 지시서대로 작업` |
| 최신 지시서 실행 | `지시서 ㄱㄱ`, `실무자1` |
| 특정 지시서 | `013 지시서를 실행`, 또는 `피드백/<대상>/013_<이름>_지시.md` 경로만 붙여 넣기 |
| FB 를 반영해 다시 작업 | `FB §5 → 011 지시 실행` |
| 하던 것 이어서 | `이어서 작업`, `계속 진행해` |
| 지시서를 다시 읽게 하기 | `지시서 다시 읽어` |
| 자리를 비울 때 기다리며 계속 | `실무자2번. 대기 10분 8시간` |
| 멈추기 | `정지` |

- 대기 모드는 지시서가 없거나 질문을 남기고 끝난 바퀴 뒤에 N분 쉬었다가 다시 찾습니다. 목표 대상의 완료보고가 모두 생기거나, `정지`, 환경 오류, 최대 시간 중 하나가 되면 무엇 때문에 멈췄는지 한 줄로 알리고 끝납니다.
- 대기 중에는 커밋 승인을 묻지 않고, 끝날 때 모든 바퀴의 바뀐 파일과 커밋 메시지 초안을 모아 한 번에 묻습니다.

## am-art:pipe-apply: 파치 → Spine → Unity 반영

**하는 일**: 정본 이미지를 등록된 반영 도구로 파치 → Spine 슬롯 → Unity 에 반영하고, **세 곳 모두 실제 파일로 확인한 표**를 보여 줍니다. 한 칸이라도 비면 "완료" 라고 하지 않습니다.

**하지 않는 일**: 이미지 생성·검수, 정본 결정, 업로드, 요청 없는 커밋, 도구가 없는 종류를 손으로 반영하기.

### 인자
- 종류: `무기`, `캐릭터`, `펫`
- 슬롯 번호: 여러 개 가능. 없으면 "작업된 것" = 상태 대장에 `통과` 나 `채택·이관` 이 있고 그 뒤 `교체완료` 가 없는 슬롯
- 범위: `파치만`, `스파인까지`, `유니티까지` (없으면 세 곳 모두)
- `점검`: 사전 점검과 세 곳 확인 표만. 파일을 바꾸지 않음

### 진행 순서
1. 대상 목록을 보여 주고 시작합니다.
2. 사전 점검:
   - Spine 저장소에 다른 세션이 고친 `.spine` 파일이나 `spine/images` 변경이 있으면 멈추고 묻습니다.
   - 테스트 카테고리 캐릭터는 Spine 에 넣지 않고 그렇다고 알려 줍니다.
   - 각 도구를 먼저 점검 모드로 돌려 바뀔 파일 목록을 받습니다.
3. 도구 설명에 "유니티까지 AD 전결" 이 있으면 바로 진행하고, 아니거나 정본 교체가 섞이면 한 번 묻습니다.
4. 반영하고, 범위가 Unity 까지면 마지막에 Unity 익스포트를 한 번 합니다.
5. 세 곳 확인 표: 파치(해시, 서버가 돌면 화면에서도 확인), Spine(슬롯 파일 해시), Unity(익스포트 점검과 아틀라스).
6. 상태 대장의 `교체완료` 줄을 확인합니다(없으면 직접 한 줄 추가).
7. 보고: 세 곳 표, 백업 폴더, 바뀐 파일, "되돌리려면 이 백업에서 복원", 그리고 "커밋할까요?" 한 질문.

### 상황별 예시

| 상황 | 이렇게 말하기 |
|---|---|
| 통과한 것 모두 반영 | `작업된게 있으면 파치에 적용해`, `파치·스파인·유니티 반영` |
| 특정 슬롯·범위만 | `무기 12 13 14 스파인까지만 반영해`, `/am-art:pipe-apply 무기 12 파치만` |
| Unity 익스포트만, 업로드 금지 | `스파인>유니티 익스포트. 업로드는 하지마` |
| 반영됐는지 확인만 | `무기 유니티 적용되어 있어?`, `/am-art:pipe-apply 무기 점검` |
| 승인해서 진행 | `게임 반영 승인`, `6종 스파인·파치 교체 승인` |
| 화면에 안 보일 때 | `파치에서 적용된게 안보여 확인해봐` |
| 되돌리기 | `방금 반영한거 되돌려줘` (복원할 백업 → 원래 위치 목록을 먼저 보여 주고 승인 뒤 복원) |

반영 도구가 없는 종류(배경, 보스, 아이콘 등)는 "반영 도구 없음" 으로만 보고합니다. 도구를 쓰려면 오너가 스크립트를 알려 주세요.

## am-art:log-compare: 이미지 비교 페이지

**하는 일**: 이미지 여러 장을 한 화면에서 비교하는 HTML 을 만듭니다. 섹션 → 줄 → 칸 구성이고, 칸 크기 조절, 눌러서 크게 보기, 칸마다 별표(최종본 표시)와 별표 목록 내보내기, 겹쳐 보기 켜고 끄기, 실제 크기(1:1) 보기, 섹션 탭이 있습니다.

| 모드 | 특징 | 결과 파일 |
|---|---|---|
| 로컬 보기 | 원본 파일을 가리켜 빠름. 칸을 누르면 원본을 열거나 경로를 복사 | `<outDir>/<페이지>.html` |
| 공유용 | 이미지를 HTML 안에 넣어 다른 사람에게 보낼 수 있음. Pillow 필요 | `<outDir>/<페이지>.share.html` |

- 표시 규칙(출력 폴더, 섹션 나누는 법, 줄당 칸 수, 게임 표시 크기 등)은 작업 저장소 맨 위의 `compare.json` 에 둡니다. 없으면 하나씩 묻고 만듭니다.
- 이미지 목록은 페이지마다 `<outDir>/<페이지>.manifest.json` 입니다. 기존 페이지에 추가하면 그 목록에만 더합니다. 없는 이미지 경로는 따로 알려 줍니다.

### 상황별 예시

| 상황 | 이렇게 말하기 |
|---|---|
| 새 비교 페이지 | `원시 무기 20종 비교용 html 만들어`, `한눈에 볼수 있게 모아보기 페이지 만들어줘` |
| 기존 페이지에 추가 | `<페이지 경로> 여기 넣어줘 이번 v03 결과들`, `<페이지 경로> 적용해줘` |
| 다른 사람에게 보내기 | `다른사람에게 보낼수 있게 만들어줘`, `공유용으로 만들어줘` |
| 별표한 최종본 정리 | `별표한거 최종본 뭐야` |

- 별표는 보는 사람의 브라우저에만 저장됩니다. "별표한거 최종본 뭐야" 라고 하면 페이지의 "별표 목록 내보내기" 를 눌러 나온 목록을 붙여 넣어 달라고 합니다.
- 공유용이 20MB 를 넘으면 줄이는 방법(긴 변 줄이기, 품질 낮추기, 섹션별로 나누기)을 묻습니다.
- 공유용 HTML 은 저장소에 올리지 않습니다. git 이 무시하지 않는 위치에 만들어졌으면 알려 줍니다.
- 이 생성기가 만들지 않은(손으로 만든) 페이지는 덮어쓰지 않고, 같은 화면의 새 파일을 만들어 나란히 비교하게 합니다. 원본 이미지는 바꾸지 않습니다.

## am-art:log-resume: 기억·학습·회상

**세 가지 모드**를 말에서 골라 씁니다.

### 기억: 알맞은 파일에 기록

| 무엇 | 어디에 |
|---|---|
| 진행 지점("어디까지 했다", 다음 할 일) | AD 패키지는 대상의 `_상태.md` 에 한 줄. 다른 프로젝트는 그 프로젝트의 상태 대장(없으면 어디 만들지 물음) |
| 제작 규칙과 수치(발 위치 고정, 최소 선 두께, 디자인 이름 등) | AD 패키지는 설정 사본 §5(규격)나 §7(교훈). Spine 저장소는 맞는 규칙 파일(`prompts/_rule_*.txt` 등) |
| 자료 위치 같은 사실(DB 경로, Unity 경로) | 그 프로젝트의 Claude Code 메모리 |

- 쓰기 전에 "이 파일에 이 내용을 추가합니다" 를 파일과 함께 보여 줍니다. 같은 내용이 이미 있으면 그 줄을 바꾸고 전 → 후로 보여 줍니다.
- 이미지 생성 지시는 Claude 메모리에 넣지 않습니다. 패키지 규칙 문서는 고치지 않습니다.

### 학습: 오너 수정본을 수치로 재서 규칙으로
1. 원본(생성 결과)과 오너 수정본을 찾습니다. 말해 주지 않으면 최근 바뀐 파일에서 짐작하고 확인받습니다.
2. 차이를 스크립트로 잽니다: 위치(dx, dy), 크기, 선 두께(최솟값·중앙값), 색.
3. 측정표를 보여 주고 "이 수치를 규칙으로 기록할까요?" 를 묻습니다. 승인하면 위 표의 규칙 자리에 씁니다.
4. "학습 내용 파기" 는 지울 줄(파일과 줄)을 먼저 보여 주고 승인 뒤에만 지웁니다.

### 회상: 기록을 찾아 답하기
찾는 순서: 지금 폴더 상태 대장의 최근 줄 → `git log`·`git status`(커밋 안 된 것은 진행 중) → 피드백 채널의 최신 문서 → 오너가 했던 말(Claude Code 입력 기록) → 세션 기록 → 실무자 쪽 Codex 기록.
답은 **마지막 완료 / 진행 중 / 오너 결정 대기 / 다음 추천** 으로 나누고 근거 파일을 붙입니다. "뭐라고 명령했어" 에는 당시 말을 날짜와 함께 그대로 인용합니다. 못 찾으면 "기록 없음" 이라고 하고 추측하지 않습니다.

### 상황별 예시

| 상황 | 이렇게 말하기 |
|---|---|
| 지금 상태 남기기 | `지금 작업 기억해둬`, `현재작업을 기억해둬`, `추가작업도 기억해둬` |
| 제작 방식 남기기 | `현재 캐릭터 제작 방식 기억해둬` |
| 내가 고친 것을 규칙으로 | `내가 수정한거 학습해`, `36,37 몸 내부 라인 두께를 수정했어. 측정해서 최소값으로 기억해둬` |
| 학습 확인·삭제 | `학습해 뒀어?`, `학습 내용 파기` |
| 어디까지 했는지 | `어디까지 했어`, `어제 작업한 캐릭터 어디까지 했어`, `이어서 작업 시작` |
| 예전 지시 찾기 | `활 무기를 2개씩 만드는데 이전엔 뭐라고 명령했어?`, `그때 내가 뭐라고 명령했어` |
| 예전 값 찾기 | `이전에 만든 6자리 코드 기억해?` |

외부 자료를 배우는 일(예: "디지몬 카드 학습해")은 이 스킬이 하지 않습니다.

## am-util:git-sync: 아티스트용 git 도우미 (Claude Code)

**누구를 위한 스킬인가**: git 을 잘 모르고 주로 Fork 를 쓰는 아티스트가 Unity 아트 저장소에서 씁니다.
**모드**: `상태`(기본), `커밋`, `올리기`, `설명`. 말로는 불리지 않는 명령이라 `/am-util:git-sync <모드>` 를 직접 입력합니다. 인자가 없으면 이 대화 내용에서 고르고, 애매하면 묻습니다.

### 늘 지키는 것
- "대답만", "의견만" 이면 아무 명령도 실행하지 않고 답만 합니다.
- git 명령을 실행할 때마다 무엇을 했는지 쉬운 말 한 줄로 알려 줍니다.
- 파일을 한꺼번에 담지 않습니다(`git add -A`, `git add .` 금지). 훅 건너뛰기와 강제 push 는 하지 않습니다.
- 되돌리면 사라지는 명령(작업 내용 버리기, 파일 정리, 브랜치 지우기 등)은 무엇이 사라지는지 먼저 설명하고 승인 뒤에만 합니다.

### 상태
- 최신 원격을 받아 온 뒤(실패하면 마지막으로 받은 기준이라고 알림) 지금 브랜치, 원격 기본 브랜치보다 몇 개 앞섰는지/뒤처졌는지, 로컬 기본 브랜치가 원격과 갈라졌는지 알려 줍니다.
- 바뀐 파일을 세 묶음으로 나눕니다:
  - **저절로 바뀐 것 후보**: Unity 가 흔히 바꾸는 것(`Packages/`, 내용 변화 없는 `.meta`, `ProjectSettings/` 의 자동 항목, `.omc/`, 녹화·캡처 폴더, 병합 찌꺼기 파일) + 이 저장소에 등록한 패턴(`git-sync.json`). 맞아도 후보일 뿐이라 내용을 보고 이유를 짧게 답니다.
  - **내 작업**: 이 대화에서 바꾼 파일과 아티스트가 이름을 댄 파일.
  - **모르는 것**: 나머지.

### 커밋
1. 내 작업 목록을 보여 줍니다. 다른 사람(개발자)이 최근에 고친 파일이면 알리고 넣을지 묻습니다.
2. 이미 스테이징된 다른 파일이 있으면 알리고 뺄지 묻습니다.
3. 파일을 하나씩 스테이징하고 최종 목록을 보여 줍니다.
4. 아티스트의 최근 커밋 형식에 맞춘 한 줄 메시지를 제안하고 "제가 할까요, 직접 하실래요?"(커밋은 제가 / Fork 에서 직접)를 묻습니다. 훅이 막으면 이유를 쉬운 말로 설명합니다.
5. 저절로 바뀐 것은 되돌릴지 묻습니다(무엇이 사라지는지 설명 뒤 승인).
6. 아티스트가 "저절로 바뀐 거야" 라고 확인한 파일은 패턴 하나를 제안하고, 승인하면 이 저장소 목록에 더해 다음부터 자동으로 후보에 넣습니다. 잘못 넣은 패턴은 뺄 수 있습니다.

### 올리기
- 이 대화에서 push 를 요청했을 때만 합니다. 커밋 요청은 push 허락이 아닙니다.
- 나갈 커밋과 파일을 먼저 보여 줍니다. 원격 브랜치가 없으면 새로 만든다고 알리고 묻습니다.
- **코드 파일**(`.cs`, `.asmdef`, `.dll`, `.shader`, `.hlsl`, `.js`, `.py` 등)이 섞여 있으면 push 하지 않고 그 파일을 알려 준 뒤 멈춥니다.
- 거부되면 받아 오거나 합치지 않고, 원격에 새 커밋이 있다고 쉽게 설명하고 am-util:update-branch 를 안내합니다.

### 최신화와 마스터 반영
- git-sync 가 직접 하지 않고 am-util 명령을 입력하라고 안내합니다(말로 불리지 않는 명령이라 사람이 입력해야 함).
- "마스터에 merge" 는 am-util:land 가 push 까지 하므로, 안내하기 전에 코드 파일 검사를 먼저 하고 코드가 있으면 멈춥니다.
- merge 뒤 돌아오면 양쪽에서 바뀐 파일을 골라 기본 브랜치 쪽 최근 변경이 사라지지 않았는지 확인합니다. 사라진 게 있으면 어느 파일의 무엇인지 알려 주고, 직접 고치지는 않습니다.

### 설명
충돌, 리베이스 오류, "기본 브랜치와 원격이 갈라짐" 상태를 쉬운 말로 설명합니다(무슨 일이 있었고 지금 무엇이 안전한지). 선택지는 작업 중단(추천), am-util:update-branch 로 최신화, 개발자에게 묻기입니다.

### 상황별 예시

| 상황 | 입력 |
|---|---|
| 지금 상태 | `/am-util:git-sync 상태` |
| 갑자기 변경이 많아졌을 때 | `/am-util:git-sync 상태` → 같은 대화에서 `로컬 체인지가 갑자기 엄청 많이 생겼는데` |
| 내 작업만 커밋 | `/am-util:git-sync 커밋` |
| 자동 변경 등록 | 같은 대화에서 `그 Packages 쪽은 저절로 바뀐 거야` |
| 원격에 올리기 | `/am-util:git-sync 올리기` |
| 오류 메시지 해석 | `/am-util:git-sync 설명` + 메시지 붙여 넣기 |
| 최신화 | 같은 대화에서 `최신화해줘` → 안내대로 `/am-util:update-branch` 입력 |
| 마스터 반영 | 같은 대화에서 `마스터에 merge 해줘` → 코드 검사 뒤 안내대로 `/am-util:land` 입력 → 끝나고 `merge 했어, 확인해줘` |
| 실행 없이 의견만 | 같은 대화에서 `대답만 해줘. 지금 올려도 돼?` |

## am-util:update-branch: 최신 기준 브랜치 위로 옮기기

**하는 일**: 지금 브랜치의 커밋을 최신 기준 브랜치(생략하면 원격 기본 브랜치, 예: `master`) 맨 끝 뒤로 옮깁니다(rebase). **push 는 하지 않습니다.**

- 로컬 기준 브랜치를 원격과 똑같이 맞춥니다. 로컬에만 있던 커밋이 빠지면 그 해시와 목록을 알려 줘서 되살릴 수 있습니다.
- 커밋하지 않은 파일은 임시 커밋("WIP 임시")에 담았다가 끝나면 스테이징 안 된 상태로 그대로 돌려줍니다.
- 옮기기 전 자리에 `backup/<브랜치>-<시각>` 백업 브랜치를 남깁니다. 임시 커밋이 있었다면 백업이 그것을 가리키므로 **백업 브랜치는 push 하거나 합치지 마세요.**
- 기준 브랜치(master) 위에서 부르면 새 브랜치 이름을 제안하고 물어서 만든 뒤 진행합니다.
- Unity 프로젝트여도 에디터를 닫을 필요가 없습니다. 끝날 때까지 에디터 창으로 전환하지 말고, 끝난 뒤 바뀐 씬을 다시 불러올지 물으면 다시 불러오기를 고르세요.
- 충돌이 나면 파일마다 양쪽이 무엇을 바꿨는지 쉬운 말로 보여 주고 중단할지 맡길지 묻습니다. 글자 파일은 양쪽 의도를 살려 합치고, 씬·프리팹·바이너리는 한쪽을 통째로 고릅니다. 자신 없으면 중단하고 원래대로 돌립니다.
- 이미 원격에 올린 브랜치였다면 원격 사본과 달라졌다고 알립니다. 원격을 고치려면 강제 push 가 필요한데, 이 스킬은 하지 않습니다.

### 백업으로 되돌리기
백업 브랜치 이름을 인자로 주거나, 실행 뒤 같은 대화에서 되돌려 달라고 하면 원래 브랜치를 실행 전 자리로 돌리고 그때의 작업 중 파일까지 돌려줍니다. 되돌리기 직전 상태도 새 `backup/` 브랜치로 남기므로 되돌리기도 다시 되돌릴 수 있습니다. 백업 브랜치는 지우지 않습니다.

### 상황별 예시

| 상황 | 입력 |
|---|---|
| 원격 기본 브랜치 기준으로 최신화 | `/am-util:update-branch` |
| 다른 기준 브랜치 | `/am-util:update-branch develop` |
| master 위에서 작업하다가 브랜치로 옮기기 | master 에서 `/am-util:update-branch` → 새 브랜치 이름 질문에 답 |
| 실행 전으로 되돌리기 | `/am-util:update-branch backup/<브랜치>-<시각>`, 또는 같은 대화에서 `방금 거 백업으로 되돌려줘` |

끝나면 확인할 것: 내 커밋이 기준 브랜치 끝 바로 뒤에 있는지, 작업 중 파일이 돌아왔는지, 빌드와 플레이. 큰 파일(LFS)이 비어 보이면 따로 받아 달라고 하세요.

## am-util:land: 대상 브랜치에 합쳐 push

**하는 일**: 지금 브랜치를 대상 브랜치(생략하면 원격 기본 브랜치)에 합쳐 원격에 push 하고, 마지막에 지금 브랜치를 합친 커밋으로 옮깁니다.

- 앞으로 감기만 하면 되면 그대로, 갈라졌으면 `.am/` 아래 임시 작업 폴더에서 merge 커밋을 만듭니다. 마지막 단계 전까지 지금 폴더의 파일은 건드리지 않습니다.
- 충돌이 나면 파일마다 양쪽 변경을 설명하고 중단할지 맡길지 묻습니다(씬·프리팹·바이너리는 한쪽을 통째로).
- 커밋하지 않은 변경은 push 에 들어가지 않고 그대로 남습니다. 합친 결과와 겹치면 지금 브랜치를 옮기지 않고 겹치는 파일을 알려 줍니다. 이미 성공한 push 는 그대로 둡니다.
- 로컬 대상 브랜치는 원격에 맞춥니다. 로컬에만 있던 커밋이 빠지면 해시와 목록을 알려 줍니다.
- push 가 거부되면 강제로 밀지 않고 원격에 새 커밋이 있다고 알립니다. 지금 브랜치 자체는 push 하지 않습니다.
- Unity 프로젝트여도 에디터를 닫을 필요가 없습니다. 끝날 때까지 에디터 창으로 전환하지 말고, 끝난 뒤 바뀐 씬을 다시 불러올지 물으면 다시 불러오기를 고르세요.
- **코드 파일 검사를 하지 않고 push 합니다.** 아티스트는 git-sync 에 먼저 "마스터에 merge 해줘" 라고 해서 검사를 받은 뒤 입력하세요.

### 상황별 예시

| 상황 | 입력 |
|---|---|
| 원격 기본 브랜치에 반영 | `/am-util:land` |
| 특정 브랜치에 반영 | `/am-util:land master` |
| 겹쳐서 옮기지 못했다고 할 때 | 겹친 변경을 커밋하거나 치운 뒤 `/am-util:land` 다시 입력 |

## 자주 묻는 것

- **스킬이 안 불려요.** am-util 세 명령은 말로 불리지 않으니 `/am-util:…` 를 직접 입력하세요. ad-review 와 ad-execute 는 반대쪽 도구에서 불리면 "다른 도구용" 이라는 한 줄만 말하고 멈춥니다.
- **경로를 계속 물어요.** 처음 한 번만 묻고 `art.json` 에 저장합니다. 계속 묻는다면 저장이 실패한 것이니 스킬이 보여 준 오류 줄을 확인하세요.
- **`검수할 문서 없음` 만 나와요.** 실무자가 완료보고를 아직 쓰지 않았거나, 이미 검수한 문서뿐입니다. 정상입니다.
- **`지시서 대기` 만 나와요.** 나에게 배정된 실행할 지시서가 없거나, 모두 보류·다른 실무자 배정·내 질문의 답 대기 상태입니다.
- **커밋하면 바로 원격에 올라가나요?** 아니요. push 는 `/am-util:git-sync 올리기` 나 am-util:land 를 입력할 때만 합니다.
- **am-art 의 git-sync 가 없어요.** am-art 0.1.4 부터 git-sync 는 am-util 에 있고, 0.1.5 에서 am-art 의 옛 안내 자리도 없앴습니다. `/am-util:git-sync` 를 입력하세요. `/am-util` 까지 쳤을 때 목록에 없으면 `/plugin marketplace update am-workflow` 뒤 am-util 을 설치(`/plugin install am-util@am-workflow`)하거나 업데이트(`/plugin update am-util@am-workflow`)하고 Claude Code 를 다시 시작하세요. 전에 등록한 "저절로 바뀌는 파일" 목록은 그대로 이어 씁니다.
- **새 버전이 Codex 에 안 보여요.** Codex 는 GitHub 의 main 에서 받으므로 `codex plugin remove am-art@am-workflow` 뒤 `codex plugin add am-art@am-workflow` 로 다시 설치하세요.
