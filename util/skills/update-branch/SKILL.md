## Working with the user
- Reply in the user's language. Lead with a one-line conclusion, then what changes in terms the user sees (screen, behavior, data), then what the user needs to do and the next step.
- Keep file paths, line numbers and internal labels in the files you write, not in chat. Use plain words that fit the reader; avoid heavy analogies.
- Ask only what only the user can decide: what they will see or feel, what is in or out of scope, and choices that are hard to undo. Ask at most 3 questions at a time.
- Every other technical choice is settled by a second opinion, not by your own recommendation. A technical choice is a design or implementation decision with two or more workable options that differ in structure, behavior or cost; where only one option is sensible, just take it.
  1. Settle your own pick first and keep it out of the brief.
  2. Write every pending choice in one brief: the goal, the user's decisions and other fixed constraints, questions still waiting for the user's answer, the paths involved, and each choice with its options in neutral wording.
  3. Codex, in Claude Code only: save the brief as a new file `opinion-<round>.md` under `.am/` (in the plan's folder when there is one; a new `.am/` folder also gets a `.gitignore` containing `*` unless `git check-ignore -q .am` succeeds) and, if `${CLAUDE_PLUGIN_ROOT}/scripts/codex-opinion.mjs` exists, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/codex-opinion.mjs" <brief file>` from the repository root with a 10-minute timeout. It prints Codex's answer to the brief; exit code 2 means Codex is not installed. Then send the brief to the am:second-opinion subagent; when Codex is not installed (exit code 2), send it at once to two of them, Claude 1 and Claude 2, each Agent call's prompt adding one line that names which of the two it is. If the first line of the script's output is `Claude reviewer: model <model>, effort <effort> …`, pass that model and effort as the Agent call's `model` and `effort`; otherwise do not override the ones pinned in its definition (both calls when there are two).
     Peer sessions instead of the subagent: in Claude Code with the ListAgents and SendMessage tools, only when a person is in this session to answer (not in a subagent, not while running without stops, not when your instructions say no human is present), each Claude reviewer is another open session. Run `claude agents --json` (2-minute timeout; if it fails, use the subagent): candidates are its rows with `kind` `interactive`, `status` `idle` (not `waiting`, which can be a pending prompt) and `cwd` equal to the repository root (ignoring case on Windows), newest `startedAt` first; take one per Claude reviewer and address it by its `name` (with the ref ListAgents shows when two sessions share it). If there are too few, give a decision card asking the user to open that many new Claude Code sessions in this repository and leave them idle, and wait for the answer; after a yes, list again and go on, after a no, use the subagent. Once per brief folder, save the text of `${CLAUDE_PLUGIN_ROOT}/agents/second-opinion.md` (else `${CLAUDE_PLUGIN_ROOT}/scripts/second-opinion.md`; with neither, use the subagent) without its frontmatter as `reviewer.md` beside the brief. Send each session one message with `notify_when_idle`, its first line saying it is an am second-opinion request, giving the absolute paths of the repository root, `reviewer.md` and the brief, and, with two, which of Claude 1 and Claude 2 it is; then wait for the replies, ending your turn while one is missing. Later rounds go to the same sessions. One that answers it runs in another folder is replaced by the next candidate; one whose message is refused, or whose idle notice comes without an answer, has failed. The `Claude reviewer:` line does not apply to sessions. Codex session instead of a new `codex exec`: under the same person condition (the tools are not needed), run the script with `--peer` after the brief file, and an idle Codex session open in this repository answers. Exit code 3 means there is none: give a decision card asking the user to open a Codex session in this repository and leave it idle, saying that the request and the answer stay in that session's history and run with its permissions (one card together with the Claude sessions when those are also too few), and wait for the answer; after a yes, run it again with `--peer`, after a no or a second exit code 3, leave `--peer` out until this task ends. Later rounds pass `--peer=<id>` with the id from the previous run's `Codex session: <id>` line, or no `--peer` when that line was missing.
  4. With both answers, send each choice they split on back to both, for at most 2 more rounds: a new brief with the original brief's content for those choices plus both picks and reasons from the last round, labelled Claude and Codex (Claude 1 and Claude 2 without Codex, each told again which one it is). A choice still split after that goes to the user as a decision card (rules below) that gives both picks and reasons. If one reviewer fails, in any round, the other's answer stands.
  5. Apply the agreed picks, not yours. A user decision always wins over a pick.
  6. List each under "Defaults applied": choice - one-line reason (second opinion), written (second opinion, Codex agreed) when Codex and Claude agreed or (second opinion, Claude reviewers agreed) when Claude 1 and Claude 2 agreed, and naming a reviewer that failed, adding your own pick when it differed; keep these marks in English in a plan of any language.
  7. Reopen a settled choice only when a user decision, including one given later, conflicts with it, a fact the brief left out changes it, or it proves unworkable (a failed check or a review finding). Send that choice back through steps 2-4 with the new fact, never to the user as a question unless the reviewers stay split, and update its line; do not swap in your own pick.
  If neither reviewer can answer (a tool without the subagent, or errors), apply your own pick and mark the line (no second opinion).
- Explain every question as a decision card first, written for someone who has seen neither this conversation nor the code:
  1. What is being decided, in one sentence, with no code names, file names or internal IDs.
  2. Why it must be decided now: how things are today and what stays blocked without an answer.
  3. For each option (2-4, your recommendation first): what the user will see or experience if they pick it, and its cost.
  4. Your recommendation and the one-sentence reason.
  5. Whether it is easy to change later or hard to undo.
  Before asking, check that a reader holding only the card could choose; if not, rewrite it. Put the card in the chat, then ask with a structured question tool if one exists (each option's description says what changes; for a screen decision, add a small text mockup as the option preview), otherwise as numbered options.
- Never edit or revert changes you did not make (the user's or another session's). Mention them only if they block the work.
- Refer to other am skills by name, e.g. "the am:check skill"; the slash or $ prefix differs per tool.

## Steps
Run every git command from the repository root, one per call, and never `cd`. Never push (not even forced), never run a commit command (step 4 makes the temporary commit with plumbing, so no commit gate runs on it), never stash, never hard-reset, and never touch another worktree. Once step 4 has made a temporary commit, every outcome (success, abort or stop) goes through step 7 before the reply.
1. Start: the current branch is `git symbolic-ref --short HEAD`; if that fails (detached HEAD), stop and ask the user to check out a branch. Stop if `git remote get-url origin` fails. Base: the argument; without one, `git symbolic-ref --short refs/remotes/origin/HEAD` minus its `origin/` prefix; if that fails, the `ref: refs/heads/<name>` line of `git ls-remote --symref origin HEAD`; with neither, ask for the base branch. Stop if `git rev-parse --git-path <name>` exists for any of `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply` (an operation in progress). If `ProjectSettings/ProjectVersion.txt` exists (a Unity project), tell the user in one line, without waiting for an answer, that the Unity editor may stay open but its window must not be brought to the front until this run ends (the rebase changes files in this folder and can pause on conflict questions, and the editor would reimport them mid-run).
2. New branch, only when the current branch is the base: ask for a new branch name and suggest one. It must pass `git check-ref-format --branch <name>`, and `git rev-parse --verify --quiet refs/heads/<name>` must fail; otherwise ask again. Then `git switch -c <name>`: the uncommitted files and the local commits come along. From here `<branch>` is the current branch.
3. Prepare 1, the latest base: `git fetch origin refs/heads/<base>`; stop if `git rev-parse --verify --quiet refs/remotes/origin/<base>` then fails, else note its hash as `<onto>`. Local base: if `git rev-parse --verify --quiet refs/heads/<base>` fails, run `git branch <base> <onto>`, then `git branch --set-upstream-to=origin/<base> <base>`. If it exists and differs from `<onto>`, note its old tip hash and `git log --oneline <onto>..<base>` (commits only on the local base; they leave it, the user's decision), then `git branch -f <base> origin/<base>`: the same result as a hard reset to the remote, without a checkout. If git refuses because another worktree has the base checked out, go on (the user's decision): note that folder (the `worktree` line of the entry with `branch refs/heads/<base>` in `git worktree list --porcelain`), leave the local base as it is and use `<onto>` from here.
4. Prepare 2, the uncommitted files: if `git status --porcelain --untracked-files=all` is empty, skip this step. Otherwise note `git rev-parse HEAD` as `<old>` and the time now as `<ts>` (YYYYMMDD-HHMMSS; step 5 uses the same one), then run `git add -A`, `git write-tree` (prints `<tree>`), `git commit-tree <tree> -p <old> -m "WIP 임시 (am-util:update-branch <ts>)"` (this exact message is `<wip-msg>`, the printed hash `<wip>`; write that hash in the chat on a line of its own) and `git update-ref -m "<wip-msg>" HEAD <wip> <old>` (it fails if HEAD moved meanwhile). If any of these fails, run `git reset --mixed` (the files stay, only the staging is undone) and stop.
5. Backup: `git branch backup/<branch>-<ts> HEAD` (`<ts>` from step 4, or the time now when step 4 was skipped; if the name exists, add `-2`, `-3` and so on; it gets no upstream). By the user's decision it points at HEAD now: the temporary commit when step 4 made one, else the last real commit. Note whether step 4 made a temporary commit (steps 7 and 8 use it).
6. Rebase: `git -c core.editor=true -c rebase.updateRefs=false rebase <onto>` (a user's `rebase.updateRefs` would move the backup along).
   - On conflicts (`git diff --name-only --diff-filter=U`), show for each file in plain words what each side changed, and ask the user whether to abort or to let you resolve them (and which side to keep where they collide).
   - During a rebase `--ours` is the base side and `--theirs` the user's commit.
   - A text file: edit it so the intent of both sides survives.
   - A scene, prefab or binary file: take it whole from one side with `git checkout --ours -- <path>` or `git checkout --theirs -- <path>`.
   - Then `git add -- <path>`, and after the last file `git -c core.editor=true rebase --continue`; handle each next conflict the same way.
   - Never guess: if you are not confident, the user chooses to abort, or a rebase command fails for another reason, run `git rebase --abort` (the branch returns to where it was, temporary commit included). If git's message says a file is in use or access is denied, add to the reply that the Unity editor or another program may be holding that file, so close it and run this skill again; if the abort fails too, report git's output and `git status --porcelain` and do not say the branch was returned.
7. Restore, only when step 4 made a temporary commit: if `git log -1 --format=%s HEAD` equals `<wip-msg>`, run `git reset --mixed HEAD~1` (the files come back, all unstaged). Otherwise look for `<wip-msg>` in `git log --format="%H %s" <onto>..HEAD`: absent means the rebase dropped it as empty because the base already holds the same changes, so there is nothing to restore; found below the top, remove nothing, stop and report it with its hash.
8. Reply:
   - The conclusion in one line.
   - The new branch, if step 2 made one.
   - The local base: old tip → new tip and the commits that left it, with hashes, so they can be recovered; created; or not moved, and the folder that has it checked out.
   - The backup branch's name; going back to the backup (call this skill with the backup's name, or ask in this conversation) runs "Back to the backup" below, which returns the branch and the uncommitted files of that moment.
   - When step 4 made a temporary commit: the backup's top is that "WIP 임시" commit, so the backup must never be pushed or merged.
   - `git log --oneline <onto>..HEAD`.
   - Each conflict and how it was resolved, or that the rebase was aborted.
   - The number of restored uncommitted files (`git status --porcelain`), all unstaged.
   - If `git rev-parse --abbrev-ref --symbolic-full-name @{u}` succeeds and is not `origin/<base>`: the branch now differs from its remote copy, so updating it there needs a forced push, which this skill does not do.
   - What to check: your commits right after the base's tip, the uncommitted files back, build and play.
   - For a Unity project, one line: back in the editor it reimports the changed files, and if it asks whether to reload a scene changed on disk, choose reload (keeping and saving the editor's copy would overwrite the updated file); if large (LFS) files look empty, ask for them separately.

## Back to the backup
When the argument starts with `backup/`, or the user asks after a run to go back to the backup, do this instead of the Steps; `<backup>` is that branch, named `backup/<branch>-<ts>` (perhaps with a `-2` suffix).
1. Check: `git rev-parse --verify --quiet refs/heads/<backup>` must succeed and the current branch (`git symbolic-ref --short HEAD`) must be the `<branch>` of that name; otherwise stop. Check for an operation in progress, and give the one-line Unity notice, as in the Steps' step 1.
2. Save the present state: the Steps' step 4 as written (a new `<ts>` and `<wip-msg>`), then the Steps' step 5 as written, a new `backup/<branch>-<ts>` at HEAD.
3. Move: `git switch --no-overwrite-ignore -C <branch> <backup>` (the working tree is clean after the save, and ignored files are kept). If it fails, undo the save's temporary commit as the Steps' step 7 does (only when the top's subject equals the new `<wip-msg>`) and stop, naming the new backup (never push or merge it when its top is a "WIP 임시" commit); if git's message says a file is in use or access is denied, add that the Unity editor or another program may be holding it, so close it and run this skill again.
4. Restore: if `git log -1 --format=%s HEAD` equals `WIP 임시 (am-util:update-branch <ts>)` with the `<ts>` of the `<backup>` name, run `git reset --mixed HEAD~1` (the uncommitted files of that run come back, all unstaged). If the top's subject is another `WIP 임시 (am-util:update-branch …)` (a backup from an older version, whose two times may differ), remove nothing and report its hash: the uncommitted files of that run are inside it, so the branch must not be pushed or merged before the user undoes it.
5. Reply: the commit `<branch>` is on again; the number of uncommitted files back (`git status --porcelain`), all unstaged; the new backup's name, which holds the state just before going back (when its top is a "WIP 임시" commit, never push or merge it), and that calling this skill with that name goes back again; that both backups remain and deleting them is the user's choice; if `git rev-parse --abbrev-ref --symbolic-full-name @{u}` succeeds, that the branch may now differ from its remote copy; for a Unity project, the reload line of the Steps' step 8.
