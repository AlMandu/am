## Working with the user
- Reply in the user's language. Lead with a one-line conclusion, then what changes in terms the user sees (screen, behavior, data), then what the user needs to do and the next step.
- Keep file paths, line numbers and internal labels in the files you write, not in chat. Use plain words that fit the reader; avoid heavy analogies.
- Ask only what only the user can decide: what they will see or feel, what is in or out of scope, and choices that are hard to undo. Ask at most 3 questions at a time.
- Every other technical choice is settled by a second opinion, not by your own recommendation. A technical choice is a design or implementation decision with two or more workable options that differ in structure, behavior or cost; where only one option is sensible, just take it.
  1. Settle your own pick first and keep it out of the brief.
  2. Write every pending choice in one brief: the goal, the user's decisions and other fixed constraints, questions still waiting for the user's answer, the paths involved, and each choice with its options in neutral wording.
  3. Codex, in Claude Code only: save the brief as a new file `opinion-<round>.md` under `.am/` (in the plan's folder when there is one; a new `.am/` folder also gets a `.gitignore` containing `*` unless `git check-ignore -q .am` succeeds) and, if `${CLAUDE_PLUGIN_ROOT}/scripts/codex-opinion.mjs` exists, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/codex-opinion.mjs" <brief file>` from the repository root with a 10-minute timeout. It prints Codex's answer to the brief; exit code 2 means Codex is not installed. Then send the brief to the am:second-opinion subagent; when Codex is not installed (exit code 2), send it at once to two of them, Claude 1 and Claude 2, each Agent call's prompt adding one line that names which of the two it is. If the first line of the script's output is `Claude reviewer: model <model>, effort <effort> …`, pass that model and effort as the Agent call's `model` and `effort`; otherwise do not override the ones pinned in its definition (both calls when there are two).
     Peer sessions instead of the subagent: in Claude Code with the ListAgents and SendMessage tools, only when a person is in this session to answer (not in a subagent, not while running without stops, not when your instructions say no human is present), each Claude reviewer is another open session. Run `claude agents --json` (2-minute timeout; if it fails, use the subagent): candidates are its rows with `kind` `interactive`, `status` `idle` (not `waiting`, which can be a pending prompt) and `cwd` equal to the repository root (ignoring case on Windows), newest `startedAt` first; take one per Claude reviewer and address it by its `name` (with the ref ListAgents shows when two sessions share it). If there are too few, give a decision card asking the user to open that many new Claude Code sessions in this repository and leave them idle, and wait for the answer; after a yes, list again and go on, after a no, use the subagent. Once per brief folder, save the text of `${CLAUDE_PLUGIN_ROOT}/agents/second-opinion.md` (else `${CLAUDE_PLUGIN_ROOT}/scripts/second-opinion.md`; with neither, use the subagent) without its frontmatter as `reviewer.md` beside the brief. Send each session one message with `notify_when_idle`, its first line saying it is an am second-opinion request, giving the absolute paths of the repository root, `reviewer.md` and the brief, and, with two, which of Claude 1 and Claude 2 it is; then wait for the replies, ending your turn while one is missing. Later rounds go to the same sessions. Codex session instead of a new `codex exec`: under the same person condition (the tools are not needed), run the script with `--peer` after the brief file, and an idle Codex session open in this repository answers. Exit code 3 means there is none: give a decision card asking the user to open a Codex session in this repository and leave it idle, saying that the request and the answer stay in that session's history and run with its permissions (one card together with the Claude sessions when those are also too few), and wait for the answer; after a yes, run it again with `--peer`, after a no or a second exit code 3, leave `--peer` out until this task ends. Later rounds pass `--peer=<id>` with the id from the previous run's `Codex session: <id>` line, or no `--peer` when that line was missing.
  4. With both answers, send each choice they split on back to both, for at most 2 more rounds: a new brief with the original brief's content for those choices plus both picks and reasons from the last round, labelled Claude and Codex (Claude 1 and Claude 2 without Codex, each told again which one it is). A choice still split after that goes to the user as a decision card (rules below) that gives both picks and reasons. If one reviewer fails, in any round, the other's answer stands.
  5. Apply the agreed picks, not yours. A user decision always wins over a pick.
  6. List each under "Defaults applied": choice - one-line reason (second opinion), written (second opinion, Codex agreed) when Codex and Claude agreed or (second opinion, Claude reviewers agreed) when Claude 1 and Claude 2 agreed, and naming a reviewer that failed, adding your own pick when it differed; keep these marks in English in a plan of any language.
  7. Reopen a settled choice only when a user decision, including one given later, conflicts with it, a fact the brief left out changes it, or it proves unworkable (a failed check or a review finding). Send that choice back through steps 2-4 with the new fact, never to the user as a question unless the reviewers stay split, and update its line; do not swap in your own pick.
  If neither reviewer can answer (a tool without the subagent, or errors), apply your own pick and mark the line (no second opinion).

## Steps
Run every git command from the repository root, one per call, and never `cd`; run the temporary worktree's commands as `git -C <temp> …`. In this folder (not the temporary worktree): no switch, checkout, stash, restore, rebase or pull, no hard reset, and no commit command (new commits are made with `git commit-tree`, so no commit gate runs). Never force push (no `--force`, `--force-with-lease` or `+` refspec); push only when the user asked for it. An environment variable for one command (`GIT_INDEX_FILE`, `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE`) is written in the shell's own syntax: in Git Bash `VAR=value git …`; in PowerShell set `$env:VAR` in the same call and remove it after the command (`Remove-Item Env:VAR`). In PowerShell, also put double quotes around any argument with braces (`"HEAD^{tree}"`, `"@{u}"`); unquoted, it reaches git wrong or does not parse. Once a temporary worktree, an index file or a message file exists, every outcome (success, stop or failure) goes through step 9 before the reply.
1. Start: the current branch is `git symbolic-ref --short HEAD`; if that fails (detached HEAD), stop and ask the user to check out a branch. Stop if `git rev-parse --git-path <name>` exists for any of `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply` (an operation in progress). If `ProjectSettings/ProjectVersion.txt` exists (a Unity project), tell the user in one line, without waiting for an answer, that the Unity editor may stay open: only a cherry-pick onto this branch changes files in this folder, at its very end. If the argument starts with `backup/`, do "Back to the backup" below instead.
2. Mode and range: from the argument and the conversation pick one mode (squash, regroup by task, fold uncommitted work into HEAD or into the matching earlier commit, reword subjects to fit their changes, split paths out of a commit, cherry-pick to another branch) and the range `<base>..HEAD` (`<base>` must pass `git rev-parse --verify -q <base>^{commit}`). Stop if `git rev-list --merges <base>..HEAD` prints anything. Note the commits that `git log --format="%h %G?" <base>..HEAD` shows as signed (not `N`): rewriting drops their signatures. A cherry-pick goes to step 8; otherwise note `<old>` = `git rev-parse HEAD`.
3. Remote check (only unpushed commits are rewritten): the remote ref is `@{u}` (`git rev-parse --abbrev-ref --symbolic-full-name @{u}`, `origin/<name>`); without one, `origin/<default>` with the default branch found as `git symbolic-ref --short refs/remotes/origin/HEAD` minus `origin/`, else the `ref: refs/heads/<name>` line of `git ls-remote --symref origin HEAD`. Run `git fetch origin refs/heads/<name>`; if it fails, do not stop: go on from the last fetched `refs/remotes/origin/<name>` and note it for the reply. Stop if `git rev-parse --verify -q refs/remotes/origin/<name>` fails. If `git merge-base --is-ancestor <oldest commit of the range> refs/remotes/origin/<name>` succeeds, stop and tell the user those commits are already on the remote.
4. Plan card: for regroup, split, fold into an earlier commit, or when some paths are to be left out, show each old commit → new commit (subject and paths) and wait for the user's approval. A squash of a named range and a reword run at once. New messages follow the repository's way in `git log -10 --format=%s`, in Korean, and never carry `Co-Authored-By` or any other Claude line.
5. Fold snapshot: refuse a path whose staged and working versions differ (in `git status --porcelain`, both status letters set and not `??`, such as `MM`, `AM` or `MD`). Note the time as `<ts>` (YYYYMMDD-HHMMSS, used by every later name). If `.am/` does not exist, first create it, with a `.gitignore` containing `*` unless `git check-ignore -q .am` succeeds. With `GIT_INDEX_FILE` set to the absolute path of `.am/tidy-<ts>.index`, run `git read-tree HEAD`, `git add -A -- <approved paths>` and `git write-tree` (prints `<wip-tree>`), then `git commit-tree <wip-tree> -p HEAD -m "WIP 임시 (am-util:tidy-commits <ts>)"`: the printed hash is `<wip>`; write it in the chat on a line of its own.
6. Trees (note `<ts>` now if step 5 did not): a squash ending at HEAD with no path left out takes `HEAD^{tree}`, fold into HEAD takes `<wip-tree>`, and a reword keeps every commit's tree, so these need no temporary worktree. Otherwise, with `.am/` as in step 5, run `git worktree add --detach --no-checkout <temp> <base>` with `<temp>` = `.am/tidy-<ts>`; each tree is `git -C <temp> read-tree <commit>` (a hash or `<old>`, never `HEAD`: in `<temp>` it is `<base>`), then `git -C <temp> restore --staged --source=<commit> -- <paths>` as listed, then `git -C <temp> write-tree`.
   - Regroup: every path of `git diff --name-only --no-renames <base> HEAD` belongs to exactly one group (stop if the commits that change a path fall in two groups). Start from `read-tree <base>`; each group in order adds its paths from `<old>` and writes its tree.
   - Split commit X: first `read-tree X` with the split paths restored from `X^` (X without them), then X's own tree.
   - Fold into commit C: C's tree with the folded paths restored from `<wip>`; each later commit gets the same (stop if `git diff --name-only <commit>^ <commit> -- <folded paths>` prints anything for it).
   - Paths left out: every new tree, including the later commits', has them restored from `<base>` (stop if a later commit changes one of them).
   - Commits after the rewritten ones keep their own trees, apart from the two rules above.
7. Commit, check and move:
   - Chain from `<base>`, each new commit the next one's parent. If `.am/` does not exist, first create it as in step 5 (`--output` makes no folder). If a `git log` below fails, go to step 9 and stop, so that no older file is used.
     - A commit whose message stays (the target of a fold, a later commit, a commit a reword does not change), byte for byte with any old trailer: `git log -1 --no-show-signature --encoding=UTF-8 --format=format:%B --output=.am/tidy-<ts>.msg <commit>`, then `git commit-tree <tree> -p <parent> -F .am/tidy-<ts>.msg`.
     - A reworded subject keeps the body: `git log -1 --no-show-signature --encoding=UTF-8 --format=format:%b --output=.am/tidy-<ts>.msg <commit>`, then `git commit-tree <tree> -p <parent> -m <new subject> -F .am/tidy-<ts>.msg`, or `-m <new subject>` alone when that file is empty. Drop the body only when the user asked to replace the whole message.
     - A combined or split commit gets a new message: `git commit-tree <tree> -p <parent> -m <msg>`.
     - Author name, mail and date come from `git log -1 --no-show-signature --encoding=UTF-8 --format=%an%n%ae%n%aI <commit>` passed as `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE`: the oldest original commit of a combined group, the commit itself for a reword, the target of a fold, each part of a split and later commits.
   - Expected tree: `git rev-parse <old>^{tree}` (`<old>` from step 2); `<wip>^{tree}` for a fold; with paths left out, the tree `<old>` gets in `<temp>` when they are restored from `<base>` (as in step 6). If `git rev-parse <new>^{tree}` differs, move nothing, go to step 9 and stop.
   - Backup: `git branch backup/<branch>-<ts> <old>` (`<wip>` for a fold; if the name exists, add `-2`, `-3` and so on). Move: `git update-ref -m "am-util:tidy-commits <ts>" refs/heads/<branch> <new> <old>` (it fails if the branch moved meanwhile; then report it with the backup's name). After a fold, `git reset -q -- <folded paths>`. Go to step 9.
8. Cherry-pick to another branch (no remote check): refuse a target checked out in another worktree (a `branch refs/heads/<target>` entry of `git worktree list --porcelain` other than this folder). The start is the local target, else `origin/<target>`; note it as `<old>`. Note `<ts>`, create `.am/` as in step 5, then `git worktree add --detach <temp> <old>` and `git -c core.editor=true -C <temp> cherry-pick <commits>`.
   - Conflicts: for each file of `git -C <temp> diff --name-only --diff-filter=U`, read both sides (`git -C <temp> show :2:<path>` and `:3:<path>`), show in plain words what each side changed, and ask the user whether to abort or to let you resolve them so each commit keeps its original intent. During a cherry-pick `--ours` is the target side and `--theirs` the picked commit. Edit a text file only inside `<temp>`; take a scene, prefab or binary file whole with `git -C <temp> checkout --ours -- <path>` or `git -C <temp> checkout --theirs -- <path>`; then `git -C <temp> add -- <path>` and `git -c core.editor=true -C <temp> cherry-pick --continue`. If you are not confident, the user chooses to abort, or a command fails otherwise, run `git -C <temp> cherry-pick --abort` and go to step 9.
   - `<new>` is `git -C <temp> rev-parse HEAD`. If the target is the current branch, run `git merge --ff-only --no-autostash --no-overwrite-ignore <new>` once and handle a refusal or failure as step 8 of the am-util:land skill does; otherwise `git update-ref refs/heads/<target> <new> <old>`, or `git branch <target> <new>` when there was no local target.
   - Only when the user asked to push: `git push origin <new>:refs/heads/<target>`. If it is rejected, only report it.
9. Clean up: when a temporary worktree exists, `git worktree remove <temp>`; if git refuses, `git worktree remove --force <temp>` (only this run's folder); if that fails too, report its path. Delete `.am/tidy-<ts>.index` and `.am/tidy-<ts>.msg` if they exist.
10. Reply:
   - The conclusion in one line, then old → new commits (`git log --oneline <base>..HEAD`, or the target's new commits).
   - Except after a cherry-pick, which makes no backup: the backup's name, and that calling this skill with it (or asking in this conversation) returns the branch there; when its top is the "WIP 임시" commit, never push or merge the backup.
   - Commits whose signature was dropped; after a fold, that the folded paths are committed and nothing is staged for them; paths left out stay as uncommitted changes.
   - When the fetch failed, one line: the remote could not be checked, so the last fetched state was used.
   - For a cherry-pick: each conflict and how it was resolved, or that it was aborted; the push result.
   - Only for a Unity project whose files changed (a cherry-pick onto this branch), one line: back in the editor it reimports the changed files, and if it asks whether to reload a scene changed on disk, choose reload.

## Back to the backup
`<backup>` is a `backup/<branch>-<ts>` branch (perhaps with a `-2` suffix) that this skill made.
1. Check: `git rev-parse --verify -q refs/heads/<backup>` must succeed and the current branch must be its `<branch>`; check for an operation in progress and give the Unity line as in step 1. It is a fold backup only when `git log -1 --encoding=UTF-8 --format=%s <backup>` equals `WIP 임시 (am-util:tidy-commits <ts>)` with the `<ts>` of its name; then `<target>` is `<backup>^`, else `<backup>`.
2. Files: for the paths of `git diff --name-only HEAD <backup>`, `git diff --quiet <backup> -- <paths>` must succeed (the working files equal the backup); otherwise stop and name them, since moving would change what they mean.
3. Save and move: `git branch backup/<branch>-<new ts> HEAD`, then `git update-ref -m "am-util:tidy-commits back <new ts>" refs/heads/<branch> <target> <current HEAD>`. For a fold backup, `git reset -q -- <paths of git diff --name-only <backup>^ <backup>>` (the folded files are uncommitted again). No file changes.
4. Reply: the commit the branch is on again, the new backup's name (calling this skill with it goes back again), that both backups remain and deleting them is the user's choice, and the number of uncommitted files (`git status --porcelain`).
