# am

am 은 Claude Code 와 Codex CLI 에 붙여 쓰는 가벼운 개발 워크플로 플러그인입니다. AI 에게 코드 작업을 맡길 때 "계획 → 구현 → 점검 → 커밋" 순서를 지키게 하고, 사람에게는 꼭 필요한 것만 묻습니다. 커밋 직전에는 프로젝트의 빌드·테스트를 실제로 돌려, 실패하면 커밋을 막습니다.

Claude Code 나 Codex 를 써 봤다면 바로 쓸 수 있습니다. 플러그인, 훅, git 브랜치를 잘 몰라도 아래 "처음 써 보기"까지만 읽으면 시작할 수 있고, 그 뒤는 필요할 때 찾아보면 됩니다.

## 한눈에 보기

보통은 명령 네 개를 차례로 씁니다.

1. `am:plan`: 큰 변경을 시작하기 전에 의도를 확인하고, 사용자만 정할 수 있는 것만 묻고, 짧은 계획 문서를 씁니다.
2. `am:do`: 계획 문서대로 구현합니다. 끝난 단계는 건너뛰고 남은 단계부터 이어 갑니다. 커밋은 하지 않습니다.
3. `am:check`: 커밋 전에 빌드·테스트(게이트), 실행 확인, 계획 대비 검토를 한 번에 합니다.
4. `am:commit`: 이번 작업 파일만 논리 단위로 커밋합니다. 맨 앞에 `push` 를 붙이거나 대화에서 커밋 뒤 push 를 요청했을 때만 push 까지 합니다.

이 네 단계를 한 번에 맡기려면 `am:auto-multi` 를 씁니다. 요청 하나를 계획 → 구현 → 점검 → 커밋까지 중간 질문 없이 이어 가고, 대신 정한 것은 마지막 답에서 알려 줍니다.

`am:auto-one` 도 같은 일을 하되, Claude Code 에서 단계마다 새 세션을 띄우는 대신 한 세션을 이어 쓰며(다음 단계의 모델이 바뀌거나 대화가 10만 토큰 이상이면 그 단계는 새 세션으로 시작), 큰 작업도 오케스트레이터에 넘기지 않고 부분으로 나눠 차례로 돕니다.

`am:auto-agent` 도 같은 일을 하되, Claude Code 에서 단계마다 별도 `claude` 세션 대신 지금 세션의 서브에이전트(단계 에이전트)를 띄우고, 단계가 끝날 때마다 채팅에 한 줄(단계와 상태)만 남깁니다. 큰 작업은 `am:auto-one` 처럼 부분으로 나눠 돕니다.

그 밖의 명령 둘은 필요할 때만 씁니다.

- `am:land`: 지금 브랜치를 대상 브랜치(생략하면 원격 기본 브랜치)에 합쳐 원격에 push 합니다. 지금 작업 폴더와 커밋하지 않은 변경은 그대로 두고, 강제 push 는 하지 않습니다.
- `am:sessions`: 이 PC 에서 `am:auto-multi` 와 오케스트레이터가 띄운 세션이 작업 폴더별로 지금 무엇을 하는지 한 번 보여 줍니다. 아무것도 바꾸거나 멈추지 않습니다.

명령과 함께 두 가지 장치가 돕니다.

- 커밋 게이트: 에이전트가 `git commit` 을 실행하기 직전에 프로젝트의 `am-gate.json` 명령을 돌리고, 실패하면 커밋을 막습니다.
- 2차 의견(`am:second-opinion`): 기술적 선택을 작업 세션이 자기 추천안으로 정하지 않습니다. 대화를 보지 못한 별도 서브에이전트(기본 모델·effort 는 아래 "모델과 effort 기본값" 표, 사용자 설정 파일로 바꿀 수 있음)가 코드를 직접 읽고 고른 안을 적용합니다. PC 에 codex CLI 가 있으면 Codex 도(없으면 두 번째 Claude 서브에이전트가) 같은 선택을 따로 고르고, 둘이 갈리면 서로의 답을 보며 다시 고르게 해 끝까지 갈린 것만 사용자에게 묻습니다. Claude Code 에서만 동작합니다.

작은 수정(파일 몇 개, 결과가 분명한 일)은 스킬 없이 그냥 요청하면 됩니다. 커밋 게이트는 그때도 동작합니다.

0.1.64 부터 `am:auto` 는 `am:auto-multi`, `am:solo` 는 `am:auto-one`, `am:lean` 은 `am:auto-agent` 로 이름이 바뀌었습니다. 옛 이름은 곧 없어지며, 그때까지는 새 이름을 알려 주고 멈춥니다.

## 용어 풀이

여러 절에 거듭 나오는 말만 모았습니다. 한 번만 나오는 말은 그 자리에서 풀어 씁니다.

- 스킬: `am:plan` 같은 명령 하나. Claude Code 에서는 `/am:plan`, Codex 에서는 `$am:plan` 처럼 앞에 기호를 붙여 부릅니다.
- slug: 작업마다 붙는 짧은 이름. 그 작업의 파일이 모이는 폴더 `.am/<slug>/` 의 이름이 되고, 명령에 `<slug>` 로 넘깁니다.
- 계획 문서: `am:plan` 이 쓰는 `.am/<slug>/plan.md`. 무엇을 어떤 단계로 할지, 무엇을 정했는지가 적히고, 다른 명령들이 이 문서를 읽고 이어 갑니다.
- 인계 문서: 계획 문서 옆의 `.am/<slug>/handoff.md`. 목표, 진행 상태(끝난 것·진행 중·남은 것), 바꾼 파일과 요지, 다시 열지 않을 확정 결정, 미해결 이슈·의심 지점, 다음에 할 일을 40줄 안팎으로 적은 짧은 문서입니다. `am:plan`·`am:do`·`am:check`·`am:commit` 이 단계를 마칠 때마다 통째로 다시 쓰므로, 대화가 압축되거나 새 세션을 열어도 이 파일만 보면 이어 갈 수 있습니다. 자세한 내용은 계획 문서를 가리킵니다.
- 구현 결과 문서: 계획 문서 옆의 `.am/<slug>/do-result.md`. `am:do` 가 모든 단계를 마쳤을 때와 중간에 멈출 때 통째로 다시 쓰는 구현 보고서로, 첫 줄은 영어로 `Status: done` 또는 `Status: stopped - <이유>` 입니다. 끝난·남은 단계, 이 작업이 바꾼 파일과 요지, 돌린 확인과 결과, 확인 못 한 것, 계획과 달라진 점, 구현 중 정한 기술 선택, 점검이 볼 의심 지점, 이전 실행마다 한 줄을 40줄 안팎으로 적습니다. `am:check` 는 점검 방향을 잡는 데만 읽고, `am:commit` 은 파일 목록을 이 작업의 파일을 가리는 근거로 씁니다. 구현 세션의 자기 보고라 무엇이 통과했다는 증거로는 쓰지 않습니다.
- 현재 작업 표시: `.am/.active` 에 slug 한 줄로 적히는 지금 진행 중인 작업. `am:plan`·`am:do` 가 작업을 시작하거나 다시 열 때 덮어씁니다. slug 없이 `am:do`·`am:commit` 을 부르면 작업 목록 맨 앞에 "현재"로 보여 주지만, 자동으로 고르지는 않고 묻습니다. 오케스트레이터가 띄운 세션은 이 표시를 쓰지 않지만, 인계 문서는 작업 폴더마다 씁니다.
- 게이트: 프로젝트의 `am-gate.json` 에 적은 빌드·테스트 명령을 실행하는 검사로, `am:check` 에서도 돌립니다. 커밋 직전에는 커밋을 막도록 설정된 명령만 돌려 실패하면 커밋을 막습니다.
- 훅: 에이전트가 어떤 도구를 쓰기 직전에 플러그인이 끼어들어 확인하는 장치. 게이트도 훅으로 돕니다.
- 서브에이전트·2차 의견: 서브에이전트는 작업 세션이 따로 띄우는 보조 AI 실행입니다. am 의 2차 의견은 대화를 보지 못한 서브에이전트가 기술 선택을 따로 고르는 장치입니다.
- effort: 모델이 답하기 전에 얼마나 깊이 생각할지 정하는 값(`medium`, `high` 등).
- 단계 세션: Claude Code 에서 `am:auto-multi` 가 계획·구현·점검 같은 단계마다 새로 띄우는 별도 `claude` 세션.
- 단계 에이전트: Claude Code 에서 `am:auto-agent` 이 단계마다 지금 세션 안에 띄우는 서브에이전트(`am:stage-plan`·`am:stage-do`·`am:stage-check`·`am:stage-commit`·`am:stage-commit-push`). `/agents` 목록에 보입니다.

## 준비물

- Node.js 18 이상(`node` 가 PATH 에 있어야 게이트 훅이 돎)
- Claude Code 또는 Codex CLI(0.160 에서 확인)
- 2차 의견은 Claude Code 2.1.280 이상(Opus 5.5 를 쓸 수 있는 버전)에서만 동작합니다. Codex 에는 이 서브에이전트가 없습니다.
- 선택: codex CLI(0.160 에서 확인, 로그인된 상태)가 있으면 Claude Code 의 2차 의견에 Codex 가 함께 들어갑니다(아래 "Codex 와 함께 정하기").

## 설치

저장소는 GitHub 공개 저장소 [AlMandu/am](https://github.com/AlMandu/am) 입니다. 아래 명령을 Claude Code 나 Codex 안에서 그대로 입력하면 됩니다.

**Claude Code**

```
/plugin marketplace add AlMandu/am
/plugin install am@am-workflow
```

**Codex CLI**

```
codex plugin marketplace add https://github.com/AlMandu/am.git
codex plugin add am@am-workflow
```

Codex 는 플러그인 훅을 사용자가 신뢰해야 실행합니다. 설치 뒤 Codex 를 시작하면 나오는 훅 검토 화면에서 "Trust all and continue" 를 고르거나, 세션 중 훅 목록에서 `t` 를 누르세요. 신뢰하기 전에도 스킬은 동작하지만 커밋 게이트는 돌지 않습니다. 플러그인을 업데이트해 훅이 바뀌면 다시 신뢰해야 합니다.

옛 AlMandu 툴킷(`am@almandu`)과는 이름이 같아서 함께 설치할 수 없습니다. 먼저 제거하세요.

**Claude Code 클라우드 세션(claude.ai/code)**

클라우드 세션은 저장소 `.claude/settings.json` 의 `enabledPlugins`·`extraKnownMarketplaces` 를 설치하지 않고, 세션 안에서는 `/plugin` 도 쓸 수 없습니다. 대신 클라우드 환경의 설정 스크립트(Setup script)에서 설치하면 세션 시작부터 am 이 켜져 있습니다. claude.ai/code 메시지 입력란 위의 클라우드 아이콘 → **Cloud** → **Add cloud environment**(기존 환경은 톱니바퀴)를 열고, 네트워크는 **Trusted** 로 두고 아래 스크립트를 넣으세요.

```bash
#!/bin/bash
# 설정 스크립트가 실패하면 세션이 시작되지 않으므로 모든 단계를 || true 로 둡니다.
command -v claude >/dev/null || exit 0
claude plugin marketplace add AlMandu/am || claude plugin marketplace update am-workflow || true
claude plugin install am@am-workflow --scope user || true
# 오케스트레이터가 필요 없으면 아래 줄을 지우세요.
claude plugin install am-orchestrator@am-workflow --scope user || true
```

- 설정 스크립트는 Claude Code 가 뜨기 전에 root 로 돌고, 사용자 범위(`~/.claude/settings.json`)로 설치한 플러그인은 그 세션에서 바로 읽힙니다.
- 환경은 첫 실행 뒤 파일 시스템 스냅샷으로 약 7일 동안 재사용되므로, 그 사이에 나온 새 버전은 들어오지 않습니다. 스냅샷이 만료되거나 설정 스크립트를 고치면 다시 설치합니다. 바로 올리려면 세션 안에서 `claude plugin marketplace update am-workflow` 뒤 `claude plugin update am@am-workflow` 를 실행하고 새 세션을 여세요.
- claude.ai 에 am 을 직접 올려(조직·개인 플러그인) 클라우드 세션에 동기화되고 있다면 같은 이름의 am 이 두 벌 실립니다. 둘 중 하나만 켜 두세요. 이 경우 위 스크립트에서 am 줄을 빼고 오케스트레이터만 설치해도 됩니다.

## 처음 써 보기

Claude Code 에서 0으로 나눌 때 오류 문구를 보여 주는 기능을 만든다고 해 봅시다.

1. `/am:plan 0으로 나누면 오류 문구를 보여 줘` 를 입력합니다. 계획 문서 `.am/<slug>/plan.md` 가 생기고, 화면에 어떻게 보일지처럼 사용자만 정할 수 있는 것이 있으면 질문이 나옵니다. 답은 그 계획 문서에 적힙니다. 결과가 분명한 작은 수정으로 보이면 계획 문서 없이 바로 해 주겠다고 제안하고 멈춥니다.
2. 새 세션에서 `/am:do <slug>` 로 구현합니다. 질문에 답할 때 "go" 를 붙였다면 이 단계가 바로 이어집니다. 모든 단계를 마치면 끝에 `am:check` 로 점검까지 합니다.
3. 그 점검 결과를 읽습니다. 결과가 BLOCK 이면 커밋 전에 고칠 것이 있다는 뜻이고, NOTE 는 참고만 하면 됩니다. 에이전트가 직접 확인하지 못한 부분은 "어디서·무엇을·무엇이 보이면 통과" 체크리스트로 받습니다. 그 목록대로 직접 확인해 보세요. 고친 뒤 따로 다시 점검하려면 `/am:check` 를 입력합니다.
4. `/am:commit` 으로 커밋합니다. 저장소에 `am-gate.json` 을 두었다면 커밋 게이트가 그 빌드·테스트를 돌려 실패하면 커밋을 막습니다(아래 "커밋 게이트").

이 네 단계를 한 번에 맡기려면 `/am:auto-multi 0으로 나누면 오류 문구를 보여 줘` 를 입력합니다. 마지막 답의 결론 바로 다음에 나오는 "대신 정한 것" 을 읽고, 마음에 들지 않으면 push 전에 되돌리면 됩니다.

`.am/` 폴더는 자동으로 git 에서 제외되므로(`.am/.gitignore`) 커밋에 섞이지 않습니다.

## 명령별 설명

### `am:plan`: 계획 세우기

- `.am/<slug>/plan.md` 를 씁니다. 질문에 답할 때 "go" 를 붙이면 바로 구현까지 이어 갑니다(`am:do` 와 같은 규칙).
- 바꿀 코드 말고도 다시 쓸 수 있는 기존 헬퍼·비슷한 기능·따라야 할 관례를 찾아, 계획 문서의 파일 줄에 `(reuses: …)` 로 적습니다.
- 계획 문서와 함께 인계 문서(`handoff.md`)를 쓰고, `.am/.active` 에 이 작업을 현재 작업으로 적습니다. 기존 계획을 다시 열 때도 둘 다 고칩니다.
- 계획 문서 머리에는 구현 규칙이 적힙니다: 순서대로 진행, 단계마다 확인 후 완료 표시, 버그면 고치기 전 재현 기록, 계획과 다르면 변경 기록에 남김, 끝나면 `am:check`.

### `am:do`: 계획대로 구현

- 완료 표시가 없는 첫 단계부터 이어 갑니다.
- 이전 세션이 이 계획으로 바꾼 파일은 이번 작업으로 보고, 표시와 파일 상태가 맞지 않으면 묻습니다.
- 계획에 답하지 않은 질문이 남아 있으면 먼저 묻습니다.
- 단계를 마칠 때마다, 그리고 중간에 멈출 때 인계 문서를 고쳐 씁니다. 이어 갈 때는 인계 문서의 다음 할 일도 읽되, 계획 문서와 다르면 계획 문서를 따릅니다.
- 모든 단계를 마쳤을 때와 중간에 멈출 때 구현 결과 문서(`do-result.md`)를 고쳐 씁니다. 다시 이어 갈 때는 이전 구현 결과 문서도 읽습니다.

### `am:check`: 커밋 전 점검

- 판정은 둘 중 하나입니다. BLOCK 은 게이트 실패, 확인된 결함, 이유 없이 빠진 계획 항목, 정해야 하는 기술 선택입니다. NOTE 는 그 밖의 모든 것이고 커밋을 막지 않습니다.
- 리뷰는 이미 있는 코드를 새로 다시 만든 곳도 그 기존 코드와 함께 짚습니다(NOTE, 커밋을 막지 않음).
- 프로젝트에 실행 확인 방법을 적어 두면 더 많이 직접 확인합니다(아래 "런타임 확인 안내").
- 작업 이름(slug)이 있으면 점검 결과(`check.md`)를 쓴 뒤 인계 문서를 고쳐 씁니다.
- 구현 결과 문서(`do-result.md`)가 있으면 먼저 읽어 실행 확인과 리뷰가 볼 곳을 정합니다. 통과 판단은 그 문서가 아니라 직접 돌린 게이트와 확인으로 내리고, 문서가 멈춤이나 남은 단계를 적고 있으면 구현이 끝나지 않았다고 알립니다.

### `am:commit`: 커밋

- 다른 세션이나 사용자가 만든 변경을 남겨 두고, 남긴 개수를 알려 줍니다.
- 구현 결과 문서(`do-result.md`)가 있으면 그 파일 목록으로 이 작업의 파일을 가립니다. 목록과 실제 변경이 다르면 실제 변경을 따릅니다.
- 커밋할 때마다 그 해시와 제목을 `.am/<slug>/commits.md`(git 에 들어가지 않는 로컬 파일)에 한 줄씩 적어 그 작업이 만든 커밋을 나중에 찾을 수 있게 합니다. 오케스트레이터가 띄운 세션에서는 적지 않습니다.
- 마지막 커밋 뒤 인계 문서를 고쳐 써, 상태가 커밋까지 끝났음을 보여 줍니다.
- `am:commit push` 는 커밋이 모두 성공했을 때만 현재 브랜치를 push 합니다. 먼저 나갈 커밋 목록을 보여 주고, 이번에 만들지 않은 커밋이 섞여 있으면 알립니다.
- 강제 push 는 하지 않으며, 원격에 새 커밋이 있어 거절되면 pull·rebase 없이 멈추고 알립니다. 커밋할 게 없으면 이미 있는 로컬 커밋만 push 합니다.
- 메모는 `push` 뒤에 씁니다(`/am:commit push 오타 수정`).

### `am:auto-multi`: 요청 하나로 계획부터 커밋까지

`am:auto-multi` 는 `am:plan` → `am:do` → `am:check` → `am:commit` 을 이어 갑니다. 각 명령의 규칙은 그대로 따르고, 사용자에게 묻고 멈추던 곳만 바꿉니다.

- 화면·범위 질문은 추천안으로 정해 계획 문서에 "(자동 결정)" 으로 남기고, 마지막 답의 결론 바로 다음에 "대신 정한 것" 으로 보여 줍니다. 2차 의견으로 정한 기술 선택(무엇을 정해야 했고 어느 안으로 정했는지, 작업 세션의 안을 뒤집었는지)도 함께 나오고, 오케스트레이터로 넘긴 작업은 그 실행이 2차 의견으로 정한 것까지 모읍니다.
- 작은 변경에도 짧은 계획 문서를 씁니다.

#### 멈추고 묻는 경우

- 이번 실행 전부터 있던 데이터·파일 삭제, 저장 형식 변경·데이터 이전, 저장소 밖 변경, 사용자·프로젝트 지침이 확인을 요구하는 일.
- 점검이 BLOCK 이면 이번 작업 안의 원인을 고쳐 한 번 더 점검하고, 그래도 BLOCK 이면 커밋하지 않고 멈춥니다. 원인을 고친 뒤 `am:auto-multi <slug>` 로 다시 실행하면 계획을 새로 쓰지 않고 남은 단계부터 이어 갑니다.

#### push

- 맨 앞에 `push` 를 붙였을 때만 push 합니다(`/am:auto-multi push 오타 수정`). 붙이지 않으면 로컬 커밋까지만 하므로, 대신 정한 것이 마음에 들지 않으면 push 전에 되돌릴 수 있습니다.
- 커밋 전 검사를 돌리지 못했으면(설정 파일 오류, 검사 프로그램 없음) `push` 를 붙였어도 로컬 커밋까지만 하고 알립니다.

#### Claude Code 에서는 단계마다 새 세션

Claude Code 에서는 `am:auto-multi` 가 진행만 맡고 네 단계를 각각 새 `claude -p` 세션으로 백그라운드에서 띄웁니다. 단계 사이에 대화는 넘기지 않고 작업 폴더(`.am/<slug>/`)의 파일만 넘기므로, 단계마다 대화가 깨끗하게 시작하고 앞 단계 내용이 섞이지 않습니다.

- 단계 세션이 멈춰야 하면 질문을 계획 문서에 남기고 끝나고, 원래 대화가 그 질문을 묻고 답을 적은 뒤 그 단계를 새 세션으로 다시 띄웁니다.
- 점검이 BLOCK 이면 고치는 구현 세션과 점검 세션을 한 번 더 띄웁니다.
- 단계는 터미널과 떨어진 작업 프로세스가 돌리고, `am:auto-multi` 가 띄운 단계 명령은 그것을 따라가다 약 8분 30초 안에 끝납니다(Bash 백그라운드 명령의 10분 제한 안). 단계가 아직 돌고 있으면 `am:auto-multi` 가 "단계가 아직 진행 중"(시작 시각과 함께)을 한 번 알리고 같은 단계를 다시 불러 이어 따라가므로, 10분 넘게 걸리는 계획·구현·오케스트레이터 이어받기도 끊기지 않습니다. 긴 단계에서는 채팅에 같은 단계 명령이 약 8분 30초마다 다시 보입니다. 아래 "진행 소식"의 "아직 진행 중" 줄과는 다른 알림입니다.
- 따라가는 명령이 끊겨도 단계는 계속되고, 그 사이 끝난 결과는 같은 단계를 다시 부를 때 새 세션 없이 한 번 받습니다. 그 사이 계획 문서나 점검 결과가 바뀌었으면 단계가 새로 돕니다. 같은 작업의 다른 단계가 아직 돌고 있으면 최대 8분 기다린 뒤 다시 부릅니다.
- 세션을 멈추거나 닫으면 단계도 멈춥니다: 따라가는 명령이 30분 동안 다시 오지 않으면 단계 작업이 스스로 멈추고(돌던 세션 정리), 오케스트레이터 이어받기 단계면 그것이 띄운 오케스트레이터 실행도 함께 멈춥니다. 이어 가려면 `am:auto-multi <slug>` 로 다시 실행합니다.
- 같은 저장소 폴더에서 다른 무인 실행(다른 작업의 `am:auto-multi`, 또는 `am-orchestrator` 실행)이 돌고 있으면 단계를 시작하지 않고 "다른 실행 … 을 기다립니다" 한 줄을 알린 뒤, 그 실행이 끝나면 이어 갑니다. 단계 사이 틈(10분 이내)에 있는 실행도 기다리고, 질문으로 멈췄거나 끝난 실행은 기다리지 않습니다. 기다림에 상한은 없습니다.
- 이 PC 에서 다른 세션(오케스트레이터의 세션·게이트, 다른 작업의 `am:auto-multi` 단계)이 도는 동안 남은 메모리가 기준보다 적으면 단계를 시작하지 않고 진행 소식에 `waiting for free memory (… MB free, needs … MB, … other sessions on this PC)` 한 줄을 남기고 기다립니다. 8분이 지나도 모자라면 `am:auto-multi` 가 알리고 같은 단계를 다시 띄웁니다. 다른 세션이 없으면 메모리와 상관없이 바로 시작합니다. 기준은 아래 ["남은 메모리 기준 (사용자 설정 파일)"](#남은-메모리-기준-사용자-설정-파일) 에 있습니다.
- 단계 세션(압축 세션·끝 표시를 다시 묻는 세션·오케스트레이터 이어받기 포함)이 끝나면 그 세션이 남긴 프로세스(MCP 서버, 백그라운드 명령 등)를 끕니다. 오케스트레이터 이어받기는 그것이 띄운 오케스트레이터 실행을 먼저 멈추고 그 실행은 건드리지 않습니다. 끈 것이 있으면 진행 소식에 `cleaned up N processes left by the <단계> session (working set about X MB)` 한 줄이 나옵니다. 작업 집합 합계는 끈 프로세스가 쓰던 메모리의 대략값이지 되찾은 메모리가 아닙니다. 정리는 최대 1분이고, 실패해도 단계 결과는 바뀌지 않습니다.
- 이 PC 에서 `claude` 명령을 찾지 못해 세션을 띄울 수 없으면 그 단계부터 원래 대화에서 지금처럼 이어 가고 마지막 답에 알립니다.
- Codex 에서는 세션을 띄울 방법이 없어 한 세션으로 진행합니다.

- 단계 세션은 확인 창을 띄울 수 없어서 단계마다 허용할 도구가 정해져 있습니다. 계획은 읽기, 읽기 전용 git 명령(status·diff·log 등), `.am/` 쓰기(현재 작업 표시 `.am/.active` 포함), 그리고 Codex 2차 의견 스크립트 실행(실행 중인 am 과 설치된 am 둘 다; 두 폴더가 다르면 진행 소식에 한 줄로 알림)만, 구현·점검은 편집과 셸(단 커밋·push·reset·브랜치 전환·stash 는 막음), 커밋은 읽기 전용 git 명령과 git add·commit, 스테이징 해제(`git restore --staged -- <경로>`)만, 그 작업의 `commits.md`·`handoff.md` 쓰기, `push` 를 붙였을 때만 push 입니다. 넘김 세션은 `git switch` 로 시작 브랜치로만 돌아가고, 사용자 답에 따라 치운 stash 는 기록했다가 실행이 바꾼 파일과 겹치지 않을 때만 되살리며 지우지 않습니다.
- 계획·커밋·넘김 세션의 git 은 저장소 루트에서 평범한 `git <하위 명령> …` 모양만 허용됩니다. `git -C <폴더> …`, `git -c …`, `git --no-pager …` 처럼 하위 명령 앞에 옵션을 붙이면 거부되며, 세션은 이 거부가 셸이 꺼진 게 아니라 모양 문제라는 안내를 받고 평범한 모양으로 다시 합니다. 그래도 `BLOCKED` 로 멈췄는데 이유가 비어 있으면 결과의 `reason` 에 거부된 명령이 앞에서 세 개까지 적힙니다.
- 각 단계는 그 스킬의 모델·effort 로 돕니다(값은 아래 "모델과 effort 기본값" 표, 사용자 설정 파일로 바꿀 수 있음).
- 계획·구현·점검·커밋 단계와 압축 세션은 프롬프트 캐시(이미 보낸 앞부분을 잠시 저장해 다시 보낼 때 비용을 줄이는 기능)를 5분 보관으로 써 비용을 줄입니다(`FORCE_PROMPT_CACHING_5M`). 오케스트레이터 작업을 오래 기다리는 넘김 세션만 1시간 보관 그대로입니다.
- 단계 세션은 Claude Code 자동 업데이트 확인을 하지 않습니다(`DISABLE_AUTOUPDATER`).
- 단계 세션은 기본으로 MCP 서버를 띄우지 않습니다(`--strict-mcp-config`). 단계에서 MCP 도구가 필요하면 아래 "남은 메모리 기준 (사용자 설정 파일)" 절의 `stageMcpServers` 를 봅니다.
- 단계 작업의 기록·출력·결과·하트비트는 `.am/<slug>/` 의 `stage-worker.json`·`stage-worker.log`·`stage-result.json`·`stage-heartbeat` 에 남고(git 제외), 단계 세션이 읽는 작업 파일이나 압축 대상에는 들지 않습니다.

</details>

#### 진행 소식

단계 세션이 도는 동안 원래 대화에 진행 소식이 한두 줄씩 나옵니다: 단계 시작, 끝(결과와 걸린 분), 막힘, 결정 필요, 2차 의견으로 정한 선택(계획·구현 단계, 무엇을 정해야 했고 어느 안으로 정했는지·어느 검토자들이 동의했는지를 쉬운 말 한 줄로).

- 2분 안에 붙어 온 소식은 한 번에 묶이고, 약 8분간 소식이 없으면 무엇이 몇 분째 도는지 "아직 진행 중" 한 줄이 나옵니다.
- 구현 단계는 끝났다고 표시된 단계 수가 함께 나옵니다.
- 오케스트레이터에 넘긴 구현은 작업 단위 소식(작업 시작, 단계 전환, 완료, 막힘)이 같은 대화에 나오고, 새로 넘긴 직후 작업을 나누는 동안은 "아직 진행 중" 만 나올 수 있습니다.
- 세션 안의 세부(지금 고치는 파일, 돌리는 명령)는 나오지 않고, 마지막 답의 내용과 순서는 그대로입니다.
- 소식 한 번마다 원래 대화의 차례가 한 번 듭니다.
- Codex 와, 세션을 띄우지 못해 한 세션으로 진행하는 경우에는 이 소식이 없습니다.

<details>
<summary>진행 소식이 오는 방식과 손으로 보는 법</summary>

- `am:auto-multi` 가 단계 명령 옆에 대기 명령을 백그라운드로 하나 더 띄우는 방식이고, 소식은 `.am/<slug>/progress.jsonl` 에 쌓입니다.
- 손으로 보려면 저장소 루트에서 설치된 am 플러그인 폴더의 `scripts/progress.mjs` 를 `node <그 경로> <slug>` 처럼 옵션 없이 부릅니다. 그렇게 부르면 읽은 위치를 따로 기억해 채팅에 나올 소식을 가져가지 않습니다(`--consumer main` 은 `am:auto-multi` 가 쓰는 이름이라 손으로 붙이지 않습니다).

</details>

#### 큰 작업은 오케스트레이터에 넘김

- `am:auto-multi` 는 계획 문서 요약에 `규모: 구현 N회, 커밋 M개` 를 적습니다. 구현 1회는 새 세션 하나가 끝내고 확인할 수 있는 크기(파일 8개 안팎, 충실히 써도 계획 150줄 안에 담기는 일)입니다.
- Claude Code 에서 `am-orchestrator` 가 설치·활성화돼 있고 규모가 구현 1회를 넘으면(커밋 개수는 따지지 않습니다), 구현부터는 오케스트레이터가 작업 단위로 돌립니다(구현 단계 세션이 몹니다). 몇 시간, 큰 비용이 들 수 있습니다.
- 끝나면 실행용 브랜치를 시작한 브랜치로 합치고(fast-forward, 곧 merge 커밋 없이 앞으로 당겨 붙임) 지우므로, 커밋이 남는 곳과 `push` 는 작은 작업과 같습니다.
- 빌드·테스트 설정(`am-gate.json`)이 없거나, 이번 실행이 만들지 않은 미커밋 변경이 있거나, 시작 전부터 게이트가 실패하면 그 질문을 묻고 기다립니다.
- 마지막 답에 작업 수·브랜치·사람 확인 목록이 나오고, 중간에 멈추면 `am:auto-multi <slug>` 로 이어 갑니다.
- 설치돼 있지 않거나 Codex 에서는 지금처럼 `am:do` 로 구현합니다.

<details>
<summary>넘김을 빼먹지 않게 막는 훅</summary>

- 이 넘김을 세션이 빼먹지 않게, Claude Code 에서는 `am:auto-multi` 를 부른 세션에만 훅이 하나 붙습니다.
- 그 세션의 계획이 위 규모를 넘고 오케스트레이터가 설치돼 있는데, 넘긴 기록(계획 Change log 칸의 넘김 줄)도 끝난 단계도 없이 파일을 고치려 하면 그 수정을 막고 이유를 알려 줍니다. 계획에 규모 줄이 없으면 한 번 막고 적게 합니다.
- 어느 계획을 볼지는 그 세션이 만들거나 고치거나 읽은 `plan.md` 로 정하고, 계획 문서·오케스트레이터 파일·`am-gate.json` 은 막지 않습니다.
- 다른 칸에 적힌 비슷한 글자(파일 이름, 실행 ID 설명)나 넘김이 막혀 멈춘 기록은 넘김으로 보지 않습니다.
- 셸 명령으로 하는 수정과 규모를 작게 잘못 적은 경우는 막지 못합니다.

</details>

### `am:auto-one`: 한 세션을 이어 가며 계획부터 커밋까지

`am:auto-one` 는 실행할 때 `am:auto-multi` 의 규칙을 읽어 그대로 따르고, 다음만 다릅니다.

- 오케스트레이터를 찾지도 쓰지도 않고, `am:auto-multi` 의 넘김 훅도 붙지 않습니다. 이미 오케스트레이터에 넘긴 계획(계획 Change log 칸의 넘김 줄)이면 멈추고 `am:auto-multi` 로 이어 가라고 알립니다.
- Claude Code 에서는 단계 명령마다 `--solo` 를 붙여, 네 단계가 새 세션 대신 한 세션을 이어 씁니다. 이어 쓰는 세션과 그 단계가 돈 모델은 `.am/<slug>/solo-session.json` 에 기록됩니다.
- 단계 사이에는 먼저 다음 단계의 모델을 앞 단계의 모델과 비교합니다. 다르면(기본값으로는 커밋 단계와 그 다음 단계) 재지 않고 새 세션으로 시작합니다. 모델이 바뀌면 이어 써도 캐시를 다시 쓰지 못해 비용만 들기 때문입니다. 업데이트 전에 남은 기록처럼 모델을 모르면 바뀐 것으로 보고 한 번 새 세션으로 시작합니다.
- 모델이 같으면 Claude Code 의 `/context` 로 그 세션이 쓴 토큰 수를 재고(단계가 돌 모델로, 모델 호출 없음), 100,000 토큰 미만이면 그대로 이어 쓰고, 이상이거나 읽지 못하면 새 세션으로 시작합니다. 단계 사이에 대화를 압축하지는 않습니다.
- 이어 쓰기는 Claude Code 에서만 합니다. Codex 와, 세션을 띄울 수 없는 PC 에서는 `am:auto-multi` 처럼 원래 대화 한 세션으로 진행합니다.
- 기억 파일: 단계마다 끝 답 직전에 그 세션의 기억(결정과 이유, 남은 문제, 작업 파일에 없는 내용)을 `.am/<slug>/solo-context.md` 에 덮어씁니다. 단계가 새 세션으로 시작하면(기록된 세션이 없음, 모델 변경, 10만 토큰 이상, 이어 연 단계의 오류 등) 그 새 세션이 이 파일을 먼저 읽고 이어 갑니다. 같은 단계가 지난번에 `BLOCKED` 나 `failed` 로 끝났다면, 멈추게 한 결론이 이어지지 않도록 재지 않고 이 파일을 읽는 새 세션으로 다시 시작합니다. 이 파일은 지우지 않고, `.am/` 아래라 커밋되지 않습니다.

#### 큰 작업은 부분으로 나눔

- 계획의 규모가 구현 2회 이상이면 계획 문서 요약 뒤에 `## Parts` 절을 두고, 이어지는 단계들을 부분마다 구현 1회 이하로 나눕니다.
- 부분마다 `.am/<slug>-p<k>/` 작업 폴더를 만들어 그 부분만 계획 → 구현 → 점검 → 커밋하고, 끝나면 부모 계획의 Change log 칸에 `- Part <k> done: <slug>-p<k>` 줄을 남긴 뒤 다음 부분으로 갑니다. 부분마다 커밋되고, `push` 를 붙였으면 부분마다 push 합니다.
- 부분을 시작할 때마다 채팅에 `Part 2/3: <slug>-p2` 같은 한 줄이 나옵니다.
- 부분 slug 하나만 주어도 부모 작업으로 이어 갑니다.

#### 진행 소식과 마지막 답

- `am:auto-multi` 의 진행 소식에 더해 다음 줄이 나옵니다: `solo: context N tokens; continued the session`(10만 토큰 미만이라 이어 감), `solo: model change (a -> b); started a new session`(모델이 바뀌어 새 세션), `solo: context N tokens; started a new session`(10만 토큰 이상이라 새 세션), `solo: context use could not be read (…); started a new session`(사용량을 읽지 못해 새 세션), `solo: no recorded session; started a new one`(기록된 세션이 없어 새로 시작), `solo: could not continue the recorded session (…); started a new session`(기록된 세션을 이어받지 못해 새로 시작), `solo: the new session reads .am/<slug>/solo-context.md`(새 세션에 저장된 기억을 읽게 함).
- 마지막 답에는 부분별 점검 판정과 커밋, 그리고 새 세션으로 바꾼 단계가 있으면 그 이유(`model change (opus -> sonnet)`, `context N tokens` 등)와 저장된 기억 파일을 받았는지가 나옵니다.
- 중간에 멈추면 원인을 고치거나 질문에 답한 뒤 `am:auto-one <slug>` 로 이어 갑니다.

### `am:auto-agent`: 단계 에이전트로 계획부터 커밋까지

`am:auto-agent` 은 실행할 때 `am:auto-multi` 의 규칙을 읽어 그대로 따르고, 다음만 다릅니다.

- Claude Code 에서는 단계마다 별도 `claude` 세션 대신 지금 세션 안에 단계 에이전트(서브에이전트)를 띄웁니다. 지금 세션은 진행만 맡아, 단계가 끝날 때마다 채팅에 한 줄(단계와 상태)을 남기고 다음 단계를 고릅니다. 마지막 단계가 끝나기 전에는 단계가 쓴 문서(계획 문서, 점검 결과, 단계 보고)를 읽지 않으므로 지금 세션의 대화가 짧게 유지됩니다. 끝에는 `am:auto-multi` 와 같은 마지막 답을 줍니다.
- 단계 에이전트는 지금 세션 안에서 돌기 때문에 터미널을 닫으면 함께 멈춥니다. 같은 명령에 slug 를 주면(`am:auto-agent <slug>`) 마지막으로 끝난 단계 다음부터 이어 갑니다.
- 단계 에이전트가 실행하는 명령과 파일 쓰기는 am 의 훅이 단계별 허용 목록으로 확인합니다. 목록 안의 것은 확인 창 없이 실행되고, 밖의 것은 거부됩니다(예: 구현 단계의 `git commit`, 계획 단계의 `.am/` 밖 쓰기). 사용자 설정의 거부(deny) 규칙은 이 허용보다 우선합니다. 진행 담당인 지금 세션의 명령은 자동으로 승인하지 않으므로, 부분 완료를 기록하는 명령 등에서 확인 창이 뜰 수 있습니다.
- 단계 에이전트가 최종 답을 상태 줄 한 줄로 끝내지 않으면 훅이 한 번 막고 다시 쓰게 합니다.
- `am:auto-agent` 의 단계가 도는 동안 같은 폴더에서 시작한 `am:auto-multi` 단계는 기다리고(`WAIT`), 반대도 같습니다.
- `am:auto-multi` 의 단계 세션과 달리 남은 메모리 기다리기, 단계 전 작업 파일 압축, 진행 소식 명령이 없습니다. 오케스트레이터도 쓰지 않으며, 이미 오케스트레이터에 넘긴 작업이면 멈추고 `am:auto-multi` 로 이어 가라고 알립니다.
- 계획 단계의 2차 의견은 서브에이전트 대신 읽기 전용 별도 `claude -p` 세션과(설치돼 있으면) Codex 가 줍니다.
- 큰 작업(구현 2회 이상)은 `am:auto-one` 처럼 `.am/<slug>-p<k>/` 부분으로 나눠 차례로 돌고, 부분마다 커밋합니다.
- 사용자 모델 파일의 `plan`·`do`·`check`·`commit` 키가 단계 에이전트에도 적용됩니다.
- Codex, 그리고 서브에이전트나 셸 도구를 쓸 수 없는 환경에서는 `am:auto-multi` 처럼 한 세션으로 진행합니다.

### `am:land`: 지금 브랜치를 대상 브랜치에 합쳐 push

`am:land [브랜치]` 는 지금 브랜치의 커밋을 대상 브랜치에 합쳐 `origin` 에 push 합니다. 브랜치를 생략하면 원격의 기본 브랜치(예: `main`)에 합칩니다. 지금 작업 폴더는 처음부터 끝까지 건드리지 않으므로, 커밋하지 않은 변경(스테이징 여부, 새 파일 포함)은 그대로 남고 push 에도 들어가지 않습니다.

- 대상 브랜치가 지금 브랜치 바로 뒤에 있으면 그대로 앞으로 당겨 push 합니다(fast-forward).
- 갈라져 있으면 `.am/land-<시각>/` 에 잠깐 만든 임시 작업 폴더에서 병합 커밋을 만들어 push 하고, 그 폴더는 끝나거나 멈출 때 지웁니다. 지금 브랜치에는 병합 커밋이 생기지 않습니다.
- 충돌은 임시 작업 폴더 안에서 양쪽 의도를 살려 풉니다. 확신이 없으면 병합을 되돌리고 멈춥니다. push 전에 테스트나 게이트는 돌리지 않습니다.
- 강제 push 는 하지 않습니다. 원격에 새 커밋이 생겨 거절되면 pull·rebase 없이 멈추고 알립니다.
- 로컬 대상 브랜치는 원격에 맞춥니다. 원격과 다르면 시작할 때 원격 위치로 옮기므로 로컬 대상 브랜치에만 있던 커밋은 그 브랜치에서 빠지고, 답에 옮기기 전 위치와 빠진 커밋 목록을 보여 줘 되찾을 수 있게 합니다. 로컬에 없으면 push 한 커밋에 원격을 따라가는 브랜치로 만듭니다. 다른 작업 폴더에 체크아웃돼 있어 옮길 수 없으면 알리기만 합니다.
- push 를 하므로 사용자가 부를 때만 돕니다. 예전 `am:merge` 의 기록(`merge.md`, `feature/<slug>` 브랜치, `commits.md`)은 읽지 않습니다.

### `am:sessions`: 돌고 있는 세션 보기

`am:auto-multi` 의 단계 세션과 오케스트레이터 실행은 뒤에서 돌기 때문에, 여러 작업을 함께 돌리면 무엇이 어디까지 왔는지 알기 어렵습니다. `/am:sessions` 를 부르거나 "백그라운드 세션들 지금 뭐 해?" 처럼 물으면 이 PC 에서 돌고 있는 am 세션을 한 번 보여 줍니다.

- 작업 폴더(작업 트리)별로 묶고, 지금 대화의 작업 폴더를 먼저 보여 줍니다.
- 줄마다 역할(계획·구현·점검·커밋 등), 몇 분째인지, 마지막 소식과 그것이 몇 분 전인지, 구현 단계면 끝난 단계 수가 나옵니다.
- `am:auto-multi` 가 오케스트레이터에 넘긴 실행은 그 작업 아래 `└ 인계` 로, 직접 시작한 오케스트레이터 실행은 작업 폴더 바로 아래에 나옵니다. 세션과 세션 사이에는 "다음 작업 준비 중" 또는 "단계 대기 중"으로 나옵니다.
- 맨 앞에 몇 개가 돌고 있는지 한 줄로 알려 주고, 15분 넘게 소식이 없는 줄은 "최근 소식 없음"으로 짚습니다. 멈췄다고 단정하지는 않습니다(게이트 제한 10분, 진행 소식 대기 8분보다 길게 잡았습니다).
- 아무것도 돌고 있지 않으면 "지금 돌고 있는 am 세션이 없습니다." 한 줄만 나옵니다.
- 읽기만 합니다. 파일을 고치거나 세션을 멈추지 않고, 멈춘 작업은 `am:auto <slug>`, `am:solo` 로 시작한 작업이면 `am:solo <slug>` 로 이어 가라고 안내만 합니다.
- `am:check`·`am:commit` 처럼 모델이 질문을 보고 스스로 부를 수도 있습니다.
- Codex 에서는 단계 세션을 띄우지 않으므로, Codex 에서 부르면 같은 PC 의 Claude Code 가 남긴 기록만 보입니다.
- 손으로 볼 때는 저장소 루트에서 `node <am 플러그인 폴더>/scripts/sessions.mjs` 를 실행합니다.

보고 예시:

```
세션 보고 (14:05)
/Users/me/projects/app (현재 작업 트리)
  am:auto 작업 login-page — 인계 단계 세션, 42분째 · 마지막 소식: T01 구현 시작 (3분 전)
    └ 인계: am-orchestrator 실행 20261015-1320
      T01 로그인 화면 — 구현 세션, 3분째 · 마지막 소식: tests running (1분 전)
      T02 비밀번호 찾기 — 점검 단계 대기 중
  am:auto 작업 fix-typo — 점검 단계 세션, 2분째
```

## 왜 이렇게 만들었나

이전에 쓰던 무거운 워크플로(단계 6개, 스킬 19종)의 실행 기록을 분석한 결과에서 나온 원칙입니다.

- 사람이 들인 수고의 대부분은 AI 오류 수정이 아니라 멈춤에 답하기, 결정 질문, 경고 처리, 어려운 출력 해독이었습니다. 그래서 질문은 화면·범위·되돌리기 어려운 선택에만 하고, 기술 선택은 묻지 않고 정한 뒤 알립니다. 정하는 쪽은 작업 세션이 아니라 2차 의견입니다(아래 "기술 선택은 누가 정하나" 절).
- 경고는 커밋을 막지 않고, 막는 경우는 정해진 몇 가지뿐입니다(위 `am:check` 절).
- 답은 결론 → 사용자가 보는 변화 → 할 일 순서로, 내부 라벨 없이 씁니다.
- 실행 확인은 에이전트가 할 수 있는 만큼 먼저 하고, 사람에게는 "어디서·무엇을·무엇이 보이면 통과" 체크리스트만 넘깁니다.
- 가장 값진 장치였던 결정론적 게이트(실제로 빌드·테스트를 돌림)는 훅으로 남겼습니다.

## 기술 선택은 누가 정하나 (2차 의견, `am:second-opinion`)

작업 세션은 자기가 만든 안을 스스로 추천하고 그대로 고르기 쉽습니다. 그래서 사용자에게 묻지 않는 기술적 선택은 별도 서브에이전트가 정합니다.

- 대상: 구조·동작·비용이 달라지는 선택지가 둘 이상인 설계·구현 선택. 답이 하나뿐이면 보내지 않고 그대로 진행합니다. 화면·범위·되돌리기 어려운 선택은 지금처럼 사용자에게 묻습니다.
- 적용: 2차 의견이 고른 안을 적용합니다. 계획 문서의 "기본값 적용" 각 줄에 2차 의견이 골랐다는 표시가 붙고, 작업 세션의 안과 달랐으면 그 안도 함께 적힙니다. `am:plan` 과 `am:do` 는 답에서, `am:auto-multi` 는 마지막 답의 "대신 정한 것" 에서 달랐던 선택을 따로 알려 줍니다. 사용자 결정은 언제나 2차 의견보다 우선합니다.
- 비용: 호출 한 번이 아래 "모델과 effort 기본값" 표의 모델·effort 로(사용자 설정 파일에 적었으면 그 값으로) 도는 별도 실행입니다. 그래서 선택을 모아 한 번에 보내고, `am:plan` 은 계획당 한 번을 기본으로 합니다.
- 쓸 수 없을 때: 한쪽 검토자만 실패하면 다른 쪽 답으로 정합니다. 두 검토자 모두 답하지 못할 때(Codex 안에서 쓸 때, 또는 두 검토자(Claude 와 Codex, codex 가 없으면 Claude 둘)가 함께 실패할 때)만 작업 세션이 정하고, 그 줄에 2차 의견 없이 정했다는 표시를 남깁니다.

<details>
<summary>요청을 보내는 방식, 다시 여는 경우, 모델과 effort, 바꾸는 방법</summary>

- 방식: 작업 세션이 자기 안을 먼저 정해 두고, 미정인 선택을 한 번에 모아 목표·사용자 결정·아직 답을 받지 않은 질문·관련 경로·선택지만 적어 보냅니다. 자기 안은 적지 않습니다. 2차 의견은 대화 기록 없이 시작해 코드를 직접 읽고, 선택마다 고른 안·이유·위험을 돌려줍니다. 선택지에 없는 안을 고를 수도 있습니다.
- 다시 여는 경우: 정한 선택은 나중에 받은 사용자 답과 부딪히거나, 요약에서 빠졌던 사실이 드러나거나, 해 보니 안 될 때(확인 실패, 검토 지적)만 다시 엽니다. 그때도 작업 세션이 직접 바꾸거나 사용자에게 기술 질문으로 넘기지 않고, 새 사실을 붙여 2차 의견에 다시 보낸 뒤 그 줄을 고칩니다.
- 모델과 effort: 기본값은 아래 "모델과 effort 기본값" 표의 값(모델을 별칭으로 적어, 새 버전이 나와도 따로 고치지 않고 따라갑니다), 도구는 읽기 전용(Read, Grep, Glob). `plugin/agents/second-opinion.md` 의 frontmatter 에 있고 테스트가 지킵니다. 실행 중 `/tasks` 를 열면 그 서브에이전트 줄에 모델과 effort 가 보입니다. 바꾸는 법은 아래 "모델과 effort 바꾸기" 절의 `second-opinion` 키입니다.

</details>

### Codex 와 함께 정하기

Claude Code 에서 쓰고 PC 에 codex CLI 가 깔려 있으면(`codex` 명령이 PATH 에 있으면) 2차 의견이 Claude 와 Codex 둘이 됩니다(없으면 아래처럼 Claude 둘). 따로 설정할 것은 없습니다.

- 토론: 두 쪽은 서로의 답을 모른 채 고릅니다. 다르게 고른 선택만, 원래 요약에 지난 라운드 두 쪽의 안과 이유를 붙여 두 쪽에 다시 묻습니다. 최대 2라운드 더 묻고(오케스트레이터 세션은 시간 제한 때문에 1라운드), 합의한 선택은 계획 문서의 "기본값 적용" 줄에 Codex 와 합의했다는 표시(`Codex agreed`)가 붙습니다.
- 끝까지 갈리면: 그 선택만 두 쪽 안과 이유를 담은 결정 카드로 사용자에게 묻습니다. `am:auto-multi` 와 오케스트레이터도 이때는 멈추고 묻습니다.
- codex 가 없으면 Claude 2차 의견을 둘(Claude 1, Claude 2) 동시에 띄워 같은 방식으로 토론하고, 합의하면 Claude 검토자끼리 합의했다는 표시(`Claude reviewers agreed`)가 붙습니다. 서브에이전트 호출이 두 배로 들고, 끝까지 갈리면 위와 같이 묻습니다. 깔려 있지만 실패하면(로그인 안 됨, 오류, 시간 초과) 어느 라운드든 Claude 2차 의견만으로 정하고 그 줄에 표시합니다. 반대로 Claude 쪽이 실패하면 Codex 답으로 정합니다.
- 비용과 시간: 기술 선택을 보낼 때마다 Codex 실행이 하나 더 들고(사용자의 Codex 사용량), 갈리면 양쪽이 다시 돕니다.
- Codex 의 읽기 전용 샌드박스는 디스크의 파일을 읽을 수 있으므로, Codex 가 읽은 내용은 OpenAI 로 갑니다.
- Codex 안에서 am 을 쓸 때는 바뀌지 않습니다(Claude 2차 의견이 없음).

<details>
<summary>Codex 를 부르는 방식과 실행 조건</summary>

- 방식: 작업 세션이 결정 요약을 `.am/` 아래 파일로 쓰고, `plugin/scripts/codex-opinion.mjs` 로 Codex 를 한 번 돌린 뒤 같은 요약을 Claude 2차 의견에도 보냅니다. 두 호출은 차례로 돕니다. codex 가 없으면(스크립트 종료 코드 2) Claude 2차 의견 서브에이전트 둘을 한 번에 띄우고, 각 호출에 자기가 Claude 1 인지 Claude 2 인지 한 줄로 알려 줍니다.
- 다시 물을 때는 매번 새로 띄우므로 전체 사정을 다시 넘깁니다. 상대 이유는 주장으로 보고 코드로 확인하며, 놓친 사실이 있을 때만 바꾸게 합니다.
- Codex 실행: 읽기 전용 샌드박스, 승인 요청 없음, 모델과 effort 는 기본이 아래 "모델과 effort 기본값" 표의 값(모델을 비워 두면 사용자의 codex 설정 그대로)이고, 사용자 설정 파일에 `codex-opinion` 키가 있으면 그 값입니다.
- 사용자의 MCP 서버와 실행 규칙(`.rules`)은 싣지 않고, 실행 기록도 남기지 않습니다(`--ephemeral`).
- 9분 안에 답이 없으면 끝냅니다.
- 스크립트는 `.am/` 안의 `.md` 요약 하나만 받고 다른 인자는 거부합니다.

</details>

## 커밋 게이트 (`am-gate.json`)

저장소 루트에 둡니다. 없으면 게이트는 아무것도 하지 않고, `am:check` 와 `am:commit` 이 "게이트 미설정"을 알려 줍니다.

```json
{
  "timeoutMs": 300000,
  "commands": [
    { "name": "test", "run": "npm test" },
    { "name": "lint", "run": "npm run lint", "blocking": false }
  ]
}
```

- `run` 은 Windows 에서는 cmd.exe, 그 밖에서는 `/bin/sh` 로 실행됩니다.
- `blocking` 의 기본값은 true 입니다. `false` 인 명령은 커밋 때 돌지 않고 `am:check` 에서만 돌아갑니다.
- `timeoutMs` 는 명령 하나의 제한입니다(기본 300초). 명령마다 따로 줄 수도 있습니다.
- 커밋 한 번에 쓰는 시간 예산은 840초입니다. 넘으면 커밋을 막고 "느린 명령은 `blocking: false` 로" 라고 안내합니다. 훅 자체 시간 제한(900초)을 넘기면 도구들이 차단 없이 통과시키기 때문입니다.
- 첫 번째 blocking 실패에서 멈춥니다. 실행 파일을 찾을 수 없으면 커밋을 막지 않고 경고만 합니다.
- 옛 AlMandu 툴킷의 `am-gate.json` 은 그대로 읽힙니다(`_notes`, `lenses` 같은 키는 무시).

### Unity 예시

Unity 예시는 [examples/unity](examples/unity/) 에 있습니다. MSBuild 로 에디터 없이 컴파일하는 `gate-build.cmd` 와 런타임 확인 절 예시가 들어 있습니다.

### 언리얼(UE5) 예시

언리얼(UE5) 예시는 [examples/unreal](examples/unreal/) 에 있습니다. `am-gate.json` 은 저장소 루트에, `ue-gate.mjs` 는 `DevTools/` 에 복사하고, `runtime-check.md` 의 절은 프로젝트 CLAUDE.md 나 AGENTS.md 에 붙여 넣습니다.

- 커밋 때 C++ 빌드와 자동화 테스트(Automation)가 돌고, 실패하면 커밋을 막습니다. 차단 메시지에는 실패한 테스트 이름과 첫 오류, 또는 컴파일 오류 줄이 나옵니다. 블루프린트 전체 컴파일은 느려서 `am:check` 에서만 돕니다.
- 에디터를 켜 둔 채 커밋해도 됩니다. 대신 열린 에디터에 반영하려면 따로 Live Coding 이나 재시작이 필요합니다.
- 처음 한 번은 사본에서 C++ 전체를 컴파일합니다. 큰 프로젝트는 설치 직후 `node DevTools/ue-gate.mjs build` 를 손으로 한 번 돌려 두세요(게이트의 빌드 제한은 600초).
- 맥(UE 5.8)에서 실측했습니다. 윈도우 경로는 엔진 소스를 보고 작성했고 아직 실측하지 않았습니다. UE4 는 지원하지 않습니다.

<details>
<summary>언리얼 게이트의 프로젝트 사본, 옵션, 엔진 찾기</summary>

- 게이트는 프로젝트(.uproject, Source, Config, Content, Plugins)를 `Saved/AmGate` 에 복사해 그곳에서 DebugGame 으로 빌드·테스트합니다. 그래서 열린 에디터가 코드를 다시 불러오지 않고, 추적 중인 설정 파일도 바뀌지 않습니다.
- 사본은 맥 APFS 에서는 복제(clone)라 디스크를 거의 쓰지 않고, 복제가 안 되는 파일 시스템에서는 Content 크기만큼 씁니다. 바뀐 파일만 다시 복사하고, `Saved/AmGate` 를 지우면 다음 실행에서 새로 만듭니다.
- 옵션: `--project <경로.uproject>`(루트나 한 단계 아래에 하나뿐이면 생략), `--filter <테스트 접두어>`(기본값은 프로젝트 이름, 맞는 테스트가 없으면 실패), `--config Development`.
- 엔진은 `.uproject` 의 엔진 버전으로 찾고, 못 찾으면 환경 변수 `UE_ROOT` 에 엔진 폴더를 지정합니다. `node DevTools/ue-gate.mjs info` 로 찾은 경로를 확인할 수 있습니다.

</details>

### 런타임 확인 안내

`am:check` 는 프로젝트 CLAUDE.md 나 AGENTS.md 의 "Runtime check" 절을 읽고 그대로 실행 확인을 합니다. 앱 실행 명령, 로그 위치, 캡처 방법, 프로브 실행법을 적어 두면 에이전트가 직접 확인하는 범위가 넓어집니다.

## 큰 작업: 오케스트레이터 (`am-orchestrator`, 별도 플러그인)

큰 설계 문서 하나를 끝까지 구현하게 하려면 같은 마켓플레이스의 `am-orchestrator` 를 함께 설치합니다. 설계 문서를 작은 작업으로 나누고, 작업마다 `am:plan` → `am:do` → `am:check` → `am:commit` 을 별도 세션으로 순서대로 돌립니다. Claude Code 전용입니다.

```
/plugin install am-orchestrator@am-workflow
/am-orchestrator:run docs/design.md
```

- 스킬을 실행한 세션이 준비·분할·실행·재개를 알아서 하고, 사용자만 답할 수 있는 것이 생겼을 때만 멈추고 결정 카드로 묻습니다. 묻고 멈추는 기준은 `am:auto-multi` 와 같습니다.
- 작업마다 세션을 따로 띄워 단계별로 권한을 달리 주고, 단계 사이에 게이트(`am-gate.json`)와 작업 트리를 직접 확인합니다. 실행용 브랜치에 커밋만 쌓고 push 는 하지 않습니다.
- 띄우는 세션의 모델과 effort 도 단계별로 정해져 있습니다(값은 [orchestrator/README.md](orchestrator/README.md) 의 "모델과 effort" 표). 대상 저장소의 `.orchestrator/config.json` 에서 바꿉니다. PC 의 모든 저장소에 쓰려면 아래 "모델과 effort 기본값" 의 사용자 설정 파일에도 적을 수 있고, 저장소의 설정이 그보다 우선합니다.
- 띄우는 세션은 이 PC 의 모든 실행을 합쳐 최대 3개까지만 함께 돕니다. `/am-orchestrator:run sessions 2` 처럼 바꾸고, 값은 업데이트해도 남습니다(자세한 것은 [orchestrator/README.md](orchestrator/README.md) 의 "동시 세션 제한").
- `am` 플러그인은 그대로 작게 둡니다. 오케스트레이터는 am 의 스킬과 게이트를 복사하지 않고 설치된 것을 부릅니다.
- 이 플러그인이 설치돼 있으면 `am:auto-multi` 도 큰 작업의 구현을 여기에 넘깁니다. 이때는 `am:auto-multi` 가 쓴 계획 문서를 설계 문서로 쓰고, 다 끝나면 실행용 브랜치를 시작한 브랜치로 합칩니다(위 "`am:auto-multi`" 의 "큰 작업은 오케스트레이터에 넘김" 참고).

자세한 내용은 [orchestrator/README.md](orchestrator/README.md) 에 있습니다.

## 모델과 effort 기본값

Claude Code 에서는 스킬을 부르면 그 차례가 스킬에 정해 둔 모델과 effort 로 돕니다. 설치만 하면 적용되고 따로 설정할 것은 없습니다. `am:auto-multi` 와 오케스트레이터가 띄우는 세션과 두 2차 의견은 아래 사용자 설정 파일로 바꿀 수 있습니다.

<!-- am:models:start -->

| 대상 | 모델 | effort |
|---|---|---|
| `am:plan` | `opus` | `high` |
| `am:do` | `opus` | `medium` |
| `am:check` | `opus` | `high` |
| `am:commit` | `sonnet` | `medium` |
| `am:auto-multi` | `opus` | `medium` |
| `am:auto-one` | `opus` | `medium` |
| `am:auto-agent` | `opus` | `medium` |
| `am:land` | `opus` | `high` |
| `am:sessions` | `sonnet` | `low` |
| 단계 사이 맥락 압축 세션(`am:auto-multi`·`am:auto-one`, Claude Code) | `sonnet` | `medium` |
| 2차 의견 서브에이전트(`am:second-opinion`) | `opus` | `high` |
| `am:auto-agent` 계획 단계 에이전트(`am:stage-plan`) | `opus` | `high` |
| `am:auto-agent` 구현 단계 에이전트(`am:stage-do`) | `opus` | `medium` |
| `am:auto-agent` 점검 단계 에이전트(`am:stage-check`) | `opus` | `high` |
| `am:auto-agent` 커밋 단계 에이전트(`am:stage-commit`·`am:stage-commit-push`) | `sonnet` | `medium` |
| Codex 2차 의견 | `gpt-6.1-sol` | `high` |

<!-- am:models:end -->

- 스킬을 부른 그 차례에만 적용됩니다. 그 차례에는 세션에서 고른 모델보다 우선하고, 다음 입력부터는 세션의 모델과 effort 로 돌아갑니다. 그래서 `am:plan` 의 질문에 답한 뒤나 `am:auto-multi` 가 멈췄다가 답을 받은 뒤의 차례는 세션 값으로 돕니다.
- Sonnet 세션에서 쓰던 경우 Sonnet 으로 정한 스킬(`am:commit`·`am:sessions`) 밖의 스킬을 부른 차례는 Opus 로 돌아 비용이 오르고, Opus 세션에서도 그 스킬을 부른 차례는 Sonnet 으로 돕니다. Opus 를 쓸 수 없는 계정에서 스킬이 어떻게 되는지는 Claude Code 문서에 없고 확인하지 못했습니다.
- 커밋과 단계 사이 압축 세션은 정해진 규칙을 따르고 게이트나 기계 검사가 결과를 지키는 일이라 Sonnet 으로 둡니다. `am:auto-multi` 와 오케스트레이터의 단계 세션은 아래 사용자 설정 파일의 `commit`·`compact` 키로 다시 Opus 로 돌릴 수 있고, 손으로 부른 스킬의 차례는 그 파일로 바꿀 수 없습니다. `am:sessions` 는 스크립트 하나를 돌리고 그 결과를 전하는 일이라 Sonnet·`low` 로 둡니다.
- 세션마다 늘 드는 비용과 스킬 호출 한 번의 토큰은 `claude plugin details am` 으로 확인할 수 있습니다. Codex 의 `am:auto-multi` 는 다른 네 스킬 파일을 함께 읽습니다. Claude Code 의 `am:auto-multi` 는 스킬 파일을 읽지 않는 대신, 단계마다 새 세션이 프로젝트를 처음부터 다시 읽습니다.
- Codex 에는 스킬별 모델 지정이 없어 이 값을 쓰지 않습니다. Codex 세션의 모델 그대로 돕니다.

<details>
<summary>값이 적힌 곳, <code>am:auto-multi</code> 에서의 적용, 환경 변수로 바꾸기</summary>

- 값은 각 `SKILL.md` 머리말(frontmatter)의 `model`, `effort` 에 있습니다.
- Claude Code 의 `am:auto-multi` 는 단계마다 그 스킬을 부르는 새 세션을 띄우므로 단계별 값이 적용되고, 원래 대화에는 `am:auto-multi` 의 값만 적용됩니다. Codex 처럼 한 세션으로 진행하면 다른 스킬을 부르지 않고 파일을 읽어 따르므로 `am:auto-multi` 의 값만 적용됩니다.
- 모델은 별칭으로 적었습니다. 쓰는 Claude Code 버전과 공급자의 모델로 풀리고, 환경 변수 `ANTHROPIC_DEFAULT_OPUS_MODEL`·`ANTHROPIC_DEFAULT_SONNET_MODEL` 로 다른 모델에 연결할 수 있습니다. effort 는 환경 변수 `CLAUDE_CODE_EFFORT_LEVEL` 이 머리말보다 우선하고, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` 은 2차 의견 서브에이전트의 model 을 무시합니다. 조직이 모델이나 effort 상한을 제한해 두었으면 그 제한을 따릅니다.

</details>

### 모델과 effort 바꾸기 (사용자 설정 파일)

`am:auto-multi` 와 오케스트레이터가 띄우는 단계 세션의 모델과 effort 는 PC 마다 둔 파일 하나로 바꿀 수 있습니다. Claude Code 의 두 2차 의견(서브에이전트, Codex)도 같은 파일로 바꿀 수 있습니다(아래 `second-opinion`·`codex-opinion`). Claude Code 전용입니다.

- 위치: `<CLAUDE_CONFIG_DIR 또는 ~/.claude>/am/models.json`(Windows 예: `C:\Users\<이름>\.claude\am\models.json`). 플러그인 폴더 밖이라 업데이트해도 남고, 이 PC 의 모든 저장소에 적용됩니다.
- 처음 만들어지는 파일: am 0.1.36 부터 설치·업데이트 뒤 첫 셸 명령 때(Claude 설정 폴더가 있을 때, Codex 세션의 셸 명령 포함) 파일이 없으면 기본값을 담아 생깁니다. `_` 로 시작하는 키(`_plan` 등)는 꺼진 기본값이라, `_` 를 지우고 값을 고쳐야 쓰입니다. `_` 를 남기고 값만 고치면 아무것도 바뀌지 않습니다. 파일 안 값은 만들 때의 기본값이므로 지금 기본값은 위 "모델과 effort 기본값" 표를 봅니다. 이미 있는 파일은 건드리지 않고, 지우면 다음 셸 명령 때 다시 생깁니다(동작은 파일이 없을 때와 같습니다).
- 예시: 계획은 Opus, 나머지 세션은 Sonnet 으로 돌리고 점검의 effort 만 `medium` 으로 낮춥니다.

```json
{
  "model": { "default": "sonnet", "plan": "opus" },
  "effort": { "check": "medium" },
  "_note": "_ 로 시작하는 키는 메모로, 무시됩니다"
}
```

- `model` 과 `effort` 는 둘 다 생략할 수 있고, 적을 때는 키별 값을 담은 객체로 적습니다. `_` 로 시작하는 키는 맨 위와 `model`·`effort` 안 어디에나 메모로 둘 수 있습니다.
- 값: 모델은 별칭(`sonnet`, `opus`, `haiku`)이나 전체 모델 ID, effort 는 `low`·`medium`·`high`·`xhigh`·`max` 중 하나입니다. 단, 2차 의견 두 키는 아래처럼 따로 검사합니다.

| 키 | `am:auto-multi` 가 띄우는 세션 | 오케스트레이터가 띄우는 세션 |
|---|---|---|
| `default` | 아래 키를 적지 않은 모든 세션 | 같음 |
| `plan` | 계획 | 계획, 결정 답변, `doctor` 의 시험 호출 |
| `do` | 구현, 고치는 구현 | 구현, 수정(`implement` 로 적으면 오류) |
| `check` | 점검 | 점검 |
| `commit` | 커밋 | 커밋 |
| `compact` | 단계 사이 맥락 압축 | 쓰지 않음 |
| `run` | 큰 작업을 오케스트레이터에 넘기는 세션 | 쓰지 않음 |
| `split` | 쓰지 않음 | 분할 |
| `second-opinion` | 2차 의견 서브에이전트(`am:second-opinion`) | 같음 |
| `codex-opinion` | Codex 2차 의견 | 같음 |

- 2차 의견 키(`second-opinion`·`codex-opinion`):
  - 적용: 단계 세션만이 아니라 Claude Code 에서 2차 의견이 도는 모든 곳(손으로 부른 `am:plan` 등, `am:auto-multi`, 오케스트레이터의 계획 세션)에 쓰입니다. Codex 안에서 쓰는 am 에는 2차 의견이 없어 쓰이지 않습니다.
  - `default` 를 물려받지 않습니다. 적지 않으면 위 "모델과 effort 기본값" 표의 값 그대로입니다. 이미 `default` 를 적어 둔 사용자의 2차 의견이 모르는 새 바뀌지 않게 하려는 것이고, Codex 는 Claude 모델 이름을 쓸 수 없기 때문입니다.
  - 값: `second-opinion` 의 모델은 별칭 `opus`·`sonnet`·`haiku`·`fable` 중 하나(전체 모델 ID 는 안 됨), effort 는 위 목록입니다. `codex-opinion` 의 모델은 글자로 시작하고 글자·숫자·`.`·`_`·`:`·`-` 만 쓴 이름(따옴표·공백은 안 됨), effort 는 `minimal`·`low`·`medium`·`high`·`xhigh` 중 하나(`max` 는 안 됨)입니다.
  - 동작: `codex-opinion` 은 codex CLI 가 깔려 있을 때만 쓰입니다. `second-opinion` 은 Codex 가 없어도 적용됩니다. Codex 2차 의견 스크립트가 먼저 이 파일을 읽고 첫 줄 `Claude reviewer: model …, effort … (from the user's setting …)` 로 알려 주며, 값이 기본값과 같으면 그 줄은 나오지 않습니다. 파일이 깨졌으면 Codex 2차 의견이 파일 경로와 이유를 알리며 실패로 표시되고, Claude 2차 의견은 기본값으로 돕니다.
  - 필요한 버전: am 0.1.29, am-orchestrator 0.8.1 이상. 그보다 옛 버전은 두 키를 모르는 키로 보고 세션을 띄우기 전에 멈추므로 두 플러그인을 함께 업데이트합니다.
- 정하는 순서: 모델과 effort 따로, 그 세션의 키 → `default` → 위 "모델과 effort 기본값" 표의 값입니다. 오케스트레이터에서는 대상 저장소의 `.orchestrator/config.json` 이 이 파일보다 먼저입니다(자세한 순서는 [orchestrator/README.md](orchestrator/README.md) 의 "모델과 effort").
- 적용 방식: 정해진 값이 그 스킬의 기본값(위 표)과 다른 단계만 스킬 본문을 머리말 없이 넘기는 inline 으로 부르고 `--model`·`--effort` 를 붙입니다. 슬래시로 부르면 스킬 머리말의 값도 함께 실리는데, 넘긴 플래그와 어느 쪽이 쓰이는지 Claude Code 문서에 없기 때문입니다. 이때 `am:auto-multi` 는 진행 소식에 `model …, effort … from the user's setting <파일>` 한 줄을 남기고, 오케스트레이터는 실행 첫 줄과 `run --dry-run` 의 "스킬 호출 방식"에 inline 으로 바뀐 단계를 보여 줍니다. 값이 같거나 파일에 적지 않은 단계는 지금과 똑같이 돕니다.
- `am:auto-multi` 는 단계 명령마다 파일을 다시 읽으므로, 실행 도중 고치면 다음 단계 세션부터 고친 값이 쓰입니다.
- 쓰이지 않는 곳: 직접 부른 스킬의 차례(`am:auto-multi` 를 부른 대화 자체, 손으로 부른 `am:plan` 등, 손으로 부른 `am-orchestrator:run`. 2차 의견 키는 예외, 위 참고), Codex 안에서 쓰는 am, 세션을 띄우지 못해 한 세션으로 진행하는 경우.
- 잘못 적으면: 깨진 JSON, 모르는 키, 빈 모델 이름, 목록에 없는 effort, 읽을 수 없는 파일이면 세션을 하나도 띄우지 않고 파일 경로와 문제를 알리며 멈춥니다(`am:auto-multi` 는 영어 한 줄, 오케스트레이터는 한국어 안내). 파일을 고치거나 지우면 예전처럼 돕니다. 2차 의견 키의 값이 규칙에 어긋나도 같습니다. 손으로 부른 스킬에서는 Codex 2차 의견이 실패로 표시됩니다.
- 확인하지 못한 점: 고른 모델에서 쓸 수 없는 effort(예: 일부 모델의 `xhigh`·`max`)나 조직이 막은 모델을 적었을 때 Claude Code 가 어떻게 하는지는 확인하지 못했습니다. 2차 의견 두 키를 뺀 모델 이름은 파일 검사에서 확인하지 않으므로(빈 이름만 막음) 오타는 세션이 뜬 뒤에야 드러납니다. Agent 호출에 넘긴 effort 가 서브에이전트 머리말보다 우선하는지도 문서로 확인하지 못했습니다(실행 중 `/tasks` 의 서브에이전트 줄로 확인할 수 있습니다). 이 파일로 넘긴 2차 의견 값과 위 환경 변수(`CLAUDE_CODE_EFFORT_LEVEL` 등) 중 어느 쪽이 쓰이는지도 확인하지 못했습니다.

## 남은 메모리 기준 (사용자 설정 파일)

메모리가 매우 부족하면 Claude Code 가 쉬는 세션의 백그라운드 실행을 끕니다. 그래서 여러 세션이 함께 도는 동안 PC 의 남은 메모리가 기준보다 적으면 새 세션의 시작을 미룹니다. Claude Code 전용입니다.

- 위치: `<CLAUDE_CONFIG_DIR 또는 ~/.claude>/am/settings.json` (Windows 예: `C:\Users\<이름>\.claude\am\settings.json`). 값을 바꾸는 명령은 없어 파일을 직접 고칩니다. 플러그인 폴더 밖이라 업데이트해도 남고 이 PC 의 모든 저장소에 적용됩니다. 옆의 `models.json` 과 다른 파일이며, 오케스트레이터의 `am-orchestrator/settings.json`(동시 세션 수)과도 다릅니다.
- 처음 만들어지는 파일: am 0.1.36 부터 위 `models.json` 과 같은 때에 파일이 없으면 생기며, `"minFreeMemoryMB": null`(기본 동작)로 적혀 있어 수를 적어야 기준이 바뀝니다. am 0.1.48 부터 새로 생기는 파일에는 아래 `stageMcpServers` 설명(`_stageMcpServers`, 메모)도 적힙니다. 이미 있는 파일은 건드리지 않고, 지우면 다음 셸 명령 때 다시 생깁니다.

```json
{
  "_note": "_ 로 시작하는 키는 메모로 무시됩니다",
  "minFreeMemoryMB": 6144
}
```

- 값: MB 단위의 0 이상의 수, 또는 `null`(적지 않은 것과 같음). `0` 은 끔입니다. 적지 않으면 Windows 에서만 기본 2048MB 를 쓰고 macOS·Linux 에서는 꺼져 있습니다. 적은 값은 모든 OS 에서 씁니다.
- 적용: `am:auto-multi` 의 단계 세션(오케스트레이터에 넘기는 세션은 빼고)과 오케스트레이터가 함께 씁니다. 저장소의 `.orchestrator/config.json` 에 쓸 수 있는 `minFreeMemoryMB` 가 있으면 그 저장소의 오케스트레이터만 그 값을 씁니다(순서: 저장소 값 → 이 파일 → 기본). `am:auto-multi` 는 언제나 이 파일을 씁니다. 자세한 것은 [orchestrator/README.md](orchestrator/README.md) 의 "동시 세션 제한" 절에 있습니다.
- 언제 읽나: 단계 명령마다 다시 읽으므로, 실행 도중 고치면 다음 단계부터 적용됩니다.
- 잘못 적으면: 깨진 JSON, 모르는 키, 수가 아닌 값(예: `"6GB"`), 음수, 읽을 수 없는 파일이면 세션을 띄우지 않고 파일 경로와 문제를 알리며 멈춥니다(`am:auto-multi` 는 영어 한 줄, 오케스트레이터는 한국어 안내). 고치거나 지우면 다시 돕니다. 파일이 없으면 설정이 없는 것입니다.
- 알아 둘 점: 다른 세션이 도는 동안에는 오래 기다릴 수 있습니다. 오케스트레이터는 1~3초마다 다시 보고 자기 세션 사이 틈이 거의 없어, `am:auto-multi` 단계는 8분마다 다시 뜨기만 할 수 있습니다(누가 먼저 시작할지는 정해져 있지 않음). macOS 에서는 Node 가 알려 주는 남은 메모리에 되찾을 수 있는 메모리가 빠져 수치가 실제보다 낮게 잡히므로, 기준을 적으면 생각보다 자주 기다릴 수 있습니다. 이미 돌고 있는 세션의 메모리가 치솟는 것은 막지 못합니다.
- 필요한 버전: am 0.1.35, am-orchestrator 0.8.5 이상. 더 오래된 오케스트레이터는 `am:auto-multi` 단계를 메모리 확인에서 세지만 이 파일은 읽지 않고 저장소 값만 씁니다. 두 플러그인을 함께 업데이트합니다.

### 단계 세션의 MCP 서버 (stageMcpServers)

`am:auto-multi` 의 단계 세션(압축·다시 묻기·오케스트레이터에 넘기는 세션 포함)은 기본으로 MCP 서버를 하나도 띄우지 않습니다. 단계마다 MCP 서버 한 벌(npx·node 등)이 뜨지 않아 메모리를 덜 씁니다. 단계 세션에서 브라우저 같은 MCP 도구가 필요하면 같은 파일에 적어 켭니다.

```json
{
  "stageMcpServers": true
}
```

- 값: `true` 면 단계 세션도 평소 세션과 같은 MCP 서버를 씁니다. `false`, `null`, 적지 않음은 모두 끔(기본)입니다. 그 밖의 값(예: `"yes"`, `1`)은 잘못 적은 것으로 보고 위와 같이 세션을 띄우지 않고 멈춥니다.
- 적용: `am:auto-multi` 의 단계 세션만입니다. 오케스트레이터가 띄우는 세션은 이 값과 상관없이 그대로입니다.
- 언제 읽나: 단계 명령마다 다시 읽으므로, 실행 도중 고치면 다음 단계부터 적용됩니다.
- 필요한 버전: am 0.1.48, am-orchestrator 0.9.8 이상. 더 오래된 오케스트레이터(0.9.7 이하)나 am 은 이 키를 모르는 키로 보고 세션 없이 멈추므로, 이 키를 적기 전에 두 플러그인을 함께 업데이트합니다.

## 우회와 한계

- 게이트를 끄려면 에이전트 세션을 시작하기 전에 환경 변수 `AM_GATE=off` 를 설정합니다. 차단 메시지에는 우회 방법을 일부러 적지 않았습니다(에이전트가 스스로 우회하지 않게).
- 게이트는 안전망이지 보안 장치가 아닙니다. 스크립트 안에서 하는 커밋, MCP git 도구, 사람이 터미널에서 직접 한 커밋은 거치지 않습니다.
- 게이트는 스테이징된 내용이 아니라 작업 트리 전체를 빌드합니다.
- Unity 예시 게이트는 .csproj 에 아직 들어가지 않은 새 .cs 파일을 컴파일하지 않습니다. 그래서 런타임 확인 첫 항목을 에디터 재컴파일로 둡니다.
- 언리얼 예시 사본에는 프로젝트의 다섯 가지(.uproject, Source, Config, Content, Plugins)만 들어갑니다. `.uproject` 가 프로젝트 밖 폴더를 상대 경로로 가리키면(예: 추가 플러그인 폴더) 사본에서는 그 경로를 찾지 못합니다. 심볼릭 링크·정션은 복사하지 않고 출력에 알립니다.

## 개발

플러그인은 스킬 9개와 옛 이름 안내 스킬 3개, 2차 의견 서브에이전트 1개, 커밋 게이트 훅 1개(`hook.mjs`·`gate.mjs`), `am:auto-multi` 의 오케스트레이터 넘김 훅 1개(`handover.mjs`), `am:auto-multi` 가 단계마다 새 세션을 띄우는 단계 세션 스크립트 1개(`stage.mjs`), 그 단계의 진행 소식을 기다렸다가 알려 주는 스크립트 1개(`progress.mjs`), Codex 2차 의견 스크립트 1개(`codex-opinion.mjs`), 사용자 설정 파일(모델·effort)을 읽는 스크립트 1개(`user-models.mjs`), PC 전체 설정 파일(남은 메모리 기준·단계 세션 MCP)을 읽는 스크립트 1개(`user-settings.mjs`), 두 사용자 설정 파일이 없을 때 기본값을 메모로 적어 만드는 스크립트 1개(`user-files.mjs`), 남은 메모리를 확인하고 실행 기록을 남기는 스크립트 1개(`memory-guard.mjs`), 세션이 남긴 프로세스를 정리하는 스크립트 1개(`proc-tree.mjs`)와 PC 에서 돌고 있는 am 세션을 보여 주는 스크립트 1개(`sessions.mjs`)로 되어 있습니다.

플러그인을 고치는 사람은 저장소 주소 대신 로컬 경로(예: `C:\Projects\am`)로 설치하면, 커밋하지 않은 수정도 바로 시험할 수 있습니다.

여러 SKILL.md 가 함께 쓰는 문구(공통 규칙 블록, `am:auto-one`·`am:auto-agent` 의 공유 블록)는 저장소 루트 `shared/` 의 원본만 고치고 `node scripts/skills.mjs` 로 반영합니다(`node scripts/skills.mjs --check` 는 어긋난 파일만 알려 줍니다).

커밋 전 확인 명령(테스트·`claude plugin validate`)은 [CLAUDE.md](CLAUDE.md) 의 "Before committing" 에 있습니다.

```
claude --plugin-dir plugin plugin details am
```

오케스트레이터 플러그인을 고쳤을 때:

```
claude --plugin-dir orchestrator plugin details am-orchestrator
```

유지보수 규칙은 [CLAUDE.md](CLAUDE.md) 에 있습니다.
